# Contributing to logex

**What this file is.** Working practices, distilled from things that actually went wrong in
this repository. It is prescriptive rather than descriptive: most of it postdates the
commits it cites, and it is a small single-maintainer project, so treat it as advice with
receipts rather than as established ceremony. Every rule below exists because something
specific broke.

**What it is not.** A workflow. There is CI, which runs the gates of "Before you commit"
on every push and pull request (PLAN.md §4·B3), but no branch protection and no review
requirement; recent history is direct-to-main. Do not invent process here.

wrong and is not.

## The one rule

**Verify by executing, not by reasoning.**

Every claim in this repository's documents that turned out to be wrong was arrived at by
reasoning; every one that survived was executed. That is not a figure of speech — it is the
observed pattern across four separate audits of these documents. A plausible-sounding
statement about this codebase is roughly a coin flip.

So: run it. Paste the real output. If you cannot run it, say so and mark the claim
`unverified` — `docs/naming.md` does this in eight places and is more trustworthy for it.
Never close the gap with a guess.

## Working on the code

### The test output will lie to you

Judge `mix test` by its exit code. Elixir 1.20 reports a partial failure as
`Result: 39/40 passed`, and a script grepping for `[0-9]+ passed` reads that as forty
passes. It happened while writing the golden record's mutation table: every mutation
"passed" the suite, including one that `printer_test.exs` plainly catches, until the table
was re-run on exit codes.

The build used to lie too. While the front end was generated by leex and yecc, Mix
regenerated `src/*.erl` only when the `.erl` was absent or a whole second older, so a
grammar edit in the same second as the last build was silently ignored — the single most
expensive trap this project had (`PLAN.md` §2·M0-3). The lexer and parser are ordinary
`.ex` files now, and Elixir 1.20's compiler compares size and content as well as mtime, so
little of it is left: measured on 1.20.4, an edit in the same second as the last build is
picked up, and only a *second* same-size edit landing in that same second was lost — once
in five attempts. If an edit to the lexer or parser seems to do nothing, `mix compile
--force` settles it.

A checkout built before the rewrite keeps the old front end's modules in `_build` after
pulling. The first build of an environment that was built before the pull deletes the
generated `src/*.erl` but leaves their modules behind; building any other environment
compiles them afresh. Run `rm -rf src/*.erl _build` once. `frontend_test.exs` fails, naming
that command, until you do.

### The toolchain

Elixir 1.20.4 on Erlang/OTP 28, the pair `mix.exs`, `shell.nix`, `flake.nix`,
`.tool-versions` and CI pin; `guides/howto/install-and-run.md` shows a reader's
`.tool-versions` with the same two lines, which a change of the pair changes too. `nix develop` (or `nix-shell`) gives it, and so does
[asdf](https://asdf-vm.com) from `.tool-versions`: `asdf plugin add erlang`, `asdf plugin
add elixir`, then `asdf install` in the checkout. `mix.exs` requires `~> 1.20`, so on an
older Elixir `mix` aborts before it runs anything; install the pinned pair rather than
loosen the bound (below). Nothing in this repository is run or kept working on an older
toolchain: the receipts `PLAN.md` records from Elixir 1.14, before the bound moved, are
history (decision 359).

### A fix needs a test that fails when the fix is reverted

Check by reverting, not by reasoning.

`3f3b104` fixed two real bugs in one regex and shipped with no test. Reverting it left
`mix test` fully green while `tokenize("ote a")` was a hard lex error again. It took
`b8fc743` to close, with one test per bug — each failing only for its own half:

    NAME = [a-zA-Z_][a-zA-Z0-9_]*   (as shipped)   0 failures
    NAME = [a-zA-Z_][a-zA-Z0-9_]+   quantifier     1) single-character tag
    NAME = [a-zA-Z_][a-zA-z0-9_]*   char class     1) brackets
    NAME = [a-zA-Z_][a-zA-z0-9_]+   both           1) and 2)

A single test asserting "tags work" would have passed with half the regex broken. Make each
test fail for exactly one reason.

New code has no fix to revert: revert a feature commit's `lib/` and every test that calls
it fails, whatever those tests assert. Revert each *rule* instead, one at a time — each
clause, guard, fallback and sort the diff adds — and take the list from the diff, not from
what the tests were written to catch. `ee91fe5` recorded 31 mutants, each red, yet its
`on_line(%Tag{line: nil})` clause could be deleted with all 184 tests green at `4a1079c`.
The review of M1-5 found fifteen rules no test failed without, twelve of them in code M1-5
added (`b8a9bd8`); the review of M1-3 had 52 of its 112 mutants survive (`0e83b5f`).

A mutant that survives is not shown redundant by an argument that it is. OE-1's
`3e45ea8` kept its one survivor, its table's mutant E46 (not a decision: that commit's
mutants E1–E71 share their letter with decisions E1–E9, which a table should not), a
timer's value that fits by its member keys where "is a map" would do, on the reasoning
that "under the contract, the only map a state can hold under a timer's name is a
ton's". The next commit's contract walk, under seed
`{2, 2, 2}`, reached a plain swap that left `%{"pre" => 40}` over a bool, a map that
would have reached the timer rules with no `.acc`, `.dn` or `.en`; `c1e5d54` added the
test and corrected the claim. Give a survivor a test or delete its rule, and if you keep
it on an argument, say that the argument is all there is.

A mutant is judged by the full suite's exit code, and a busy machine can make that
code lie the other way: a mutation run is several suites at once, and the runner's
real-clock tests have margins of real milliseconds. In M5-5's review `trip_test.exs`
failed while three mutation runs loaded the machine, so a mutant would have counted red
for a test that has nothing to do with it; under eight busy loops on four cores, 6 of 15
runs of `trip_test.exs` failed, on three tests whose margins were about 100 ms, since
widened (`8cef95b`). A mutant red only on a real-clock test is run again alone before it
counts, and a new real-clock test is run under load before it lands: give each margin
hundreds of milliseconds where the point it makes allows.

A walk over a rung must reach a group nested in another, and a test must say so. M1-6's
spike walked a rung for its `ton`s and for its comparisons of two literals, and cutting
either walk to one group deep left the whole suite green: a nested `ton t1 5000` then
started with `.pre` 0 and was done at once. "A group nested in another" is a standing row
of every rung walker's mutation table.

### Beware of a green suite

`690fc2d` fixed an atom that no stage in the pipeline could produce — `get_arg/2` matched
`:lit_int` while everything upstream emitted `:int_lit`, so the entire integer-literal
feature was dead end to end. The suite stayed green from `0f7d77f` until that fix, because
the evaluation fixtures hand-wrote the same misspelling, cancelling it out.

`test/logex/end_to_end_test.exs` exists because of that: it drives source to an environment
and its assertions name no IR tag, so it can only pass if the stages genuinely agree. (One
helper matches the `{:routine, {:rungs, _}}` wrapper to count rungs — that is the only AST
shape in the file.) **Add to it when you change behaviour.** `instructionize_test.exs` and
`evaluation_test.exs` hand-type the input to one stage and cannot catch a seam at all;
`lex_and_parse_test.exs` starts from a source string, so it crosses the tokenize→parse seam
and no further.

Also beware assertions that cannot see the bug. The empty-rung fix was first drafted with
an acceptance block that printed only the environment — provably identical with and without
the phantom-rung defect it was meant to verify. `b65e756` shipped with rung-count
assertions instead. Assert on the thing that changed, not on a projection of it.

Moving a test can drop what it saw, and a commit that only rewrites tests cannot be checked
by reverting it: the old form still passes. Check it with the old form's mutants instead.
Wherever the rewrite narrows an assertion, name the mutant only the dropped part caught,
apply it, and watch the new form fail. `72bee33` moved the suite off `evaluate/2`; the
printer's `{false, %{"xx" => 0}}` became `%{"xx" => 0}`, because no public function returns
power flow, and the dropped `false` had been the one guard on the power a de-energised
`ote` passes on. With that clause passing `true`, the suite failed at `02d555e` and passed
at `72bee33`, and stayed green until `b8a9bd8`.

A property pins only what its generator reaches. `api_contract_test.exs` went red for
every mutant in its own table (`02d555e`), yet it never declared a dint `var_input`, never
produced 2 of its 9 refusal kinds, and gave a bad program or state only to `call/4`: it
caught none of twelve rule-breaks off those paths. It now asserts its reach, the way
`printer_test.exs`'s `@required_shapes` does — every compile stage, every refusal kind a
host can cause — and that each call is refused exactly when it is a mistake. Give a new
property the same, and run its reach under a few other seeds before trusting it: M1-6's
first draft saw a timer with a negative preset under the fixed seed and under none of
eight others. The same holds inside a property: OE-1's walk restated decision 29's two
exceptions and the condition on undoing a resume, but under its seed its generator
reached none of the cases they decide, so deleting any of them, from the walk or from
`lib/`, left the walk green. Give each condition of a restated rule a reach atom for the
case it decides, and measure the reach under seeds the draw was not tuned on: the walk's
draw, weighted until its reach held under 25 seeds, still missed an atom at 4 of the
seeds 1 to 60, all outside those 25, until it took 400 walks instead of 200. One family
of seeds is one sample too: the compile, runtime and resource walks of
`api_contract_test.exs` each held their reach under their own seed, yet at 600 sources,
40 programs and 150 configurations they missed an atom in 9 of 780 runs under the seeds
`{n, 77, 7}`, `{n, 1, 1}` and `{7, n, 2026}`. Size a walk's draws from its rarest atom's
rate per draw, read over one family, so that the atom is expected 15 times a run or more,
and then hold the reach under 60 seeds or more drawn from more than one family the draws
were not sized on. Those three now take 2,000, 150 and 1,000, and each holds under 100
seeds of each of the three families.

A property that restates a rule cannot catch that rule's defect. OE-1's edit walk checks
every report entry against its rule, restated from the two programs' text. The
restatement is written from the same design as the code, so a misreading of the design
lands in both, and they agree. What can catch it is a check that knows nothing of the
rule: a report's listed writes, replayed on the state before its step, give the state
after it; a held value is the one the walk last saw the host receive, or, for an output
the next program still shows, the one its next scan gives; a one-shot pulses only where
the previous scan ran the same `ons` rung text with its condition 0; a test then an
untest with no scan between leaves the original as it was; and no scan lets a timer gain
more than its own time. Switch the restatement off and run the mutation table
again to see how far those reach: for the timers they still failed 10 of 14 mutants
(`c1e5d54`), and for the one-shots 14 of 18 (`1a39feb`). The eight they passed are what
a misreading shared with the restatement looks like (a `.pre` record with its pair
swapped, no preset taken outright where a `ton` returns, a `.dn` forecast at the
boundary or for an idle timer, line numbers compared, a block kept for a bit no `ons`
reads, an unsorted list, a cost), and only `edit_test.exs`'s worked cases fail them. So
a property needs both kinds of check, and a rule the independent ones cannot see needs a
worked test of its own. An independent check stays independent only while it takes
nothing from the code it checks: the round trip first took its exemptions from the
reports, every write the edit listed as `:added` or `:input`, so an edit that reset an
input whose section changed, and reported it, passed the walk; and it exempted a resume
no rule had approved. The review of OE-1 found both, and the round trip now finds what
a switch starts from the two programs' text and the state alone.

The same trap has a live instance. `PLAN.md` §6 keeps the sequential `env` threading in the
`{:branches, _}` reducer deliberately, and B7 invites rewriting that reducer. Until
`end_to_end_test.exs` grew "a later leg sees what an earlier leg wrote", making the legs
independent left that whole file green and failed only a hand-typed fixture called
"evaluates an AST with OTEs" — a name giving no hint an invariant was at stake. If you
declare something load-bearing, name a test after it.

### New instructions

Two steps, in `CLAUDE.md`, and step 1 has a test behind it.

1. **Survey the name first** — add a stanza to `docs/naming.md`. `test/logex/naming_test.exs`
   fails if a mnemonic reaches `@instructions` without one.
2. **Then the code** — the mnemonic and its operand signature in `@instructions` (each
   operand's access and type, as `compiler.ex` describes above the map), plus
   **two** `evaluate/3` clauses, in `Logex.Runtime`. The de-energised `{false, env}` clause
   is mandatory; without it the instruction works on an energised rung and raises `FunctionClauseError`
   the moment a contact opens. The new mnemonic becomes a reserved word, in any case, so it
   breaks any program with a tag of that name: say so in the commit.

## Working on the documents

### Anchor on names, not line numbers

`PLAN.md`'s line references have gone stale three times. The third was self-inflicted:
`6802f9c` anchored every `compiler.ex` reference on clause heads — and in the same commit
edited `CLAUDE.md`, shifting every `CLAUDE.md` line reference in `PLAN.md`. `747d630`
cleaned that up.

Cite `the {:xic, _, [{:name, _, arg}]} clause of evaluate/3`, not `compiler.ex:79`. Clause heads,
function names, grammar productions and bullet titles survive edits above them. §1 and §2
keep their numbers deliberately; §2 is explicitly historical.

They do not survive their own removal. When a commit renames, moves or removes a function
or clause, grep the documents for each old clause head, not only the function's name, and
fix every hit in that commit or the documents pass after it. A name can outlive its
clauses: B5 (`d0870b3`) kept `evaluate/2`, private in `Logex.Runtime`, but removed its
`{:branches, _}` and `is_list(branch)` clauses. The documents pass (`4a1079c`) fixed every
`Logex.Compiler.evaluate/2`, and left `PLAN.md` §6 and B7 citing "the `is_list(branch)`
clause" until `b8a9bd8`.

### Landing work stales the plan

`PLAN.md` §1's counts, §7's Status column and the README's "What has landed" list all go
out of date when you ship. This repo brings them current in a separate audit pass
(`440bc83`, `4e256ff`) rather than in the same commit — either is fine, but the pass has to
happen. A plan that disagrees with the code is worse than no plan, because it is trusted.

Any language change stales the README: a new instruction adds a row, a syntax change
touches the syntax list, the instruction table *and* the worked examples. The examples'
output is real, and `test/logex/readme_test.exs` keeps it so (decision 359), in README
and, since decision 546 (e), in every page `docs/pages.exs` lists that is not a document
from before that decision ("Writing a page of the documentation", below, for what a page
adds to this): each `elixir`
block followed at once by a block beginning `$ mix run x.exs` is an example, run in a
fresh VM in a directory of its own, `tmp/readme/<page>/x.exs/`, its output compared
exactly with the rest of that block. A block a script reads from the disk is marked by
the line straight above its fence, `<!-- file: conveyor.ld -->`, which GitHub does not
show, and from there on it is that file of every later example of its page; a file README
only describes in
prose, `faster/packing.logex` "being `packing.logex` with `interval 5`", is made in the
test's `@derived` table from the file it names, and a script README shows as the rest of
another, `a_trip.exs`, in its `@continues`, each beside README's words, which the test
checks are still there. The real-clock example's figures line, which README says is this
run's alone, is compared by its beginning. An `elixir` block that no `$ mix run` block
follows is no example, so the test refuses one unless its `@fragments` names it by its
first line, a fragment of prose the test parses and, where the table gives it a setup, runs
in that setup, held to what README's prose says of it (decision 365): today the one call
made from another process in "Running a plant on the clock", run on a runner whose first
round's write was slow, which must wait for an owed round and then answer. So a new
example needs its files marked and its output shown, and
a changed one is run by the suite: when the test fails, the code or the README is wrong,
and the diff it prints says which line. The prose, the syntax list and the instruction
table have no test behind them.

The examples are files a host can copy, under `examples/` (decision 517 (b)): every
script and every file README shows, the files `@derived` makes and each continued script
whole, beside `examples/mix.exs`, a project naming logex in the directory above, so that
`mix run scan.exs` from there runs one as README does. The test runs each example from
its files there, copied to its directory under `tmp/readme/`, holds every block README
shows to its file and `examples/` to nothing else, and runs `scan.exs` through the
project with `mix run`, its build kept under `tmp/`; so a block changed in README is
changed in its file in the same commit, and a path is marked once on a page, a later
file of the same name named apart, `broken_retain.logex`. `test/logex/clauses_test.exs`
holds every script there to the clauses rule, as it holds the harness.

### Writing a page of the documentation

The documentation is a site ExDoc builds (decisions 546 to 548): README first, the pages
under `guides/`, and the modules' own documentation. `docs/style-guide.md` is the rule
for a page, who reads it and the words it may use, with three pages beside it:
`docs/house-manner.md`, the forms of these older documents a page does not have,
`docs/examples-and-pictures.md`, the marks of a block and of a picture, and
`docs/check-a-page.md`, which of the seven kinds a page is and how to add one, check it
and build the site. Read them before writing one, and start from the kind's template
under `docs/templates/`. What it rests on, each held by a test:

- **One list of pages.** `docs/pages.exs` has a line for every Markdown file of the
  repository, its kind and its place in the site, one line a page, which the formatter
  is kept off; `mix.exs` builds the site from it, and a file with no line fails
  `test/logex/docs_test.exs`. The ten documents from before decision 546, this one among
  them, are listed `:legacy`: the writing rules are not applied to them, and all but
  README are read on GitHub, not in the site, where no script follows their links;
  README's examples are run and its links followed, as a page's are. The ten are named
  in the test, and no page joins them: a new page has its kind, and README, written
  again, is a `:readme`.
- **One reading of a page.** `scripts/page.exs` cuts a page into prose and code blocks
  for the checker, the site, the pictures and the examples' test alike, as GitHub cuts
  it. A fence it cannot take as the page means it, one not closed or with more than a
  language after it, is a failure with the page's name and the line, and stops no other
  page's tests; on a page under the rules a block fenced with tildes or shown by
  indentation, an HTML tag and a comment left open are failures too, since each would
  be shown to a reader and read by no check (`test/logex/page_test.exs`).
- **Every example is run.** The examples' test above reads every page that is not
  `:legacy`, each judged on what it shows. A file another page shows is given to a page's
  examples by a link the reader sees, ``[`motor.ld`](first-program.md)``, and a script
  that names a file its page does not give it is a failure of the reading, with the
  file's name. A block that is no example carries a mark, `part of`, `fragment` or
  `unchecked`, or is of a language the suite compares with nothing, a diagram, data,
  Markdown shown as Markdown, or a command line that shows commands alone; any other
  block the test refuses. What it compares with nothing the checker counts for a
  reviewer, each marked block and each such block. `mix test test/logex/readme_test.exs
  --only page:<path>` runs one page's examples, `--only reading:<path>` its reading
  alone, in two seconds however many the pages.
- **The writing rules a script can measure are measured.** `elixir scripts/prose.exs`
  checks every page that is not `:legacy` against the rules of the style guide, a
  sentence's length, a word with a plainer one, a tense the rules leave out, and counts
  what it cannot judge, a passive verb among them; `test/logex/prose_test.exs` holds each
  rule and every page. It refuses the literal forms of its lists and reads no meaning:
  the manner in other words passes it, and a reviewer reads for that.
- **No picture is drawn by hand.** `mix run scripts/draw.exs` draws a ladder from its
  `.ld` text and a timing diagram from a run, into `guides/assets/`, each named by a mark
  above its picture; `test/logex/pictures_test.exs` holds every picture to what the script
  draws today, so a picture cannot disagree with the program it shows, and two marks
  that name one file and differ in its source are refused, on one page or on two.
- **The site builds with no warning but the ones listed.** `scripts/docs.sh` builds it and
  compares what ExDoc warns of, and every link of the pages it wrote that leads to a
  file or a heading of the site, with `docs/site-warnings.txt`, which lists what the
  modules' own text gives today; a new warning or such a dead link is `DOCS-FAIL`. A
  link to a heading of a Markdown file read on GitHub is held to that file's headings
  when the page is staged; a link to another site is followed by no script.
  `.github/workflows/docs.yml` runs it on every push and publishes the site from `main`.

The rule below holds in the pages too: the glossary gives a term's word in "the
conventional set" beside IEC 61131-3's, and names no vendor for it; a page names Logix
only where it compares what a controller does, as README does. Whether a user's page may
name the product a reader comes from is a question `PLAN.md` puts to the maintainer under
DOC-1's step 1.

### Do not restore vendor names

`docs/naming.md`'s Conventional column is unattributed on purpose, and the policy extends
to prose in every document. Rule 2 of the naming rule says to name which vendor a mnemonic
came from; for that one column, "the conventional set" *is* the name. This is a project
choice, not an oversight to fix.

## Things that will bite you

- **Do not relax `mix.exs`.** On an older toolchain `mix compile` aborts and the obvious
  fix is to loosen `elixir: "~> 1.20"`. Install the pinned pair instead, Elixir 1.20.4 on
  OTP 28, with `nix develop` or `asdf install` ("The toolchain", above). The code itself
  needs it: `lib/` calls `Map.split_with/2`, new in 1.15, so no sandbox that patches the
  bound on an older Elixir builds it either. An automated audit of this repo once
  recommended relaxing it, having mistaken a test rig's patched copy for the repository's
  own — a wrong conclusion from real evidence.
- **Nothing checks the grammar for ambiguity.** The parser is written by hand (its
  moduledoc gives the grammar and which function parses each production), so there is no
  generator to report a conflict. What stands in
  for it: `printer_test.exs`'s round-trip properties, whose generator must reach every
  production (`@required_shapes`), and the golden record, which pins what the language
  accepts. A new syntax form goes into that generator before it lands. When yecc was in
  use its conflict warning did not fail `--warnings-as-errors` either; the replacement for
  that gate was measured, not assumed (`PLAN.md` §6).
- **Do not grow a binary one byte at a time.** `<<acc::binary, ch>>` from `""` looks like
  an accumulator and is a fresh off-heap, 256-byte buffer per lexeme. It made the lexer up
  to 2.2x slower than leex with every token right; `bin_opt_info` flagged only the lesser
  cost beside it, returning `{acc, rest}`. Measure the run and cut it from the source once;
  `lexer_binaries_test.exs` fails otherwise.
- **Test a pass over the program for growth, not speed.** `Logex.Warnings` walked every use
  once per declared tag (`a34fa87`), so compiling was quadratic — 16,000 tags took 7.5 s
  against 0.3 s — with every warning right and the suite green for seven commits.
  `b8a9bd8` groups the uses once. Compile two sizes and compare reductions
  (`Process.info(self(), :reductions)`), not time, so the bound holds on any machine:
  "compiling stays linear in the program's size" in `logex_test.exs` sees 4.3x to 4.9x for 4x
  the tags alone, and saw 14.2x. A new pass over rungs or tags must be reached by that test's
  program, or get a test like it. **A large heap hides a copy**: `b4be654` moved that test
  into a process whose heap no collection fills, to steady it on a busy machine, and a
  walk that appended each rung with `++`, 12x the time, then grew only 5.3x to 6.4x and
  passed its bound now and then, since `++` is charged few reductions and nothing copied
  what it built again; in the VM's own heap it grew 12.4x to 12.9x. So the test measures
  in both, each with a bound of its own. **Growth in depth is a second axis**: M1-6's path pass
  copied what it found in a group at every level of nesting, so a rung 8,000 groups deep
  took 2.9 s, and the size test, which never nests, stayed green. "compiling stays linear
  in the depth of nesting" reaches every walk into a group, the one that finds the first
  rung's line for a declaration after it included: its first program had no such
  declaration, and a copying rewrite of that walk passed it. It compares 500 and 8,000
  levels, not 500 and 2,000, because `++` is charged few reductions for what it copies: a
  walk that copies with `Enum.flat_map` at every level grew 4.0x to 4.7x for 4x the depth,
  within the size test's bound, and grows 20x or more for 16x, where a linear compile grows
  about 16x. **Measuring a mutant moves its figure**: reductions count garbage collection,
  whose cost depends on what ran before, so the compiler's two copying walks of M1-6 give
  50x to 61x in the committed test, but gave 29x in a copy of it that also timed 2,000
  levels, the figure first written here. Read a figure from the committed
  test's own failure message, and quote the fixed compile's and the lowest mutant's, not a

## Before you commit

    mix format --check-formatted
    mix compile --force --warnings-as-errors
    MIX_ENV=test mix compile --force --warnings-as-errors
    mix test --warnings-as-errors
    scripts/dialyzer.sh

All five must pass, judged by exit code; the third builds `lib/` as the suite builds it,
and the fifth is OTP's own Dialyzer over the dev build (decision 549; below).
`scripts/gate.sh` runs the five in order and names the tests that failed ("Scripts",
below).
CI (`.github/workflows/ci.yml`) runs the same five, each a step of its own judged by its
exit code, on every push and pull request, on Erlang/OTP
28 and Elixir 1.20.4 through `erlef/setup-beam`: a red run there is a red commit, whatever
ran green here, and a work item's report says so. Its test step ends a red run's log with
each test that failed, `file:line: Module: test name` a line, as `scripts/gate.sh` does
here: it deletes ExUnit's
failures manifest, runs `mix test --warnings-as-errors` with its output in the log, and
then `elixir scripts/failed.exs --exit` with the suite's code, which names the tests a red
run failed, or says why it names none, and exits with that code, and makes a run that
exited 0 and wrote no manifest, a suite a test halted, red (decision 515 (e)).
`test/logex/scripts_test.exs` runs the step as the workflow writes it, and holds the
workflow to every gate on every push and pull request, no step carrying a key, an `if:`
or `continue-on-error:` for one, that could skip it or let its failure pass: on GitHub a
failing suite under `continue-on-error: true` is a green job (RV-22's review, run 7). A
push runs CI on the commit it ends at alone, so push each commit you want checked, and
read its run before you call it landed. `--force` recompiles every module in `lib/`, so a
warning in a file you did not touch still fails the build. `mix compile` never compiles the
tests, and plain `mix test` exits 0 when they warn: from `ee91fe5` to `4a1079c` the type
checker printed two warnings on every run of `runtime_test.exs`, across six commits that
passed the old three lines, and `mix test --warnings-as-errors` exits 1 on them. If you changed what the language
accepts, or the golden record's generator, on purpose, regenerate the record in the same
commit and read its diff:

    mix run test/fixtures/generate_frontend_golden.exs && git diff test/fixtures/

Apart from the header line, which names the commit the tree was on top of, the diff is the
exact list of inputs whose meaning changed. If it lists anything you did not intend, the
change is wrong, not the record.

The fifth gate is OTP's own Dialyzer over the dev build, `scripts/dialyzer.sh`
("Scripts", below), which `scripts/gate.sh` runs once the suite is green and CI runs as
the step after its suite's, red on any warning its flags give:
the specs of the host contract, every public function of the modules decision 514 and
decision 523 name, read against the code and against the toolchain's applications
(decision 515 (c)). Dialyzer holds a spec only where it can type what the function gives:
it types nothing a call to a process gives back, the runner's, a simulated device's, a
manual clock's and a compile's own process's, nor a field of a struct, so it passes a
false spec of those (RV-24's review, F1). `test/logex/typespec_test.exs`, in the suite,
holds every spec of the contract to the values its function gives and the arguments it is
given, and each contract function with a spec must be reached there, or the file fails.
Until decision 549 the gate did not run Dialyzer, and a contributor who changed what a
function gives and forgot its spec learned of it from CI, minutes after the push; the
gate runs it now, after the suite, so the spec the code breaks is seen before the commit.
Its first run on a machine builds the PLT, about a minute, two and a half on a loaded
machine, and later runs check the one it
kept and take some 10 to 35 s, the analysis most of it, longer on a loaded machine. A
warning is fixed in the code, with a test that fails when the fix is reverted where
it is a defect, or, where it is not, the code made to say what it does and the reason
recorded in `PLAN.md` (decision 551); never silenced by a broader
spec, a `no_return()`, a `@dialyzer` attribute or a flag dropped without its reason. A
spec states the contract the code and its tests already hold, what a host hands in and gets
back, a host's mistake being its pinned `ArgumentError`, never a narrower or a wider one;
a public function added to the contract gets one, and a type it hands out a `@typedoc`, or
`runtime_test.exs` fails.

The gate does not build the site, and the Docs workflow is red on what the gate never
sees: a commit that changes a module's or a function's text, or a page, runs
`scripts/docs.sh` here too, to `DOCS-OK`. Two commits of RV-30 passed the gate and were
red by Docs, a function's text having named a module that has no page (`f4fa1af`,
`4024fe1`). And a commit's runs are read on that commit: a push runs the workflows on
the tip it brings, so of commits pushed together all but the last have no run. Push each
commit as it is made, or to a branch of its own where a later push would cover it; two
of RV-30's had no run until its review pushed each so (`e3a8c2f`, `f4fa1af`).

A mark that throws an answer away, `_ = ...`, is a line of
`test/logex/dropped_answers_test.exs` too, beside why the answer may be dropped there:
Dialyzer is red on a drop left unmarked and passes every marked one, a defect among
them, so the list is where a marked drop is read (decision 550; RV-30's review).

## Releasing

A release is a version, a changelog entry drawn from `docs/organisation.md` §7's decisions
and a tag, made before anything is published (decision 515 (b)). `CHANGELOG.md`'s head says
how an entry reads; `scripts/release.sh` checks a release and makes its tag; and
`test/logex/release_test.exs` holds both, as `scripts_test.exs` holds the gate: it runs
`scripts/changelog.exs` on the tree, and on changelogs of every shape it refuses, and
`scripts/release.sh` in a scratch repository of its own, with a gate that stands in for
the suite, a `gh` that stands in for GitHub's and an origin of its own, every check
passed and each taken back in turn.

- **Between releases.** A commit that records a decision in §7 names it in the newest
  entry, `## Unreleased`, opening one above the newest release where there is none: the
  entry's first line, `Decisions: 541–543.`, names every decision it carries, each once in
  the file. The suite is red until every decision §7 records is named (`release_test.exs`,
  decision 542). A change that alters what a running program writes to its outputs gets an
  item under "What changes a running program's outputs": the rule before and after, a
  plant that shows it, and how to find a program it reaches, as the changelog's head shows
  for decision 146; a word newly reserved or a form newly refused, one under "What no
  longer compiles, loads or starts".
- **To release**, from `main`, its CI run green, which the release step checks (waiting
  under decision 541, as the first number and the tag's push are: whether the step reads
  CI's runs itself is put to the maintainer when a release is planned, `PLAN.md`'s RV-22,
  question 5):
  1. The version is the maintainer's to give (the first's, and what a number says of the
     release after it, wait under decision 541, `PLAN.md`'s RV-22, question 1). In one
     commit, `mix.exs`'s `version:` is set to it and `## Unreleased` becomes `## X.Y.Z —
     YYYY-MM-DD`, the release's day; push it to `main` and read CI's run on it.
  2. `scripts/release.sh --dry-run` runs every check, tags nothing, pushes nothing, and
     says what it would tag. Read it.
  3. Either `scripts/release.sh`, which makes the annotated tag `vX.Y.Z` on the commit
     checked out and prints the command that pushes it, `git push origin
     refs/tags/vX.Y.Z`, run by hand; or `scripts/release.sh --push`, in place of the plain
     run, which makes the tag and pushes it (whether a tag is pushed is the maintainer's,
     waiting under decision 541, `PLAN.md`'s RV-22, question 2). Not one after the other:
     a run after a plain one is refused, the tag being here already. A push that fails
     leaves the tag here and prints the command. Each check refuses, a line `refused:
     ...`, and tags nothing: the tree not clean; the commit not on origin's `main`,
     fetched as it runs, so that a tag never names a commit only one checkout holds; CI
     not run on the commit, or a run of `.github/workflows/ci.yml` on it not concluded
     `success`, read through GitHub's CLI, `gh api`, signed in (`GH_REPO` names the
     repository where the checkout's remotes do not); the changelog's newest entry not
     that version, or a decision of §7 no entry names, each once (`elixir
     scripts/changelog.exs --release`); the tag here or on origin already; the gate red
     (`scripts/gate.sh`, its log `_build/release-gate.log`).
  4. A publish, to Hex or anywhere, comes only after the tag, a step of its own.

## Scripts

`scripts/` holds the checks this file asks for, each run from anywhere in the checkout,
each judging what it runs by its exit code, never by its output. Each `mix test` they run
starts by deleting ExUnit's failures manifest, so the tests they name are that run's.

- **`scripts/gate.sh [log] [mix test args]`** runs the five gates of "Before you commit"
  in order, the first that fails stopping the rest, writes what they print to the log
  (`_build/gate.log` unless given), prints its last lines and `GATE-OK` or `GATE-FAIL
  rc=<n>`, and exits with the gates' code. The fifth, `scripts/dialyzer.sh`, runs once the
  suite is green, whatever arguments the suite was given (decision 549): a red one is
  `GATE-FAIL` with the script's code, followed by a line that names the step and the log,
  which keeps everything the script printed, on either stream; 2 is a warning, `its
  warnings are in <log>`, and any other code a run that could not be made, `which could
  not run: what it printed is in <log>`. A red suite's code may be 2 too, so read the
  line after `GATE-FAIL`, which names the tests or the step. `scripts/release.sh`'s gate
  is this script, so a release is held to the five. The suite is judged by `elixir
  scripts/failed.exs --exit`, as CI's test step judges it ("Before you commit"): a failed
  suite is followed by the tests that failed, `file:line: Module: test name` a line, read
  from ExUnit's failures manifest, since `Result: 2406/2407 passed` names none, and a long
  log hides them, or by why none is named; and a suite that exits 0 with no manifest
  written, one a test halted with `System.halt(0)`, is `GATE-FAIL rc=1`, where `mix test`
  alone reports it green.
- **`elixir scripts/failed.exs`** prints the tests ExUnit's failures manifest holds. The
  manifest is ExUnit's own and kept across runs: a test's failure stays in it until a run
  passes that test, so after a failing run of one file and a passing run of another it
  still names the first; after the scripts here, which delete it first, it names that
  run's alone. A suite whose test files fail to compile or load runs no test, and ExUnit
  marks it failed whole: the script says so in one line beginning `suite:`
  (`test/logex/scripts_test.exs`). The manifest holds no line, so each test's is read from
  its file's syntax tree, the `test` or `doctest` call whose name, its `describe`'s before
  it, is the test's, a part the compile makes matching any text; it is the line ExUnit's
  own report gives, which `mix test file:line` runs again, the same for each of the
  suite's 3,013 tests when RV-22's review compared them. Where more than one call could
  name a test, the surest gives the line, a call in the test's own module before one in a
  module the compile names, and a name all literal before one the compile makes; where
  the surest are more than one, as a literal-named loop's `test name` and another loop's
  test both match, the file alone is given, never a line that may be another test's. A
  test no such call names, one a helper of a test file's own defines, is given its file
  alone. With `--exit N`, after a run made with the manifest deleted before it, `N` the
  run's exit code, it judges the run: a red one's tests under the heading `mix test exited
  N; the tests that failed:`, or why none is named, no manifest (the suite did not finish)
  or a manifest of no failure (a warning under `--warnings-as-errors`, for one), exiting
  `N`; and a run that exited 0, silent and 0 where the manifest is there and names no
  failure, red, 1, where there is none.
- **`scripts/dialyzer.sh`** runs OTP's own dialyzer over logex's dev build as the gate's
  fifth step and CI's step do ("Before you commit"), no dependency added: it compiles,
  reads the toolchain from
  the `elixir` on the path, builds the PLT of the applications logex calls, erts, kernel,
  stdlib and elixir, under `_build/dialyzer/`, named by the OTP and Elixir versions and
  the applications, or checks the one kept there and builds it again where the check
  cannot read the files it names, and analyses `_build/dev/lib/logex/ebin` with
  Dialyzer's default warnings and `-Wextra_return`, `-Wmissing_return`, `-Wunderspecs`,
  `-Woverlapping_contract`, `-Wopaque_union` and, since decision 550,
  `-Wunmatched_returns`, reading no Dialyzer configuration file;
  it prints what Dialyzer prints, then `DIALYZER-OK` or `DIALYZER-FAIL rc=<n>`, and exits
  with Dialyzer's code, 2 for a warning and 1 for a run that could not be made; with no
  `dialyzer` on the path it says so and exits 127, nothing built and a kept PLT left as
  it is. `test/logex/scripts_test.exs` runs it as CI's
  step writes it, over a stand-in `dialyzer`, and holds its flags and its PLT's name,
  check and build.
- **`scripts/mutate.sh [-t test_file]... [-N] patch... [-- mix test args]`** is a
  mutation table. Make each mutant as a patch, `git diff > m1.patch` from an edited tree,
  then restore the tree; the script applies each patch in turn (`git apply`), runs the
  named test files and then the full suite, restores the tree (`git apply -R`, on an
  interrupt too) and prints a Markdown row, `| patch | named files | full suite | failed
  tests |`, each suite's exit code and Result line, a mutant the full suite passes marked
  `SURVIVED`, and the files whose tests failed with their counts. Each run's log is kept
  beside its patch. `-N` skips the full suite, for a quick look; a mutant counts only by
  the full suite, and one red only on a real-clock test, or under load, is run again
  alone before it counts ("A fix needs a test that fails when the fix is reverted").
- **`scripts/load.sh [-n runs] [-l loops] [mix test args]`** runs `mix test` with the
  arguments `runs` times (10 unless given) while `loops` busy loops (one a core unless
  given) hold the machine, a line a run with its exit code, Result line and failed tests,
  and then how many failed, its logs in `_build/load/`. A new real-clock or runner test
  runs under it before it lands, `scripts/load.sh -n 50 test/logex/runner_test.exs`
  ("Wait for a process's `DOWN`…", above).
- **`scripts/release.sh [--dry-run] [--push]`** and **`elixir scripts/changelog.exs
  [--release]`** are the release step and its checks of the documents ("Releasing",
  above).
- **`scripts/docs.sh [log]`** builds the site ("Writing a page of the documentation",
  above): it fetches ExDoc for the `docs` environment, the one step here that needs Hex
  and the network, runs `mix docs`, and then `elixir scripts/site.exs check <log>`, which
  holds the build's warnings and every link of `doc/` to `docs/site-warnings.txt`; it
  prints the log's last lines and `DOCS-OK` or `DOCS-FAIL rc=<n>`. `mix docs` first runs
  `elixir scripts/site.exs stage`, which copies the site's pages to `_build/docs/pages/`,
  each under its name in the site, a page under `guides/` its file's name and any other
  its whole path, with each link to a page made that name, the anchor it names made
  the one ExDoc gives the heading, and each link to a file the site does not hold made a
  link to GitHub; it refuses a link to no file, an anchor no heading gives, a picture
  outside `guides/assets/`, and two pages with one name.
- **`elixir scripts/prose.exs [--review] [page...]`** checks pages against the writing
  rules, every page of `docs/pages.exs` that is not `:legacy` where none is named, a line
  a failure, `page:line: [rule] what it found. Write: what to write`, exiting 1 on any;
  `--review` lists what it only counts, a passive verb, a glossary term with no link, a
  block marked `unchecked` and a block the suite compares with nothing; `--kind <kind>
  <file>` checks a file `docs/pages.exs` does not list.
- **`mix run scripts/draw.exs [--check] [page...]`** draws each picture a page marks,
  `<!-- rung: file.ld -->` or `<!-- timing: file.timing.exs -->`, into the file the page
  shows; `--check` writes nothing and exits 1 where a picture is not what it would draw.
  `scripts/pictures.exs` is the drawing, which the suite reads too.
- **`scripts/page.exs`** has no command: it is the one reading of a page's Markdown the
  four above and the examples' test share, and the page's name in the site. The scripts
  written in Elixir hold a `case` where a value is told apart, function clauses for the
  rest, and no `cond`, `if` or `unless` (`test/logex/clauses_test.exs`).
