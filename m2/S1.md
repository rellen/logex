## 0. The answer in one page

- **Two public additions, both decided names.** `Logex.Configuration`, a struct and one
  function, `new!/1`. `Logex.Runtime` gains the `%Logex.Runtime{}` struct (opaque) and
  `start/1`, `cycle/3`, `next_due_in/1` and `get/2`, with the signatures org §4.6 gives
  (org:667-680). Nothing else becomes public. `call/4` and `instance/1` are unchanged, and
  the evaluator is untouched.
- **A configuration is data with every part M2-2 to M2-6 needs, from M2-1.** Tasks,
  globals (located input and output points among them), instances, connections, and the
  program types themselves. Each part is a map with a `line`, nil from Elixir, so M2-2's
  reader feeds the same constructor and its diagnostics cite the line.
- **One constructor runs every §4.4 check its data can express** (org:426-447), in one
  `ArgumentError`, a line each. Its checks return `{line, message}` pairs, so M2-2 turns
  them into located diagnostics without a second validator.
- **The scheduler is one fold.** Each cycle advances the clock, merges the inputs into the
  input image, works out the due periodic tasks once, runs them by priority, then the
  earlier due time, then declaration order, then every task-less instance; each scan is
  `call/4` with the instance's copy-in, followed by its copy-out. Outputs are every output
  point. A late task runs once, reports `{:overlap, task, missed}` and keeps its phase.
- **The Done-when passes as written** (`spike test/logex/end_to_end_test.exs`, describe
  "the scheduler, from Elixir data (M2-1)"), and so does the full gate: 484 tests
  (6 doctests), up from 430, exit 0 for each of the four commands.
- **51 mutants**, each one rule reverted alone, 50 red and 1 green, the green one
  showing a limit of growth tests counted in reductions (§9).
- **Not built**, each additive later at no cost: a configuration restart, a stored overlap
  count, a warnings field, reserved words in the data path, line references inside
  messages, a printer, an unchecked scan entry, a generation counter, event tasks (§7).
- **One departure needs the maintainer** (§12): no per-task overlap count is stored,
  because nothing reads it; the events carry each increment. Two smaller ones: M2-1's
  data carries the globals, connections and §4.4 checks org §6.2 gives M2-2 (the
  inventory's C7), and CLAUDE.md's rule for new instance state is extended to an opaque
  struct.

## 2. The API, every signature and return shape

```elixir
Logex.Configuration.new!(fields :: keyword) :: %Logex.Configuration{}   # raises ArgumentError

Logex.Runtime.start(%Logex.Configuration{}) :: %Logex.Runtime{}
Logex.Runtime.cycle(rt, elapsed_ms :: non_neg_integer, inputs :: %{String.t() => integer})
  :: {rt, outputs :: %{String.t() => integer}, [event]}
Logex.Runtime.next_due_in(rt) :: non_neg_integer | :infinity
Logex.Runtime.get(rt, path :: String.t()) :: integer

event :: {:ran, task :: String.t() | :none, instance :: String.t(), now :: non_neg_integer}
       | {:overlap, task :: String.t(), missed :: pos_integer}
```

**`new!/1`'s fields**, a keyword list (`spike lib/logex/configuration.ex:131`):

| Field | Shape | Left out |
|---|---|---|
| `name:` | a string shaped like a name | refused |
| `programs:` | `%{"motor" => %Logex.Program{name: "motor"}}`, each under its own name | `%{}` |
| `tasks:` | `[%{name:, interval:, priority:}]` | `[]` |
| `globals:` | `[%{name:, type:, initial:, at:}]`, `initial` and `at` optional | `[]` |
| `instances:` | `[%{name:, type:, task:}]`, `task` optional | `[]`, then refused |
| `connections:` | `[%{member: "m1.start", to: "pb_start" \| 0}]` | `[]` |

Each part says what one `.lcf` line of org §4.4 says (org:409-417): `task fast interval 10
priority 1`, `var_global k1 bool at panel.q.0`, `program m1 motor with fast`, `m1.start
pb_start`. Field names say what a field means (`task`, not the text's `with`).

**The stored shape.** The struct holds each part as a map with every field, a left-out
field at nil, and `line: nil` (`spike lib/logex/configuration.ex:250`). A host reads the
struct; it never builds one: one built or edited by hand is outside the contract, as a
hand-built `%Logex.Program{}` is (`lib/logex/runtime.ex:42-43`).

**`cycle/3`** returns the decided tuple, `{rt, outputs, events}` (org:540). Its order
differs from `call/4`'s `{outputs, state}` (inventory Q0.4, C16); I kept the decided
order, and §11 does not reopen it.

**`get/2`** reads an access path, the resource left out (org:678): a global by its name
(`"k1"`), an instance's tag of any section (`"m1.fault"`), or a member a program may name
of a function block instance, at any depth (`"m1.t1.acc"`, and from M2-5 `"m1.s2.run"`).
It returns an integer, never a map.

## 3. The data

### 3.1 `%Logex.Configuration{}`

```elixir
%Logex.Configuration{
  name: "plant",
  programs: %{"motor" => %Logex.Program{}},
  tasks: [%{name: "fast", interval: 10, priority: 1, line: nil}],
  globals: [%{name: "k1", type: :bool, initial: nil, at: "panel.q.0", line: nil}],
  instances: [%{name: "m1", type: "motor", task: "fast", line: nil}],
  connections: [%{member: "m1.motor", to: "k1", line: nil}]
}
```

- **Lists keep declaration order**, which is execution order within a task and the last
  tie-break between tasks (org:570-577; D7.2's "execution order is a list in the
  configuration"). Names are unique (rule C2), so each list is also keyed by name.
- **`programs` is embedded.** `start/1` takes the configuration alone (org:675), so the
  types must be in it (inventory Q1.2). It is the decided shape of
  `Configuration.compile(name, source, %{"motor" => program})` (org:470), so both front
  ends hold the same map.
- **Plain data.** No funs, pids or refs (D7.1).

### 3.2 `%Logex.Runtime{}`, opaque

| Field | Value | State or derived |
|---|---|---|
| `config` | the `%Configuration{}` it runs | the configuration |
| `now` | ms since `start/1`, the time of the last cycle | state |
| `globals` | `%{name => integer}`, one value per global; the input points among them are the input image | state |
| `instances` | `%{name => %Logex.Instance{}}`, flat, keyed by name | state |
| `tasks` | `%{name => next_due}` for each periodic task | state |
| `plan` | worked out from `config` by `start/1`: each task's priority, interval, place and instances; the task-less instances; each instance's type, copy-in and copy-out lists; the input points with their types; the output points | derived; not state |

Source: `spike lib/logex/runtime.ex:79-95` (struct) and `:276-324` (`plan/1` and the point's direction). The input
image is not a separate map: an input point is a global, so its value has one copy
(D7.7). The output image is not stored: each cycle reads the output points' globals.

## 7. How the later items, and OE-2, extend it

### 7.1 M2-2 · the configuration file

- `Logex.Configuration.compile(name, source, programs)` reads `.lcf` lines with
  `Logex.Lexer` and `Logex.Parser` (readiness §6: every line shape lexes and parses as a
  rung of names and integers, so the golden record does not change) into the same part
  maps, with `line` set, and calls the same private checks. Each `{line, message}` becomes
  a `%Logex.Diagnostic{line: line, file: path, message: message}`; the stage is a question
  for M2-2 (inventory Q0.1). No message changes.
- Cross-references gain the other part's line where it has one, through one helper:
  `` `k` is already driven by `m1.run_lamp` (line 13) `` (the spike's receipt form,
  org:457). From Elixir every line is nil, so the Elixir messages pinned now stay.
- M2-2 reserves `program var_global at bool dint` (org:1378) in a word table in
  `Logex.Configuration`; the name check (C5) then refuses those names from Elixir too,
  with the message the text gets. No host built a configuration between the two commits,
  so the tightening breaks nothing that shipped.
- No part shape changes. Text words map to the data's values: `bool` to `:bool`, the
  third word of `program` to `type`, `with` to `task`.

### 7.2 M2-3 · tasks in text

`task <n> interval <ms> priority <p>` and `with` fill the task maps and the instance's
`task` field, which exist from M2-1. M2-3 reserves `task interval priority with`. No
runtime change. Its acceptance (`m1` 100 times, `m2` 20 times in one simulated second)
runs on the scheduler as built: the M2-1 Done-when test already counts 100 and 34 for 10
and 30 ms over cycles at 0, 10, …, 990.

### 7.3 M2-4 · `var_external`

- The check gains: each program's externals match a global by name and type (Ed 2
  §2.4.3), and a program that writes an external bound to an input point is refused.
  Both cite a `.ld` line, so they need fix F15's answer (inventory Q0.2).
- The scan needs the globals during the scan, one copy (D7.7). The scheduler's private
  step, `run_instance/3` (`spike lib/logex/runtime.ex:348-359`), is the one place to change:
  pass the externals' values into a private scan entry beside `call/4` (which refuses any
  key but a var_input, `lib/logex/runtime.ex:303-308`) and write them back after, so the
  instance's env never keeps a copy between scans. `call/4`'s contract does not change.
- `get(rt, "m1.estop")` returns the global's value: one copy.

### 7.4 M2-5 · function blocks

`get/2` already walks members through `FbType.member/2` at any depth (`spike
lib/logex/runtime.ex:480-507`), so a user block instance, an `%FbType{}` tag, reads as
`"m1.s2.run"` with no change, and a `:local` member stays hidden by `FbType.public/1`
(`lib/logex/fb_type.ex:96-97`). A connection cannot reach into a block (C18), which M2-5
keeps. If M2-1 lands first, M2-5's acceptance can read `m1.s2.run` through `get/2` as
written (inventory C1). M2-5 owes `get/2`'s growth test in depth, which M1-6's
three-part paths cannot exercise.

### 7.5 M2-6 · event tasks

A task map gains `single:` (a bool global's name), and `interval` becomes optional where
`single` is given. The runtime keeps each event task's last trigger value (the listed
exception, D7.3), samples it after the input merge and before any scan, and marks the
task due on a rise, or in the first cycle if the trigger is already 1 (org:559-569). That
changes the private value in `rt.tasks`, which is free while the struct is opaque.
`next_due_in/1` ignores a pure event task.

### 7.6 OE-2

The candidate is a whole configuration, from `new!/1` or `compile/3`. OE-2 compares the two
by name, part by part: a task's interval and priority may change, its addition or removal
is refused; an instance's type change goes through its type's plan, and a change of task
is refused; a located global's addition, removal or change of `at` is refused, an
unlocated global may come and go; connections are free (org:858-871). The switch rebuilds
`plan` from the candidate between two cycles. A generation counter (`lib/logex/edit.ex:178-182`)
is one more field of an opaque struct.

### 7.7 What M2-1 does not build, and why that costs nothing later

| Not built | Why it costs nothing |
|---|---|
| a restart of the resource | `start/1` again is a cold restart. A `restart/2` later is a new function; §6 gives its rules now |
| a stored overlap count | each `{:overlap, task, missed}` carries the increment, so a host sums them; a counter and its reader can be added to an opaque struct later (§12) |
| a `warnings:` field | no M2-1 check is a warning; a defaulted field is additive (inventory Q0.3) |
| reserved words in the data path | there is no text yet to disagree with; each text item adds its words to both front ends (§7.1) |
| line references inside messages | M2-2 adds one clause to one helper; the Elixir messages stay |
| a `.lcf` printer | M2-2's question (inventory Q0.5) |
| a public check (`check/1`) | M2-2's reader lives in the same module and calls the private one |
| an unchecked scan entry | `call/4` re-checks each scan, about 12% of a scan (readiness §1.6); a private entry can come later without a surface change |
| precomputed var_output lists on `%Program{}` (readiness item 2) | independent of M2-1; a scan's cost is `call/4`'s either way |
| a generation counter | OE-2's, in an opaque struct |
| a host write to unlocated globals | deferred (org:1251); refused today with a pinned message, which a later rule can relax |
| a helper building the one-instance configuration of a program | sugar; the Done-when test builds it in ten lines |
| a check that `start/1` re-runs | a hand-built configuration is outside the contract, as a hand-built program is; §11 Q-L |

**The walk's oracles.** Three do not restate the scheduler's bookkeeping:
1. *When a task runs* comes from a closed form: with its phase at 0, a task of interval
   `i` runs in a cycle at `now` after one at `prev` (-1 before the first) when
   `floor(now / i) > floor(prev / i)`, and misses `floor(now / i) - floor(prev / i) - 1`.
   The code keeps a `next_due` per task instead.
2. *What a scan does* is replayed through `call/4` alone, from the configuration's own
   connections, and every global and every instance value is compared through `get/2`.
3. *Every accepted call is made twice* and must give the same result.

The order of due tasks is restated (priority, due time, place), so a misreading of that
rule shared by the walk and the code would pass; the worked tests in `runtime_test.exs`
and the Done-when's chain catch it (CONTRIBUTING.md:183-205).

**Reach under other seeds.** I ran the walk under 25 seeds besides the committed one
(`{n, 7, 3}`, n = 1..25): every refusal kind, mistake and behaviour was reached and every
oracle held, 25 of 25 green.

## 11. Open questions for the maintainer

Each has options with their consequences and a recommendation. The spike built the
recommendation.

**Q-A · The first cycle's time** (inventory Q1.16, C14). Decide before commit 1.
- *A1, built:* the decided rule as written: the clock and every phase start at
  `start/1`, every task is due at 0, and a first cycle's `elapsed_ms` counts from the
  start. A host takes its first cycle at elapsed 0; one that first cycles at 10 ms has
  missed the 10 ms task's run at 0, and is told so (`{:overlap, "fast", 1}`). Consequence:
  no special case; a runner's first call is `cycle(rt, 0, inputs)`.
- *A2:* anchor each phase at the first cycle. Consequence: no overlap in cycle 1 whatever
  its elapsed time, but the phase then depends on the first call, and the first cycle is
  a special case in the code and in OE-2's re-anchoring.
- *A3:* `start/2` with a start time. Consequence: a second clock origin to explain.
- *Recommend A1.* The inventory calls cycle 1's overlap spurious; it is a real missed run
  relative to the start, and the decided wording says so.

**Q-B · The overlap count** (org:596). Decide before commit 1. This is the one departure
(§12).
- *B1, built:* store no count; each `{:overlap, task, missed}` carries the increment.
  Consequence: nothing to read until something needs it; a host that wants the total sums
  the events.
- *B2:* store a count per task and expose it, for example `Runtime.overlaps(rt) ::
  %{task => count}`. Consequence: one more public function and one more piece of state
  with its edit rules.
- *B3:* store it unread. Consequence: state no test can observe, so no test can fail when
  it is reverted, against CLAUDE.md's rule for a fix.
- *Recommend B1*, and B2 when a runner or a logic-readable task state needs it.

**Q-C · `next_due_in/1` and task-less instances** (inventory Q1.18, C13). Decide before
commit 3.
- *C1, built:* only periodic tasks count; `:infinity` when there is none. A runner with
  task-less instances paces those cycles itself, as org:661 says.
- *C2:* 0 whenever a task-less instance exists. Consequence: a runner sleeping on it
  busy-loops.
- *Recommend C1.*

**Q-D · One set of names** (inventory Q1.5, Q2.11). Decide before M2-2.
- *D1, built:* tasks, globals and instances share one set of names, case-folded as tags
  are; program type names are apart (a type is named only in a type position).
  Consequence: `get(rt, "m1")` and a connection's other end are never ambiguous; a plant
  cannot name a global like an instance.
- *D2:* a set per kind. Consequence: a reader of `m2.reset m1` could not tell a global
  `m1` from the instance `m1` without looking both up, and every message naming a
  name would have to say which kind it means.
- *Recommend D1.* Relaxing it later breaks nothing; tightening later breaks plants.

**Q-E · The limits of a task's numbers before the text exists** (inventory Q1.9, Q3.1,
Q3.2). Decide before commit 2.
- *E1, built:* interval 1 to 2147483647 ms and priority 0 to 2147483647, the dint range a
  preset has (`Declarations.preset?/1`).
- *E2:* priority 0 to 31 as CODESYS (research CDS-1) or 0 to 15. Consequence: tighter, and
  relaxable later.
- *Recommend E1*, every number in logex being a dint. By decision 7's reasoning E2 is the
  safer start, since relaxing breaks nothing; E1 is recommended because no source bounds
  IEC's PRIORITY (inventory U24) and logex has no other small-range number. The `priority`
  stanza must say that Siemens numbers the other way (research SIE-1).

**Q-F · The location's grammar now** (inventory Q2.9, Q2.8). Decide before commit 2.
- *F1, built:* one device name, lowercase `i` or `q`, one or more numbers without a
  leading zero, so that one address has one spelling and "two globals at one location"
  is a string comparison.
- *F2:* a dotted device (`rack1.slot2.i.0`), or `I`/`Q` in any case. Consequence: the
  runtime reads a point's direction from the second field (`spike
  lib/logex/runtime.ex:318-323`), which a dotted device would change, and the one-address
  check would need normalising.
- *Recommend F1*, relaxable later.

**Q-G · An output point's initial value** (inventory Q2.10). Decide before commit 2.
- *G1, built:* refused, as for an input point; the line shape has no initial value for a
  located global (org:414).
- *G2:* allowed. Consequence: an output point's value before its first driver would be
  that value; its place on the line, before or after `at`, must be decided for M2-2.
- *Recommend G1.*

**Q-H · A configuration of no instance** (research IEC-5). Decide before commit 2.
- *H1, built:* refused, as IEC requires a program in a configuration (Ed 2 B.1.7, Ed 3
  Annex A).
- *H2:* allowed. Consequence: an empty resource that cycles and reports nothing.
- *Recommend H1.* An OE-2 edit that removes the last instance is then refused, which is
  sound: such a controller drives nothing.

**Q-I · A restart of the resource, and a changed interval** (inventory Q1.21, Q3.8).
Decide before OE-2's design.
- *I1, built:* none in M2-1; `start/1` again is a cold restart, and §6 states what a
  restart must do to each piece.
- *I2:* `Runtime.restart(rt, :cold | :warm)` now, by §6's column.
- *Recommend I1.* For OE-2's changed interval, recommend keeping the next due time already
  set and stepping by the new interval from it, so no run is lost or doubled at the switch.

**Q-J · What `get/2` reads** (inventory Q1.19; readiness §9 item 11). Decide before
commit 3.
- *J1, built:* any declared tag of an instance, `var` included, and any member a program
  may name, at any depth; globals by name; never an internal member, a whole instance, or
  a member of a bool or dint.
- *J2:* var_inputs, var_outputs and public members only. Consequence: `m1.fault`, which
  org §4.6's receipt reads (org:699-704), and the README's `state.env["fault"]`, could not
  be read through a configuration.
- *Recommend J1.* VAR_ACCESS stays deferred (org:1251); `get/2` is a read for tests and
  hosts.

**Q-K · The programs inside the configuration** (inventory Q1.2). Decide before commit 2.
- *K1, built:* `programs: %{"motor" => program}`, the decided shape of `compile/3`
  (org:470), checked key by key.
- *K2:* a list, keyed by each program's name. Consequence: no key/name mismatch to check,
  and `compile/3` would differ from the decided shape.
- *Recommend K1.*

**Q-L · Whether `start/1` checks the configuration again.** Decide before commit 3.
- *L1, built:* no. `start/1` takes a `%Configuration{}` from `new!/1`; one built or edited
  by hand is outside the contract, as a hand-built program is for `call/4`.
- *L2:* yes, one linear pass, so any `%Configuration{}` entering the runtime is checked.
  Consequence: OE-2's candidate path gets it for free, at the cost of every start.
- *Recommend L1 now*, and L2 if OE-2's design wants a struct-level entry.

**Q-M · `new!/1`'s input form, and its error mode** (inventory Q1.6, Q1.7). Decide before
commit 2.
- *M1, built:* a keyword list of lists of maps, each map a line's data; every problem in
  one raise.
- *M2:* tuples mirroring the lines (`{"fast", interval: 10, priority: 1}`), or builder
  functions per part. Consequence: more surface, or two representations.
- *M3:* raise on the first problem, as `Tag.new!/4` does. Consequence: a host fixes one
  mistake per run, while M2-2's reader needs every one anyway.
- *Recommend M1.*

**Q-N · Reserved words in the data path before the text.** Decide before commit 2.
- *N1, built:* none in M2-1; each text item reserves its words in both front ends.
- *N2:* reserve all of org §4.8's `.lcf` words now. Consequence: words reserved before
  their `docs/naming.md` stanzas exist, which CLAUDE.md's naming rule forbids.
- *Recommend N1.*

## 12. Departures from decided rules

1. **No per-task overlap count is kept** (org:596, "adds `missed` … to its overlap count";
   `PLAN` M2's "missed periods coalesced, counted and reported", PLAN:1360-1361). Argued in
   §11 Q-B: nothing reads it, so it would be state no test can see; the events carry each
   count. Needs the maintainer's yes.
2. **M2-1 carries globals, located points, connections and every §4.4 check that its
   data can express**, where org §4.1 assigns VAR_GLOBAL and connections to M2-2
   (org:203-204) and §6.2 lists "the §4.4 checks" under M2-2 (org:1377). Argued by the
   decided M2-1 itself: "copy-in/copy-out" and "a pure, checked constructor" (org:1365-1367),
   and "a constructor built from Elixir data runs the same checks" (org:474-475); without
   them, a configuration M2-1 accepts could become one M2-2 refuses, a tightening that
   breaks plants (decision 7's reasoning). M2-2 keeps the text, the loader, the reserved
   words and the file's diagnostics. This is the inventory's C7.
3. **CLAUDE.md's rule for new instance state is extended, not followed literally, for
   `%Logex.Runtime{}`** (CLAUDE.md:166-173 asks a field of `%Logex.Instance{}` for a
   check with a pinned message). An opaque struct only `start/1` and `cycle/3` make gets
   no check; it gets a value at start and a rule for a cycle, a restart and a switch (§6).
   The spike's CLAUDE.md says so (inventory C25).

Not departures, but readings the maintainer should see: the first cycle (Q-A), task-less
instances and `next_due_in/1` (Q-C), and "one simulated second" as cycles at 0, 10, …,
990 ms (inventory Q1.17), which matches M2-3's counts.

## 13. Risks

- **Messages pinned before their text exists.** M2-2 may want the spike's wording with
  lines (org:452-460, "declare it first, as `task medium …`"); every message in §5.1 would
  then change with its pins in one commit. The forms here were chosen to read the same
  from Elixir and from text.
- **A reductions growth test misses a quadratic made of BIFs.** `name in Map.keys(map)`
  per instance is quadratic in time and stays inside the bound (mutant G-build, §9),
  because `Map.keys/1` and list membership are charged few reductions, as CONTRIBUTING.md
  says of `++`. The test catches the quadratic the spike actually had (G-build2).
- **`call/4` re-checks every scan** (readiness §1.6, about 12% of a scan). Accepted for
  M2-1; measured there, not here (unverified on the spike).
- **No running configuration can be edited until OE-2** (inventory Q7.6): the resource is
  opaque, so a host cannot take an instance out to run `Logex.Edit` on it. Documented in
  the spike's `Logex.Runtime` moduledoc.
- **The direction of a point is read in two places**: the location regex in
  `Logex.Configuration` and a split in `Logex.Runtime` (§11 Q-F). Both change together if
  a device may be dotted; a comment at each says so.
- **The walk restates the order of due tasks.** Its independent oracles are the
  closed-form due test, the replay through `call/4`, and determinism; the order itself is
  pinned by worked tests.
- **Map order beyond 32 keys.** Events and outputs come from lists, and every list of input problems is sorted; the growth test runs 800 instances, but asserts only a ratio, so order
  at that size is pinned by reasoning, not by a test (unverified by test).
