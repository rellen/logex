## 0. The answer in one page

- **The words.** `function_block` (IEC's FUNCTION_BLOCK keyword, rule 1) heads a block's
  `.ld` file; `cal` (IEC's IL operator CAL, rule 1, its basis Ed 2 and Ed 3 IL) runs an
  instance. Both stanzas are appended to `docs/naming.md` in the spike, and the `cal`
  stanza supersedes the Program control table's `cal <routine>` row, which stays. The survey
  found two things the documents did not have: IL's conditional call says *"All assignments
  in an argument list of a conditional function block invocation shall only be performed
  together with the invocation, if the condition is true"* (Ed 2 §3.2.3 p.126; Ed 3
  §7.2.4.3 p.198), which is decision 12 in IEC's own IL; and Ed 2's text on p.126 calls
  Table 53's feature 1a "formal" and 1b "non-formal", the reverse of its own table on p.127
  (org §4.3 cites the table, rightly; Ed 3 Table 69 agrees with the table).
- **A block compiles to its type.** `Logex.compile(source, name: "seal")` on a file headed
  `function_block seal` returns `{:ok, %Logex.FbType{name: "seal", members: […], body:
  %Logex.Program{}}}`. The members are its declarations in text order: `var_input` an
  `:input`, `var_output` an `:output`, `var` a `:local` (a new role), each `write: false`.
  `body` is the compiled program (rungs, tags, warnings, source); it is nil for the
  built-in `ton`. No new struct, and `Logex.Program` gains no field.
- **The library is a `types:` option.** `Logex.compile(source, name: "motor", types:
  [seal])` and `Logex.compile_file(path, types: [seal])`: a list of the `%FbType{}`s that
  `compile/2` returned, checked as host data. No loader in M2-5 (F1-Q6): M2-2's loader,
  which must find program files beside the `.lcf`, finds block files the same way.
- **`cal s1 a b q`.** Positional, the inputs then the outputs (org §4.3). Rung power is
  EN; ENO is EN, so `cal` passes on the power it receives and anything may follow it. True:
  copy the inputs in, run the body over the instance's nested map, copy the outputs out.
  False: nothing (decision 12): the instance and its output tags are frozen, and a timer
  inside keeps `.en` and `last` and catches up (decision 8). One `cal` per instance.
- **Members from outside.** Inputs and outputs are read anywhere (org §4.3, decision 9);
  a block's own `var`s, instances included, are named only inside it, so from outside no
  path is deeper than `s1.run`; nothing outside writes a user block's member.
- **The evaluator re-enters a body privately** (B5): the `cal` clause of
  `Logex.Runtime.evaluate/3` runs the body's rungs with `rung/3`. It finds the body through
  a new runtime-filled `%Logex.Scan{}` field, `tags`, the tag table of the program or block
  whose rungs run, which the clause narrows to the block's for its body, along with the
  instance's subtree of blocked one-shots. That narrowing departs from CLAUDE.md's "the
  scan is the same for every instruction of one call" (F1-Q12).
- **Recursion** is refused by name, at the `var` line that holds it, at any depth.
- **Online edit.** An instance of a user block is ordinary state: started by
  `initial_env/1`, kept and pruned by name, its one-shots blocked by dotted path (`s1.edge`)
  where its `cal`'s rung is added or changed. Any change to a block type, members or body,
  is refused at accept as a type change, its line numbers aside (F1-Q2): broader than §4.9's
  "Allowed while running: rungs", so that is an explicit question. The nested migration
  stays OE-2's (F1-Q3).
- **The Done-when** runs as written except `m1.s2.run`, which before M2-1 is read from the
  instance named `m1` in the test, by a rung (`xic s2.run`) and by that path in its state
  (F1-Q1).
- **Receipts.** The gate passes: format 0, compile 0, test compile 0, `mix test` 0, 478
  tests (6 doctests), up from 430. 41 rules were reverted one at a time; every one turned the
  suite red (§9).

## 1. The words: survey and reservation

Both stanzas are in the spike's `docs/naming.md`, appended under `## Stanzas` (the file is
append-only), each with the template's six rows, `Chosen`, `Why` and `Checked`.

### 1.1 `function_block`

- **Rule 1.** IEC names the thing: FUNCTION_BLOCK … END_FUNCTION_BLOCK (Ed 2 §2.5.2.2 rule
  1, p.69, Table 33 p.71; Ed 3 §6.6.3.2 rule 1, p.99, Table 40 feature 1, p.100), a keyword
  in Ed 2 Table C.2. Lowercased, as `var_input` takes VAR_INPUT. `end_function_block` is
  dropped as `end_var` was: one file is one block.
- **What IEC allows and logex keeps from M1-3 and M1-6.** Ed 3 rule 8 lets inputs be
  initialised; logex refuses an initial value on a `var_input` (M1-3), so in a block too.
  Ed 3 rule 17 declares instances in every section but VAR_TEMP; logex declares an instance
  only with `var` (M1-6). Ed 3 rule 11 makes a VAR PRIVATE unless PUBLIC; logex has no
  PUBLIC, so a block's `var` is private: from outside, only inputs and outputs are named.
- **Read in the sources:** Ed 2 and Ed 3 directly, from the research pass's copies
  (`m2/inv-sources-src/ed2.txt`, `ed3.txt`). The conventional family's rows are from its
  add-on-instructions manual (Sept 2025) pp.21 and 23 and design-considerations reference
  p.65, as `research.md` CNV-15 to CNV-17 quote them. Siemens, CODESYS and Mitsubishi rows
  are marked `unverified` in the stanza: no page on their block declaration was read.

### 1.2 `cal`

- **Rule 1, with its basis stated** (org §4.3): CAL is IL's operator, Ed 2 Table 52
  feature 19 (pp.125-126) and Table 53 feature 1a (p.127); Ed 3 Table 68 feature 21 (p.197)
  and Table 69 feature 1a (p.199). Ed 3 §7.2.1 (p.195) deprecates IL and Ed 4 removed it.
- **Two facts the survey added** (read directly):
  1. IL's conditional call, CALC, performs its assignments only with the call: Ed 2 §3.2.3,
     p.126, *"All assignments in an argument list of a conditional function block
     invocation shall only be performed together with the invocation, if the condition is
     true"*; Ed 3 §7.2.4.3, p.198, the same with "parameter assignments". A `cal` on a rung
     is IL's `CALC` with the rung's result, so decision 12 is IEC's own rule for it, not
     only Ed 3's "external implementation" (EXAMPLES 2 and 4, §6.6.1.5 p.64).
  2. Ed 2's §3.2.3 text (p.126) calls feature 1a the formal list and 1b the non-formal;
     its Table 53 (p.127) has them the other way, as does Ed 3 Table 69. The stanza says so.
- **The false EN, stated as Ed 3 §6.6.1.5 rule 1 requires.** Nothing copied in, nothing
  out. MatIEC takes the other conformant choice: the callee returns at once on a false EN
  (`generate_c.cc`, "// Control execution"), but the caller assigns every input before
  and every output after the call, unconditionally (`generate_c_st.cc`,
  `visit(fb_invocation_c *)`), read at `3a41303` for this pass. The conventional family
  passes inputs in (`research.md` CNV-13). CODESYS's choice is `unverified`.
- **Reserved.** `cal` is a key of `@instructions` (spike `lib/logex/compiler.ex`), so it
  is a mnemonic, reserved in any case in every `.ld`, and `naming_test.exs` requires its
  stanza. No test, `lib/` file or golden-record source uses `cal`, as a tag or at all
  (`grep -w -i` at `47319f7`; `inventory.md` §10). The commit that lands it must still say
  it breaks any program with a tag `cal`, in any case.
- **`function_block`** is not a mnemonic and not a section or type word, so
  `Declarations.reserved/1` does not return it: it is reserved by file kind (org §4.8). The
  spike adds `Logex.Declarations.header_word/0` and a `naming_test.exs` test that it has a
  stanza (inventory Q0.6).

## 2. The API, every signature and return shape

Public functions added or changed, all in the spike; everything else is unchanged.

```elixir
# lib/logex.ex
Logex.compile(source, name: name)                 :: {:ok, %Logex.Program{}} | {:ok, %Logex.FbType{}} | {:error, [%Logex.Diagnostic{}]}
Logex.compile(source, name: name, types: types)   # either keyword order; types :: [%Logex.FbType{}]
Logex.compile_file(path)                          :: same as compile/2
Logex.compile_file(path, types: types)            # new arity; `[]` also accepted

# lib/logex/compiler.ex
Logex.Compiler.instructionize(routine)                    # unchanged
Logex.Compiler.instructionize(routine, declared)          # unchanged
Logex.Compiler.instructionize(routine, declared, types)   :: {:ok, %Logex.Program{}} | {:ok, %Logex.FbType{}} | {:error, diagnostics}
Logex.Compiler.instructions()                             # gains "cal" => {:cal, [{:instance, :block}]}

# lib/logex/fb_type.ex
%Logex.FbType{name: String.t(), members: [Member.t()], body: nil | %Logex.Program{}}
%Logex.FbType.Member{role: :input | :output | :local | :internal, …}   # :local is new
Logex.FbType.formals(type)    :: [Member.t()]             # the inputs, then the outputs, each in declaration order
Logex.FbType.signature(type)  :: [{:instance, name} | {:value, type} | {:write, type}]

# lib/logex/scan.ex
%Logex.Scan{now:, first:, ons_blocked: [], tags: nil}     # tags is new, the runtime's

# lib/logex/declarations.ex (not in the pinned surface)
Logex.Declarations.header_word() :: "function_block"
Logex.Declarations.header(rungs) :: {line, operands} | nil
Logex.Declarations.split(rungs, declared \\ [], library \\ %{})   # library: name => %FbType{}

# lib/logex/tag.ex, lib/logex/runtime.ex, lib/logex/edit.ex: no new function.
Logex.Tag.new!("s1", seal)   # now accepts a user block type that Logex.compile/2 returned
```

`runtime_test.exs`'s surface test changes to match: `Logex` gains `compile_file: 2`,
`Logex.Compiler` gains `instructionize: 3`, `Logex.FbType` gains `formals: 1` and
`signature: 1`, and `%Logex.Scan{}` gains `:tags`.

**Why the block's type is the compile's result** (inventory Q5.3). IEC makes a
FUNCTION_BLOCK a POU type as a PROGRAM is, and the schema logex needs to declare an
instance, `%FbType{}`, already exists (M1-6, decision 9). Returning the schema with its body
means a program's tag already carries everything a `cal` needs, a `Tag.new!/4` from Elixir
can take the type it was given, and `Runtime.instance(seal)` is refused by its struct, not
by a flag. The alternatives were a `kind` field on `%Program{}` (a block could then be run
as a program by mistake, and every program function would check the kind) and a new
struct (a third POU struct for one field).

**Why `types:` is a list.** The names are in the types; a map by name would add a second
copy of each name and a host mistake when they disagree. Org §4.4's
`Configuration.compile(name, source, %{"motor" => program})` takes a map for programs; M2-2
can take either, and F1-Q6 asks.

## 3. The data shapes

```elixir
# seal.ld compiled
%Logex.FbType{
  name: "seal",
  members: [
    %Member{name: "start", type: :bool, role: :input,  write: false, initial: 0},
    %Member{name: "stop",  type: :bool, role: :input,  write: false, initial: 0},
    %Member{name: "run",   type: :bool, role: :output, write: false, initial: 0}
  ],
  body: %Logex.Program{name: "seal", source: "function_block seal\n…", rungs: […], tags: %{…}, warnings: []}
}

# a member that holds an instance: its initial is the overrides map FbType.initial/2 reads
%Member{name: "t1", type: Logex.FbType.ton(), role: :local, initial: %{"pre" => 250}}
%Member{name: "x",  type: seal,               role: :local, initial: %{}}

# an instance's state, nested by name, one map per instance at any depth
env["s1"]            == %{"start" => 0, "stop" => 0, "run" => 1}
env["p1"]["x"]["run"] == 1                                   # a block holding a block
env["d"]["t1"]       == %{"pre" => 100, "acc" => 40, "dn" => 0, "tt" => 1, "en" => 1, "last" => 60}

# IR: the instance, then one lowered operand per formal
{:cal, 7, [{:name, 7, "s1"}, {:name, 7, "start"}, {:member, 7, ["t1", "dn"]}, {:name, 7, "motor"}]}

# the instance's block list: a top-level bit by its name, a bit inside an instance by its path
%Logex.Instance{ons_blocked: ["edge", "p.edge", "p1.x.edge"]}

# what the evaluator is handed (built by call/4 once a scan; never by the host)
%Logex.Scan{now: 60, first: false, tags: program.tags,
            ons_blocked: %{"edge" => true, "p" => %{"edge" => true}, "p1" => %{"x" => %{"edge" => true}}}}
# and what a cal hands its body
%Logex.Scan{now: 60, first: false, tags: seal.body.tags, ons_blocked: %{"edge" => true}}
```

The member order is the text's (declared-from-Elixir tags first, in the list's order), so
the positional operands follow what the file says. `Program.initial_env/1` is unchanged:
it already calls `FbType.initial/2` for any `%FbType{}` tag (`lib/logex/program.ex:47-52`),
which already recursed into a member whose type is a type (`lib/logex/fb_type.ex:75-84`).

## 4. The rules

Each rule states where it lives in the spike, and the mutant that reverts it (§9). "Decided"
cites the source that settled it; "open" means this design chose, and a question in §11 asks.

### A function block's file

- **FB-1 Header.** A source whose first rung starts with `function_block`, in any case, is
  a function block's; the rung must be exactly `function_block <name>`. It is taken off
  before the declarations are read, so it is neither a declaration nor logic (spike
  `Compiler.kind/2`, `Declarations.header/1`). *Decided:* org §4.3, decision 4.
- **FB-2 Header shape.** No name, a literal, a second word or a branch group is a
  diagnostic at the header's line, and the body is still compiled for its own mistakes,
  as a program after a refused file name is (`Compiler.header/1`). Open.
- **FB-3 Block name.** It is shaped like a name (no `.`) and is no reserved word in any
  case: no mnemonic, section or type word, and not `function_block`, because a block's
  name is spelled as a type word in the files that hold it (`Compiler.block_name/2`). Open
  (inventory C18). Mutant M4.
- **FB-4 Header placement.** `function_block` as the first word of any other rung, in a
  block or a program, is a diagnostic naming it, not "unknown instruction"
  (`Compiler.unknown/2`). Mutant M2.
- **FB-5 Name agreement.** The header's name must equal the name it is compiled as:
  `compile/2`'s `name:`, which `compile_file/1` takes from the file. Exactly, case
  included. A mismatch is a `:validate` diagnostic at the header line, merged in line
  order with the compiler's (`Logex.headed/2`). *Decided:* decision 4 ("matches the file
  name"). Mutant M1.
- **FB-6 Reserved in a block.** In a block's file no tag may be named `function_block`, in
  any case: a diagnostic at its line, or `ArgumentError` for a tag from Elixir. A program
  may still have such a tag (`Compiler.reserved_in/2`). *Decided:* org §4.8. Mutant M3.
- **FB-7 Result.** A block compiles to `{:ok, %FbType{}}`, its `body` the compiled
  `%Program{}` named and with its source, its warnings carrying the file under
  `compile_file/1` (`Compiler.as_type/3`, `Logex.lowered/4`, `Logex.in_file/2`).
- **FB-8 Members.** One per declaration, in text order (tags from Elixir first, in the
  list's order): `var_input` `:input`, `var_output` `:output`, `var` `:local`, each
  `write: false`, `initial` the tag's starting value (an instance's overrides map, `%{}`
  if none, a timer's `%{"pre" => preset}`). Mutant M35.
- **FB-9 Formals.** `FbType.formals/1`: the inputs, then the outputs, each in declaration
  order. *Decided:* org §4.3 ("the var_inputs, then the var_outputs, in declaration
  order"). Mutant M36.

### The library and declarations

- **FB-10 `types:`.** A list of user block types, each a `%FbType{}` whose `body` is a
  `%Program{}`, whose name is shaped and not reserved, no two named alike in any case.
  Anything else is `ArgumentError` (`Compiler.library!/1`). Mutants M5, M38.
- **FB-11 Type words.** A declaration's type word is `bool`, `dint` or `ton` in any case,
  then a block given in `types:` by its exact name (`Declarations.type_word/2`). A block's
  name is not reserved: a tag may share it. *Decided:* PLAN:732-734.
- **FB-12 Unknown type.** With blocks given, the message names them and suggests the
  nearest, case-sensitive; with none, it is M1-3's message unchanged
  (`Declarations.unknown_type/4`). Mutant M6.
- **FB-13 An instance.** Declared with `var` and no initial value; the initial-value
  message for a user block names its own reason, not a preset
  (`Declarations.instance/1`). *Decided:* M1-6 for instances. Mutant M7.
- **FB-14 From Elixir.** `Tag.new!/4` accepts a user block type that `compile/2` returned
  (`body` a `%Program{}`, name shaped and not reserved); a built-in must equal its own
  (`Declarations.fb_type/1`). Mutant M39.

### Recursion

- **FB-15 No block holds itself.** In block `B`, a declaration whose type is named `B`, or
  holds an instance of a type named `B` at any depth, is a diagnostic at its line naming the
  path (`Compiler.recursion/2`, `holds/2`). A block's own name is a type word in its own
  file, through a stand-in when `types:` lacks it, so the mistake is called recursion, not
  an unknown type (`Compiler.own/2`). From Elixir it raises. *Decided:* org §4.3 (Ed 2
  §2.5). Mutants M8, M9.
- **FB-16 One mistake, one message.** A declaration refused as recursive is taken out of
  the table and its uses are never reported as undeclared (`Compiler.excused?/2`). Mutant
  M10.

### `cal`

- **FB-17 What `cal` runs.** Its first operand is a declared instance of a user block. None,
  a literal, an undeclared name (with M1-3's note), a bool or dint, a member, or a built-in
  timer is a diagnostic; after one, the would-be operands are skipped
  (`Compiler.lower_word/4`'s `cal` clause, `called/3`, `callee/4`, the built-in
  `resolve/6` clause). *Decided:* PLAN M2-5 (non-instance a diagnostic; `cal` on a
  built-in refused). Mutant M17.
- **FB-18 Arity.** It takes exactly as many operands as the block has formals, listed by
  name in the message; one too many is the next instruction, as for any mnemonic
  (`Compiler.arity/5`). *Decided:* org §4.3. Mutant M11.
- **FB-19 An input operand** is a value of the formal's type: a literal that fits, or a
  tag or readable member of that type (`Compiler.formal/5`, `formal_type/5`). Mutant M12.
- **FB-20 An output operand** is a tag or a member logic may write, of the formal's type,
  never a `var_input` and never a literal (`formal_access/4`, `literal_formal/4`,
  `formal_write/6`). Mutants M13, M14, M15.
- **FB-21 Every message names the formal**: ``operand 2 of `cal s1` is `stop` (var_input
  bool)``, then the problem. *Decided:* org §4.3's example.
- **FB-22 One `cal` runs an instance.** A second is an error at its line, citing the
  first (`Compiler.second_calls/2`). Open (F1-Q8). Mutant M16.
- **FB-23 ENO is EN.** `cal` passes on the power it receives, so anything may follow it on
  its path, unlike `ton` (the path pass is unchanged). *Decided:* org §4.3 ("its ENO is the
  power out"); no block can reset ENO, since logex has no ENO word. Mutant M37.

### Evaluation (`Logex.Runtime`, private)

- **FB-24 Energised.** Each input operand is read in the caller's env and copied into its
  formal; the body's rungs run over the instance's map; each output formal is written to
  its operand (`Runtime.called/5`, `copy_in/3`, `copy_out/3`). *Decided:* org §4.3.
  Mutants M18, M19.
- **FB-25 De-energised** (decision 12): nothing copied in, the body does not run, nothing
  written out, no power. The instance and every tag its outputs name are frozen; a timer
  inside keeps `.en` and `last` and catches up when it next runs (decision 8). Mutant M20.
- **FB-26 `first` and `now`** are the call's, the program instance's, so a block first run
  after the first scan can fire its one-shot on that run. *Decided:* PLAN M2-5 note.
  Mutant M21.
- **FB-27 The body's scan.** A `cal` hands its body the scan with `tags` the block's
  table and `ons_blocked` the instance's own subtree; `now` and `first` unchanged
  (`Runtime.called/5`). Departs from CLAUDE.md's convention (F1-Q12). Mutants M22, M40.
- **FB-28 Blocked one-shots by path.** The instance's `ons_blocked` names a bit inside an
  instance by its dotted path; `call/4` makes the list a tree once per scan
  (`Runtime.tree/1`, `grow/2`), so a program bit `edge` and a block's `edge` never
  collide. Mutant M23.
- **FB-29 `scan.tags` is the runtime's.** A host that fills it in is refused
  (`Runtime.scan!/2`). Mutant M24.
- **FB-30 A block type is not a program.** `Runtime.instance/1`, `call/4` and the rest
  refuse a `%FbType{}` with their own message, and so does `Edit.accept/3`
  (`Runtime.program!/1`, `Edit.program!/1`). Mutants M25, M41.
- **FB-31 Total on a hand-built env.** An instance a hand-built env holds as anything but a
  map runs from an empty map, as a timer does (`as_map/1`).

### Members

- **FB-32 Reads from outside.** A user instance's inputs and outputs are read anywhere an
  operand of their type may go (`FbType.public/1`, unchanged). *Decided:* org §4.3,
  decision 9. F1-Q4 asks about inputs, which IEC forbids.
- **FB-33 Locals are hidden.** A block's own `var`, an instance it holds included, is named
  only inside the block; from outside it is a diagnostic that says it is internal, so no
  path from outside is deeper than one member (`Compiler.hidden/3`). Open (the FbType
  moduledoc left it to M2-5, `lib/logex/fb_type.ex:21-24`). Mutant M26.
- **FB-34 No writes from outside.** No member of a user block is written by logic outside
  it (`write: false`; `Compiler.outside/1`'s message). Open (PLAN M2-5 note; F1-Q5).
  Mutant M27.
- **FB-35 Members of a non-instance.** The M1-6 message now says "only an instance of a
  function block has members".

### Warnings

- **FB-36 An instance no `cal` runs**: "`s2` is a seal, but no `cal` runs it: it never
  runs" (`Warnings.unrun/2`). *Decided:* PLAN M2-5 ("must say `cal`"). Mutant M28.
- **FB-37 A `cal`'s operands are uses** with its block's signature: an output it writes is
  written, so a var_output only a `cal` drives is no undriven output, and a `cal` writing an
  `ons` storage bit is warned as any writer is (`Warnings.signature/3`). Mutant M29.

### Online edit (`Logex.Edit`)

- **FB-38 A block type is the whole block.** Accept compares an instance's type by its
  name, members (with initial values) and body rungs with line numbers taken out; any other
  difference is a type change, refused with its own message (`Edit.identity/1`,
  `retyped/4`). Open (F1-Q2). Mutants M30, M31.
- **FB-39 Held outputs through `cal`.** A `cal`'s output operands are writes, so an output
  only a `cal` drove is held where the program started drives it no more (`Edit.written/3`).
  *Decided:* decision 20. Mutant M32.
- **FB-40 One-shots inside a block.** Each `ons` in an instance's block, through every `cal`
  there, is a one-shot of the rung that `cal`s the instance, by path; decision 21's rule

**F1-Q2 · A changed block type while running** (inventory C12, Q5.22; readiness §5).
§4.9 allows "rungs" while running and refuses "the members of a function block type"; a
block's body is neither.
- *(a) Refuse any change to a block type, members or body, line numbers aside* (the
  spike, FB-38). Cost: editing a block's logic needs a restart, as editing an existing
  add-on instruction needs the conventional family offline (`research.md` CNV-17). Nothing

- *(b) Allow a body-only change* (same members by name, type, role and write flag;

  a changed nested initial value is `:initial_changed` by path (decision 29). CODESYS does
  this: *"If no changes were made to the declaration part … but in the implementation only

  OE-1's commit 5.

  moved by name and type. Cost: (b) plus a migration per member and nested instance,
  OE-2's work brought forward.

*Recommend (a) for M2-5, then (b) in OE-2 with (c).* (a) is the reversible choice: allowing
more later breaks no program, and the refusal message says why. *Decide before:* the edit
commit (step 6). This is a departure from §4.9's "Allowed while running: rungs" if a block's
body counts as rungs (§12).

## 13. Risks

- **The contract property does not reach blocks yet.** The seeded property and the edit
  walk in `api_contract_test.exs` generate no `cal`, block or nested state (§8). Until they
  do, `cal`'s totality on hand-built envs and the edit rules for blocks rest on the
  example tests here. This is the main gap between the spike and a landing.
- **A type carries its body in every tag that holds it.** It is plain data and shared, so
  memory is not the cost; the costs are `inspect` in a host-mistake message (`types holds
  …` prints a whole body) and `Edit`'s identity, which strips every block body at every
  accept. Measured linear in depth (the growth test); not measured in the number of block
  types. A message could print only a type's name where it has one.
- **State can be exponential in nesting** where a block holds two of a block that holds two
  …: that is the state's own size, and the recursion check and `Edit`'s walks are the same
  order as the state. No test grows width.
- **Recursion is by name.** A block given in `types:` that was compiled against an older
  block of the name being compiled is refused as recursion, though the data holds no
  cycle: `loop` holding `wrap`, where `wrap` holds an earlier `loop`. That is the intent,
  since state and types are known by name, but it means a library is compiled bottom-up,
  and a loader (M2-2) must order it so.
- **`FbType.signature/1` on the built-in `ton`** returns a list built from its inputs and
  outputs, which no `cal` uses (a `cal` of a timer is refused first). It should refuse a
  built-in type, or say in its doc that it is for a user block only; the spike only says
  the latter.
- **An unknown block type cascades** into "not declared" at every use (F1-Q11), so a typo in
  a block's name gives one line per `cal` and member read.
- **No loader.** `compile_file/1` of a program that uses `seal` fails with "unknown type"
  even with `seal.ld` beside it, until M2-2 or F1-Q6 (b). With no blocks given, the
  message is M1-3's, which names none.
- **Fix F15 stays open.** A block's body has no file, so an `:edit` diagnostic about a block
  type change cites only the program's line, and a recursion found through a block from
  another file cites the declaration in this file, not the other. M2-2 needs F15 closed
  when its loader compiles block files.
- **Wording that still says "program":** `a program's name is a string` and
  `Logex.compile_file/1 takes a path as a binary` are given for a block and for
  `compile_file/2` too. Small, and pinned; a landing should decide whether to reword.
