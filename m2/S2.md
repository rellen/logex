## 0. Summary

- **The shape.** `%Logex.Configuration{}` holds everything M2-1 to M2-6 need as plain
  data: the program types (embedded, by name), and lists in declaration order of tasks,
  globals (located or not), program instances and connections. Each element is a small
  struct with a `line` (nil from Elixir), and the configuration has a `file` (nil from
  Elixir). M2-2's reader builds the same structs with lines and a file; nothing else
  changes shape later (§7).
- **One validator.** `Logex.Configuration.check/1` returns every problem as a
  `%Logex.Diagnostic{stage: :configure}` at its element's line in the configuration's file,
  in line order. `Logex.Configuration.new!/1` builds from Elixir and raises one
  `ArgumentError` whose message is every problem, a line each, formatted as the
  diagnostics are. `Logex.Runtime.start/1` checks again. This is the
  `Tag.new!/4`/`Declarations.check/1` pattern (`lib/logex/declarations.ex:132-141`,
  `:316-323`) widened to "every problem in one raise" (`lib/logex/runtime.ex:270-289`).
- **The scheduler.** `%Logex.Runtime{}` is opaque plain data: the configuration, `now`,
  one value per global (the input image is the input points' values), each instance's
  `%Logex.Instance{}` by name, each task's `next_due` and overlap count by name, and a
  `wiring` derived once from the configuration. `cycle/3` follows org §4.6 step by step
  and scans every instance through `call/4` (`lib/logex/runtime.ex:69-74`), which is what
  keeps `scan/2` and a one-instance configuration in agreement.
- **The Done-when passes** as three tests in `S2-work/test/logex/end_to_end_test.exs`,
  plus a fourth with a timer; the gate passes with **486 tests (7 doctests), exit 0**, up
  from 430. **62 rules reverted one at a time, every one red**; the table is §13.
- **The main departure** (§11): the §4.4 checks on data that M2-1 holds land with M2-1,
  not M2-2 (org §6.2 line 1377). The main open questions (§10): that split, the
  `:configure` stage, one namespace, the overlap count's reader, the first-cycle anchor,
  `next_due_in/1` with task-less instances, `get/2`'s reach, and the location grammar.

## 1. Scope

PLAN M2-1 (`PLAN.md:1297-1313`) and org §6.2 (`docs/organisation.md:1363-1372`):
`%Logex.Configuration{}` with a pure, checked constructor; `Logex.Runtime.start/cycle/
next_due_in/get`; periodic and task-less instances; copy-in and copy-out; overlap events;
and §4.9's list (org:873-887). M2-1 has no syntax. Its Done-when, verbatim:

> a configuration built in Elixir with a 10 ms task, a 30 ms task and a task-less
> instance, cycled for one simulated second by an injected clock, runs each instance
> exactly as often as its task dictates, in priority order; a late cycle yields one
> `{:overlap, …}` and no lost phase; the README program gives identical outputs through
> `scan/2` and through a one-instance configuration.

Read with the decided §4.6 (org:534-691), copy-in needs a source and copy-out a sink, so
M2-1's data holds globals and connections, and the README program's one-instance
configuration needs input and output points (decision 7, every var_input connected,
org:1471-1472). Hence the data model below holds globals, locations and connections from
M2-1, and M2-2 adds only text (S2-Q1).

## 2. The API

### 2.1 `Logex.Configuration` (`S2-work/lib/logex/configuration.ex`)

```elixir
%Logex.Configuration{
  name:        String.t() | nil,                         # the configuration's own name
  file:        String.t() | nil,                         # set by M2-2's loader; nil from Elixir
  programs:    %{String.t() => %Logex.Program{}},        # the program types, by name
  tasks:       [%Logex.Configuration.Task{}],            # declaration order
  globals:     [%Logex.Configuration.Global{}],          # declaration order
  instances:   [%Logex.Configuration.Instance{}],        # declaration order = order in a task
  connections: [%Logex.Configuration.Connection{}],      # declaration order
  warnings:    [%Logex.Diagnostic{severity: :warning}]   # none in M2-1; M2-4 is the first
}

%Logex.Configuration.Task{name: String.t(), interval: pos_integer, priority: non_neg_integer, line: pos_integer | nil}
%Logex.Configuration.Global{name: String.t(), type: :bool | :dint, initial: non_neg_integer | nil, at: String.t() | nil, line: pos_integer | nil}
%Logex.Configuration.Instance{name: String.t(), type: String.t(), task: String.t() | nil, line: pos_integer | nil}
%Logex.Configuration.Connection{instance: String.t(), member: String.t(), to: String.t() | non_neg_integer, line: pos_integer | nil}

Logex.Configuration.new!(keyword) :: %Logex.Configuration{}        # raises ArgumentError, every problem
Logex.Configuration.check(config) :: [%Logex.Diagnostic{stage: :configure}]
Logex.Configuration.location(at)  :: {:ok, {device, "i" | "q", [non_neg_integer]}} | :error
```

- `new!/1` takes `name:`, `programs:` (a **list** of `%Logex.Program{}`, keyed by each
  program's name), `tasks:`, `globals:`, `instances:` and `connections:`, every one
  optional. It returns the configuration with `check/1`'s warnings kept, or raises one
  `ArgumentError` whose message is its own problems (§5.1) then `check/1`'s errors, each
  formatted by `Logex.Diagnostic.format/1`, joined by newlines.
- `check/1` is total over any value in any field: a junk element, an improper list or a
  hand-built program is a diagnostic, never a `FunctionClauseError`
  (`S2-work/lib/logex/configuration.ex`, `proper/4`, `elements/4`). A non-configuration
  raises `ArgumentError`.
- `location/1` is public because the wall-clock runner (after M2, org:1249) routes points
  by device and address (org:514-516); it has a doctest.
- A connection carries no direction (decision 5, org:1464-1467): the member's section
  gives it, as the text does. `to` is a global's name or, for a var_input, a constant, as
  the second word of a connection line is a name or a literal (org:416-417).

### 2.2 `Logex.Runtime` (`S2-work/lib/logex/runtime.ex`)

```elixir
%Logex.Runtime{}   # @opaque; fields: config, now, globals, instances, tasks, wiring

Logex.Runtime.start(config)                  :: %Logex.Runtime{}
Logex.Runtime.cycle(runtime, elapsed_ms, inputs) :: {runtime, outputs, events}
Logex.Runtime.next_due_in(runtime)           :: non_neg_integer | :infinity
Logex.Runtime.overlaps(runtime)              :: %{task_name => non_neg_integer}
Logex.Runtime.get(runtime, path)             :: integer

outputs :: %{output_point_name => integer}     # every output point, every cycle
events  :: [{:ran, task_name | :none, instance_name, now} | {:overlap, task_name, missed}]
```

`instance/1`, `call/4`, `put_inputs/3`, `scan/2,3` and `restart/3` are unchanged. The
tuple order of `cycle/3` is §4.6's (org:540, `{rt, outputs, events}`), kept: the value a
host threads comes first, as in `Logex.Edit`'s `{edit, state, report}`
(`lib/logex/edit.ex:8-12`). `overlaps/1` is the one function the decided API block
(org:669-680) does not list (S2-Q4).

### 2.3 `Logex.Diagnostic`

`@type stage` gains `:configure` (`S2-work/lib/logex/diagnostic.ex`), for a
configuration's tasks, globals, instances and connections (S2-Q2). `line` may be nil for
a `:configure` problem of an element built from Elixir or of the configuration as a
whole.

## 3. The data shapes, and why

| Choice | Why |
|---|---|
| Elements are lists in declaration order, each with a `name` | §4.9: "execution order is a list in the configuration", instances "held flat, keyed by instance name, never nested under a task" (org:875-877). A list keeps the order a printer needs (M2-2) and lets the one validator see a duplicate, which a map would hide from it, so the text path and the Elixir path report it the same way |
| The runtime keys every piece of state by name | org:875-876: "every piece of runtime state is keyed by name, never by position" |
| `programs` embedded, keyed by name | `start(config)` takes one argument (org:675), and the checks need the programs' tags. §4.9's "a `%Logex.Program{}` per program type and … one `%Logex.Configuration{}`" (org:775-777) holds: the configuration holds them by name (S2-Q12) |
| `task` on an instance, not instances under a task | org:876-877, and decision 19's refusal of moving an instance is then one field compared by name (org:864-865) |
| A connection is `{instance, member, to}` with no direction | decision 5 (org:1464-1467); the text has no arrow, so the data has none |
| `line` on every element, `file` on the configuration | the angle's "diagnostics with an optional file and line", and M2-2's "located diagnostic naming its file and line" (PLAN:1319-1320) without a second validator |
| Input image = the input points' global values | §4.6 step 2's "persistent image" (org:550-551) is one copy; an input point has no other writer (org:428-429), so the image cannot drift from the global. Forcing, later, sits between the merge and the scans and before the outputs (org:1250): both points exist in `cycle/3` |
| `wiring` derived at `start/1` | a cycle needs instances grouped by task and connections grouped by instance; grouping per cycle costs O(instances × tasks). It is not state of its own: OE-2 rebuilds it from the candidate |

## 4. The rules

Each rule is enforced in the spike and pinned by a test; §13 gives the revert receipt.

### 4.1 The configuration (`check/1`; one validator)

- **CF-1** A task's, global's or program instance's name is a name: a letter or `_`,
  then letters, digits or `_` (`Declarations.name?/1`, `lib/logex/declarations.ex:57`).
  The configuration's own name, when given, too.
- **CF-2** One namespace for tasks, globals and program instances: the first to take a
  name keeps it, in line order; a name taken again, or differing only in case, is
  refused, as tags' are (`lib/logex/declarations.ex:441-458`). A program type is named in
  type position only, so `program motor motor` is not a clash (S2-Q3).
- **CF-3** Programs are a map of `%Logex.Program{}` (with a map of tags and a list of
  rungs) under their own names, each a name. `new!/1` takes them as a list, refuses an
  unnamed one and a name given twice.
- **CF-4** Each field is a proper list of its element struct; each element's `line` is a
  positive integer or nil.
- **CF-5** A task's interval is 1 to 2147483647 ms (org:442-444; the upper bound S2-Q11).
- **CF-6** A task's priority is 0, the highest, to 2147483647 (decision 11; S2-Q11).
- **CF-7** A global is `:bool` or `:dint` (Q4.4: no function block global in M2).
- **CF-8** A global's initial value is an integer that fits its type
  (`Declarations.fits?/2`, `lib/logex/declarations.ex:92-93`).
- **CF-9** …and is not negative: no line can say one until a negative literal lexes
  (`PLAN.md` §5; the `Tag.new!/4` rule, `lib/logex/declarations.ex:413-417`).
- **CF-10** A located global takes no initial value: an input point because its value
  comes from outside (org:428), an output point because the line shapes give `at` no
  initial value (org:413-414) and the data API refuses what the text cannot say
  (org:779-780). An output point starts at 0 (S2-Q9).
- **CF-11** A location is `<device>.i.<address>` or `<device>.q.<address>`: one token to
  the lexer, its device a name, `i` or `q` in lowercase, its address one or more
  integers, the leftmost the highest (org:496-503; S2-Q8).
- **CF-12** One address holds one global, addresses compared as numbers
  (`panel.i.00` is `panel.i.0`) (S2-Q8).
- **CF-13** A program instance's type is a program of the configuration (did-you-mean or
  the list). An instance of a program that was given but refused (CF-3) is not reported
  again.
- **CF-14** A program instance's task, when it has one, is a task of the configuration.
- **CF-15** A connection names a declared program instance; one whose instance is
  declared but cannot run (CF-13, CF-2) is not checked: one mistake, one message.
- **CF-16** …and a member that its program declares; a dotted member goes too deep.
- **CF-17** …and only a var_input or a var_output: a `var`, a timer included, stays
  internal (org:439).
- **CF-18** A var_input is connected once.
- **CF-19** …to a global of its type (org:437-438) …
- **CF-20** …or to a constant that fits it (a tie-off, org:416), 0 or more.
- **CF-21** A connection's instance and member are names; its `to` is a name or an
  integer of 0 or more.
- **CF-22** A var_output drives a global, never a constant.
- **CF-23** …never an input point (org:428-429).
- **CF-24** …of its type.
- **CF-25** One connection at most drives a global (org:430-431). A var_output may drive
  several globals, one line each (org:417), and an output point may be read back
  (org:402-404).
- **CF-26** Every var_input is connected, to a global or a constant (decision 7,
  org:1471-1472), each missing one cited at its instance's line, in its program's
  declaration order.
- **CF-27** A configuration runs at least one program instance (IEC Ed 2 B.1.7, Ed 3
  Annex A require a program: `research.md` IEC-5; S2-Q10).
- **CF-28** The diagnostics are in line order, those with no line last, each stamped with
  the configuration's `file`. One problem is reported per connection, the first in the
  order CF-15…CF-25 lists; a var_input with any connection counts as connected for CF-26,
  and a global as driven only by a good connection.
- **CF-29** `check/1` is total: any value in any field, of the configuration or of an
  element, gives diagnostics, never another exception. A junk name is never offered as a
  did-you-mean, and a connection to a global whose type CF-7 refused is not checked again.
  (The seeded property of §8 found both cases as crashes in the spike's first form; a
  revert of the output-side guard alone stayed green under the property, so one test now
  pins both cases.)

### 4.2 Starting (`start/1`)

- **RT-1** `start/1` takes a `%Logex.Configuration{}` and checks it again; any error
  raises one `ArgumentError` listing every one, formatted.
- **RT-2** It builds every instance with `Runtime.instance/1` (fix F14, org:1628-1629), so
  its first scan is a first scan (`first: true`, `ons_blocked: []`, `switched: false`).
- **RT-3** `now` is 0, every global is at its initial value or 0, every task's `next_due`
  is 0 ("anchored at start", org:556) and its overlap count 0.

### 4.3 A cycle (`cycle/3`), in order (org:546-583)

- **CY-0** The checks, in order: the runtime (`%Logex.Runtime{}`), `elapsed_ms`, then the
  inputs.
- **CY-1** `now` advances by `elapsed_ms`, a non-negative integer.
- **IN-1** `inputs` is a map keyed by input-point name: only an input point is set. A
  non-string key, an output point, an unlocated global, a path into an instance and an
  unknown name are refused.
- **IN-2** Each value fits its point's type exactly, as a var_input's does (the
  `call/4` messages, `lib/logex/runtime.ex:336-347`).
- **IN-3** Every input problem comes in one raise, a line each, in key order (as
  `merge!`, `lib/logex/runtime.ex:269-289`), and a refused cycle changes nothing.
- **CY-2** The inputs merge into the input points, which keep their values between
  cycles: a host sends only what changed, and every scan of the cycle sees one sample.
- **CY-3** A periodic task is due when `next_due <= now`.
- **CY-4** Due tasks run by priority, the lower number first; then the earlier
  `next_due`; then declaration order (decision 11, rule 3a).
- **CY-5** A task that runs moves `next_due` to `next_due + (missed + 1) × interval`,
  where `missed = div(now − next_due, interval)`: past `now`, by whole intervals, so the
  phase never drifts (org:592-602).
- **CY-6** `missed > 0` emits `{:overlap, task, missed}` before the task's scans, and adds
  `missed` to the task's overlap count.
- **CY-7** Within a task, instances run in the configuration's order; task-less instances
  run after every due task, once each, in every cycle, an elapsed-0 cycle included
  (org:574-577, org:661).
- **CY-8** A scan copies each connected var_input in, from its global's current value or
  its constant, runs the instance through `call/4` with `%Scan{now: now, first:
  state.first}`, and copies each connected var_output out to its global at once, so an
  instance sees what an earlier one wrote in the cycle and never what a later one writes
  (org:585-590).
- **CY-9** The outputs are every output point (a global at a `q` address), after every
  scan of the cycle, whether or not any scan wrote it; never an unlocated global.
- **CY-10** A task with no instance is still scheduled: due, moved on, its missed periods
  counted and reported; it runs no scan. (OE-2 may remove a task's last instance while
  running, org:869, so a task with none must be legal; a warning, if any, is M2-3's.)
- **EV-1** One `{:ran, task, instance, now}` per scan, `task` the task's name or `:none`,
  in the order the scans ran; each `{:overlap, …}` before its task's scans. The kinds are
  an open set (org:887).

### 4.4 Reading (`next_due_in/1`, `overlaps/1`, `get/2`)

- **NX-1** `next_due_in/1` is `min(next_due) − now`: 0 after `start/1`, when every task
  is due, and more than 0 after every cycle, which moves each task it runs past `now`; it
  ignores task-less instances, and is `:infinity` with no task (S2-Q6). (The spike first
  floored it at 0; reverting the floor turned nothing red, because no call within the
  contract reaches an overdue task, so the floor was removed and the walk asserts the
  value is positive after every cycle.)
- **NX-2** `overlaps/1` is each task's overlap count, by name.
- **GT-1** `get/2` takes an access path that lexes as one name token: a global
  (`"estop"`), an instance's declared tag (`"m1.fault"`, a `var` included), or a public
  member of a function block instance at any depth (`"m1.t1.acc"`), through
  `FbType.member/2` (`lib/logex/fb_type.ex:87`), so never an internal member.
- **GT-2** An instance or a block instance named whole, a path past a bool or a dint, and
  a name that is neither a global nor an instance are refused, with a did-you-mean.
- **ST-1** Every call takes a `%Logex.Runtime{}` from `start/1` and checks that first. One
  built or edited by hand, or a configuration changed after `start/1`, is outside the
  contract (the moduledoc says so, as for `%Logex.Instance{}`,
  `lib/logex/runtime.ex:42-43`).
- **ST-2** A cycle is a function of its arguments: made twice, it gives the same result.

## 6. New state, and its rule across an online edit

`first` is set by `instance/1` and cleared by its first scan; `ons_blocked` and `switched`

## 7. How the later items and OE-2 extend it

Nothing below reshapes a struct M2-1 lands or reverses one of its rules. Each item adds
text, adds a field with a default, adds a rule, or narrows or widens one by a clause (CF-1
gains the configuration keywords at M2-2; CF-5 admits an event task at M2-6).

### 7.1 M2-2 · the configuration file

- **Text only.** `Logex.Configuration.compile(source, programs, opts)` (S2-Q15 on its
  argument order) lexes and parses with `Logex.Lexer`/`Logex.Parser` as
  `Logex.Declarations` does (no golden change, `readiness.md` §6), maps each rung to one
  element struct by its first word, setting `line`, sets `file`, and calls `check/1`. Its
  own diagnostics (stage `:configure`) are the line shapes: an unknown line word with a
  did-you-mean, a missing or extra word, a branch group, an unknown type word, `with`
  before M2-3.
- **Words.** `keywords/0` on `Logex.Configuration` returns `program var_global at bool
  dint`; `naming_test.exs` reads it; CF-1 grows "and not a configuration keyword", so
  the data path refuses a name the text cannot say (org:779-780). Until then, M2-1
  reserves nothing (no stanza is owed by M2-1).
- **Fix F15.** A `file` field on `%Logex.Program{}`, set by `compile_file/1`; M2-2's
  loader resolves `motor` to `motor.ld` beside the `.lcf` (org:473). `check/1` needs it
  first in M2-4.
- **A printer** from `%Logex.Configuration{}` to text, with a round trip: every
  configuration `new!/1` accepts prints to text that compiles to an equal configuration
  but for lines and file (S2-Q16).
- **`compile_file/1`** refuses anything but `.ld` (PLAN:1321-1324), and the stale comment
  at `test/logex_test.exs:270-271` goes.
- **Warnings**, if any (an unused global, a task with no instance), go to `warnings`.

### 7.2 M2-3 · periodic tasks in text

`task <n> interval <ms> priority <p>` and `program … with <task>` build `Task` and
`Instance.task`, which exist from M2-1. M2-3 adds only the reader's lines and its words
(`task interval priority with`, four stanzas; the `priority` one must say that Siemens
numbers the other way, `research.md` SIE-1). Word order and a missing `priority` are the
reader's diagnostics. Its acceptance's counts (100 and 20) are M2-1's scheduler at 10 ms
steps from t = 0 to 990 (C14, Q1.17).

### 7.3 M2-4 · shared globals

- **Program.** `var_external` is a row of `Declarations.@sections`; `Tag.section` gains
  `:var_external`; a public "which tags a program writes" (one IR walk, `readiness.md`
  §4.1).
- **`check/1` gains** three rules: each `var_external` of each runnable instance's
  program has a global of its name and type, cited at the `program` line with the `.ld`
  file and line in the message (F15); a `var_external` the program writes is not bound to
  an input point; and two instances writing one global through `var_external` is a
  warning in **`config.warnings`**, which M2-1 lands empty (C5 resolved: the
  configuration's channel, not a program's).
- **Runtime: one copy.** `wiring` gains `externals: %{instance => [name]}`; the scan step
  (`scanned/3`) puts each external's global value into the instance's env before `call/4`
  and takes it out after, writing it back to `globals`, so between scans the only copy is
  `globals` (org:886). `evaluate/3` is untouched. A lone program's `scan/2` keeps its
  externals in its env: the implicit configuration's globals are its own (Q4.2).
- **`get/2`** reads `m1.estop` as the global.

### 7.4 M2-5 · user function blocks

- **Configuration: nothing.** A program carries its block types (in its tags' types, or a
  library: M2-5's question), and the configuration holds programs.
- **`get/2`: nothing.** It already walks a member whose type is a `%Logex.FbType{}`, at any
  depth, through `FbType.member/2`, which leaves out internal members
  (`S2-work/lib/logex/runtime.ex`, `in_block/5` and `member_at/6`). So `m1.s2.run` reads
  as M2-5's acceptance says, through a `var` (`s2`), once M2-5's `FbType` has nested
  members; whatever M2-5 decides about `:local` it decides in `FbType.public/1`, and
  `get/2` follows. M2-5 owes `get/2` a growth test in depth (S2's path walk is linear in
  depth).
- **Scheduler: nothing.** `cal` lives in the evaluator, under `call/4`.

So M2-5 needs nothing from M2-1, and M2-1 nothing from M2-5. S2-Q17 asks to keep decision
1's order.

### 7.5 M2-6 · event tasks

- `Task` gains `single: nil | global_name`, and `:interval` leaves its `@enforce_keys`
  (nil for an event task); CF-5 becomes "a task has an interval of 1 to 2147483647 ms,
  or a `single`, or both"; a new rule: `single` names a bool global (org:445-447).
- Each event task's state gains `last: 0`, the trigger's last sampled value: 0 at
  `start/1`, so a trigger already 1 fires in the first cycle (decision 11); 0 at a restart;
  kept by OE-2 for a kept task, and a changed `single` refused as a task change (decision
  19 allows only interval and priority). This is the "event task's trigger" exception
  §4.9 names (org:879-880), and its home is the runtime's task state, not
  `Program.initial_env/1`'s doc (C21).
- `cycle/3` samples every trigger after the input merge and before choosing due tasks
  (Q6.1); with `interval` too, the periodic due counts only while the trigger is 0.
- `next_due_in/1` ignores event-only tasks, as it ignores task-less instances (NX-1):
  a runner cycles on an input change.
- The `ton`-in-an-event-task warning goes to `config.warnings`.

### 7.6 OE-2

- **Compare by name.** Instances (type, task), globals (type, `at`, `initial`) and tasks
  (interval, priority, later `single`) are all lists of named structs: OE-2 maps each by
  name and compares fields (Q7.3).
- **One plan per type.** Every instance of a type is `for i <- config.instances, i.type
  == name` (Q7.4), each state an ordinary `%Logex.Instance{}` whose `type` names its
  program (`lib/logex/instance.ex:28`), so `Logex.Edit`'s private switch and prune (F5)
  apply per instance.
- **A generation counter** is OE-2's to add: `%Logex.Runtime{}` is opaque, so a field
  added later breaks no host (Q7.2; S2-Q18).
- **Held output points.** A global no connection drives any more keeps its value in
  `globals` by construction; OE-2 reports each output point among them (decision 20,
  C6). Nothing is owed before OE-2.
- **Editing during M2** is not possible: the runtime is opaque, so `Logex.Edit` cannot be
  applied to an instance inside it (Q7.6). The moduledoc should say so when M2-1 lands.

### 7.7 The §4.4 plant, as M2-1's data

## 10. Open questions for the maintainer

Each has options, consequences, a recommendation, and when it must be decided: most before
M2-1 lands (commit 1 of §9), the rest before the item named. S2-Q13 and S2-Q18 are OE-2's,
stated here because they concern M2-1's state.

**S2-Q1. Does M2-1's data hold globals, locations and connections, with the §4.4 checks
on them?** (C7; `readiness.md` §9 item 1)
- *(a) Yes, all of it in M2-1* (the spike). M2-2 adds text, words and line shapes only.
  Consequence: M2-1 is larger (28 configuration rules), and lands checks org §6.2 assigns
  to M2-2 (§11 D1).
- *(b) Tasks and instances only, copy-in keyed by `instance.var_input`*, globals in M2-2.
  Consequence: the README one-instance test needs a different host image shape, and M2-2
  reshapes the data M2-1 landed: rework §4.9 asks to avoid (org:873).
- *Recommend (a).* Copy-in needs a source; §4.4's "a constructor built from Elixir data
  runs the same checks" (org:474-475) and §4.9's "one checked constructor, which the
  `.lcf` parser feeds" (org:881) both read as one validator before any text.

**S2-Q2. The stage of a configuration problem.** (Q0.1)
- *(a) `:configure`, new* (spike). *(b) `:validate`, reused*: its documented meaning is
  `instructionize/2`'s (`lib/logex/diagnostic.ex:9-12`). *(c) A stage per kind of check.*
- *Recommend (a)*: one stage for the validator and M2-2's line shapes; `.lcf` lex and
  parse errors keep `:lex` and `:parse`.

**S2-Q3. Names.** (Q1.5, Q2.11, Q3.4)
- *(a) One namespace for tasks, globals and instances; program types apart; case-only
  twins refused* (spike). *(b) A namespace per kind.* *(c) Program types in it too*,
  refusing `program motor motor`.
- *Recommend (a).* `get/2` reads a global and an instance by the same first word, so they
  must not clash; refusing a clash now and allowing it later breaks nothing, the reverse
  breaks plants (decision 7's argument). Program types are named only in type position.

**S2-Q4. The overlap count's reader.** (Q1.20)
- *(a) `overlaps/1`* (spike), a fifth function beside §4.6's four.
- *(b) Events only, no stored count*: departs from org:596 ("adds `missed` to its overlap
  count") and decision 11's "counted".
- *(c) The count kept, unreadable*: state no test can see, against CLAUDE.md:178-180.
- *Recommend (a).*

**S2-Q5. The first cycle.** (C14, Q1.16)
- *(a) Keep §4.6: `start/1` is time 0, every task due at 0; a first cycle after elapsed
  `e` reports the periods before it* (spike; `scheduler_test.exs`, "a first cycle after
  the start reports the periods before it": 25 ms in, a 10 ms task reports 2). A runner
  cycles at elapsed 0 first.
- *(b) Anchor each task at the first cycle*: no report, a phase that depends on the host.
  Departs from org:556 "anchored at start".
- *(c) `start/2` with a start time*: a second form of the API.
- *Recommend (a)*, with the moduledoc saying it: the report is true, not spurious.

**S2-Q6. `next_due_in/1` with task-less instances.** (C13, Q1.18)
- *(a) It ignores them and is `:infinity` with no periodic task* (spike): "the runner
  paces cycles" (org:661).
- *(b) 0 whenever a task-less instance exists*: a runner that sleeps on it busy-loops.
- *Recommend (a)*; M2-6's event tasks are ignored the same way.

**S2-Q7. Restarting a configuration.** (Q1.21; `readiness.md` §9 item 13)
- *(a) None in M2-1: `start/1` again is the cold restart*; `:warm` waits for RETAIN, as
  `restart/3`'s does (`lib/logex/runtime.ex:131-134`).
- *(b) `restart/2` now*, with a rule per field (§6's restart column).
- *Recommend (a)* for M2-1; OE-2 decides whether a restart during an edit needs (b).

**S2-Q8. The location grammar.** (Q2.9)
- Device: *one name* (spike) or dotted (`rack1.slot2.i.0`). `i`/`q`: *lowercase only*
  (spike; org:497 "lowercased") or any case. Address: *one or more integers, compared as
  numbers* (spike) or exactly one. One address, one global: *refused* (spike) or allowed.
- *Recommend the spike's on each*: each can be widened later without breaking a plant. A
  known oddity: `panel.i.1` and `panel.i.1.0` are two addresses.

**S2-Q9. An initial value on an output point.** (Q2.10)
- *(a) Refused* (spike): the line shapes give `at` none, and an output starts safe at 0
  until its instance first scans, which copies out the var_output's own initial value.
- *(b) Allowed*, with a place on M2-2's line.
- *Recommend (a).*

**S2-Q10. A configuration with no program instance.** (`research.md` IEC-5)
- *(a) A diagnostic* (spike), as IEC's grammar requires a program. *(b) Allowed.*
- *Recommend (a).*

**S2-Q11. Bounds.** (Q3.1, Q3.2)
- Interval: *1 to 2147483647 ms* (spike; a dint, like a preset,
  `lib/logex/declarations.ex:28`) or any positive integer. Priority: *0 to 2147483647*
  (spike) or unbounded, or 0..31 (CODESYS).
- *Recommend the spike's*: logex's integers are dints.

**S2-Q12. Programs inside the configuration.** (Q1.2, Q2.5)
- *(a) Embedded, `programs: %{name => program}`*, `new!/1` taking a list (spike).
  *(b) `start/2` taking the programs beside a configuration that names them.*
- *Recommend (a)*: `start(config)` has one argument (org:675), and the validator needs the
  tags.

**S2-Q13. A task's interval changed by OE-2.** (Q3.8)
- *(a) `next_due` kept; the next run advances by the new interval* (phase re-anchored at
  that run). *(b) `next_due` moved to the next multiple of the new interval from start.*
  *(c) Re-anchored at the switch.*
- *Recommend (a)*: no run is added or lost at the switch. Decide before OE-2; stated here
  because it is M2-1's state.

**S2-Q14. The constructor's form.**
- *(a) `new!/1` with a keyword list of element structs; `check/1` public; `start/1`
  checks again* (spike). *(b) Plain maps for elements.* *(c) `start/1` trusts a
  configuration from `new!/1`*, a hand-built one outside the contract.
- *Recommend (a)*: structs document the fields and enforce keys; checking at `start/1`

**S2-Q15. `Configuration.compile`'s argument order.** (C15; decide before M2-2)
- *(a) `compile(source, programs, name: "plant")`*, mirroring `Logex.compile(source,
  name:)` (`lib/logex.ex:50-71`); departs from org:470's `compile(name, source, types)`.
- *(b) Keep org:470.*
- *Recommend (a)*, and `programs` as a list, as `new!/1` takes it.

**S2-Q16. A printer from data to `.lcf`.** (C17, Q0.5; decide before M2-2)
- *(a) M2-2 owes it, with a round trip* (`readiness.md` §9 item 12). *(b) No printer in

- *Recommend (a)*: "the data API refuses what the text cannot say" has nothing to be

**S2-Q17. The order of the milestone.** (C31; decide before M2-1)

- *(b) M2-5 first* (`inventory.md` §11), rewording its acceptance (C1).

**S2-Q18. A generation counter.** (Q7.2; decide before OE-2)
- *(a) OE-2 adds it*: the runtime is opaque, so a new field breaks no host. *(b) Reserve

- *Recommend (a).*

**S2-Q19. What `get/2` reads.** (Q1.19; `readiness.md` §9 item 11; decide before M2-1)

## 12. Risks

- **`Logex.Configuration.Task` shadows Elixir's `Task`** wherever a host aliases it. The
  spike never aliases it (`%Configuration.Task{}`); the moduledoc should warn, or the
  struct take another name (`Logex.Configuration.TaskDecl`?), against IEC's word.
- **The walk's model restates the scheduler.** Its next due time is computed another way
  (the next multiple of the interval after `now`), and one oracle (runs plus missed
  periods) knows nothing of it, but a shared misreading of §4.6 would pass both. The
  Done-when's output oracle (an input sampled at multiples of 30) is a third.
- **Cost per scan.** `call/4` checks the program, state, scan and every input again
  (about 12%, `readiness.md` §1.6), and `outputs/2` walks every tag (§9 commit 0). A
  configuration multiplies both by its instances. Accepted for M2-1; measured above as
  linear.
- **`get/2` at depth** is linear in the path (the walked path is kept reversed), but no
  growth test pins it until M2-5 gives it depth.
- **An opaque struct a host may still match on**: a host that matches `%Logex.Runtime{}`
  fields breaks when OE-2 adds one. The moduledoc says it is opaque.
- **Messages that inspect a configuration or a runtime** (`expected a %Logex.Runtime{} …,
  got: %Logex.Configuration{…}`) print the whole value, programs included; long but
  correct.
- **M2-4's one copy is sketched, not spiked** (§7.3). It changes `scanned/3`, not
  `call/4`'s contract, but `Program.initial_env/1` meets externals and needs M2-4's
  rule.
- **`configuration.ex` is long** (1,101 lines in the spike, most of it the validator's
  messages). M2-2's reader belongs in a module of its own, beside it, not in it.
- **Hand-built inputs to `check/1`** are handled totally, but a hand-built
  `%Logex.Program{}` whose tags are not `%Logex.Tag{}` is filtered silently in
  `unconnected/2` rather than reported; it is outside the contract already
  (`lib/logex/runtime.ex:42-43`).
