## 0. The answer in one page

- **What a host gets.** `Logex.Configuration.new!/1` builds a configuration from Elixir
  data and refuses it with every problem in one `ArgumentError`. `Logex.Runtime.start/1`
  makes a resource of it; `cycle/3` steps it; `next_due_in/1` says how long to sleep;
  `get/2` reads a global, a tag or a member by path; `overlaps/1` gives each task's count of
  missed periods; `restart/2` starts the resource again. Everything else in M2-1 is
  private.
- **The host's loop is four lines** (§2.3): sleep `next_due_in/1`, read devices, `cycle/3`
  with the time that really passed, write the outputs. `start/1` leaves every task due, so
  the first cycle runs at once, and a cycle is a pure function of its three arguments.
- **The data model carries M2-2 to M2-6 without rework.** Globals (located or not),
  instances, tasks and connections are lists of plain maps in declaration order, each with
  a `line` (nil from Elixir), and the program types are embedded by name. M2-2's reader
  builds the same maps with lines and calls the same `check/1`, which returns
  `{line, message}` pairs (§3, §7).
- **Three tensions the inventory found are settled here** with a recommendation each:
  the first cycle's "spurious" overlap is the decided rule working, not a defect (Q-5);
  `next_due_in/1` ignores task-less instances, which the runner paces (Q-4); and the §4.4
  checks M2-1's data can express land with M2-1 (Q-1, a departure).
- **The Done-when passes as written** (`spike test/logex/end_to_end_test.exs`, describe "a
  configuration from Elixir data (M2-1)"), and so does the gate: format, both compiles and
  `mix test --warnings-as-errors` each exit 0, **491 tests (6 doctests), up from 430**.
- **A seeded walk checks the scheduler against an oracle** written from org §4.6's text,
  300 random configurations of 40 random host calls each, with every accepted call made
  twice; and a second walk feeds `new!/1` 1,500 randomly broken configurations. Each
  asserts its reach, and the reach held under 25 seeds besides the committed one.
- **Growth in reductions**: a cycle takes 16.14x to 16.28x the reductions for 16x the
  instances (30 runs, bound 19.5), 4.02x to 4.13x for 4x the tasks, and `new!/1` with
  `start/1` 4.15x to 4.24x for 4x the configuration (36 runs each, bound 5.5).
- **Mutation table** (§10): 63 rules reverted one at a time, **63 red**. Three findings came
  out of it and are fixed in the spike: a declaration-order tie-break no test told from
  name order, a growth test that could not see an append at 4x, and 19 first-form mutants
  that did not compile and were rewritten.
- **Departures for the maintainer** (§12): the §4.4 checks in M2-1, two functions beyond
  org §4.6's API list (`overlaps/1`, `restart/2`), and `new!/1` raising every problem
  rather than the first, as `Tag.new!/4` does.

## 2. The API

### 2.1 Every signature and return shape

```elixir
# Logex.Configuration (spike lib/logex/configuration.ex)
Logex.Configuration.new!(fields :: keyword) :: %Logex.Configuration{}      # raises ArgumentError
Logex.Configuration.check(config) :: [{line :: pos_integer | nil, message :: String.t()}]
Logex.Configuration.location(at) :: {:ok, :input} | {:ok, :output} | :error

# Logex.Runtime (spike lib/logex/runtime.ex); call/4, instance/1, put_inputs/3,
# scan/2,3 and restart/3 are unchanged
Logex.Runtime.start(config) :: %Logex.Runtime{}                            # @opaque
Logex.Runtime.cycle(rt, elapsed_ms :: non_neg_integer, inputs :: %{String.t() => integer})
  :: {rt, outputs :: %{String.t() => integer}, [event]}
Logex.Runtime.next_due_in(rt) :: non_neg_integer | :infinity
Logex.Runtime.get(rt, path :: String.t()) :: integer
Logex.Runtime.overlaps(rt) :: %{task :: String.t() => non_neg_integer}
Logex.Runtime.restart(rt, :cold | :warm) :: rt

event :: {:overlap, task :: String.t(), missed :: pos_integer}
       | {:ran, task :: String.t() | :none, instance :: String.t(), now :: non_neg_integer}
```

`new!/1`'s `fields` is a keyword list of `name:` (a string shaped like a name, required)
and five lists, each optional and `[]` when left out:

| Key | Element | Required keys | Optional keys |
|---|---|---|---|
| `programs:` | a `%Logex.Program{}` from `Logex.compile/2`, kept under its own name | — | — |
| `tasks:` | `%{name:, interval:, priority:}` | all three | — |
| `globals:` | `%{name:, type:, initial:, at:}` | `name`, `type` (`:bool` or `:dint`) | `initial`, `at` |
| `instances:` | `%{name:, type:, task:}` | `name`, `type` (a program's name) | `task` (nil: task-less) |
| `connections:` | `%{member:, to:}` | both: `"m1.start"`, and a global's name or an integer | — |

`runtime_test.exs`'s surface test pins both modules exactly (`spike test/logex/runtime_test.exs`,
"the public surface (B5)"): `Logex.Runtime` gains `__struct__: 0, __struct__: 1, cycle: 3,
get: 2, next_due_in: 1, overlaps: 1, restart: 2, start: 1`; `Logex.Configuration` is
`[__struct__: 0, __struct__: 1, check: 1, location: 1, new!: 1]` with its six keys.

**Why these names.** `start`, `cycle`, `next_due_in` and `get` are org §4.6's (org:675-678).
`overlaps/1` and `restart/2` are new (Q-2, Q-3, DEP-2). `check/1` is public because M2-2's
reader is the second caller of the one validator (§4.9, "one checked constructor, which
the `.lcf` parser feeds", org:881) and may live in its own module; `location/1` is public
because the runner routes points by device (org:514-516) and must read a location the way
the validator does. None of these is a language word, so none owes a `docs/naming.md`
stanza.

### 2.2 Tuple orders (inventory Q0.4, C16)

`cycle/3` returns `{rt, outputs, events}` as org:540 decides, against `call/4`'s `{outputs,
state}` and `Logex.Edit`'s `{edit, state, report}`. Kept: the decided order puts the value
the host threads first, as `Logex.Edit` does, and `call/4`'s order is M1-5's, older than
both. Not reopened.

### 2.3 The host's side: a runner, step by step

```elixir
rt = Logex.Runtime.start(config)          # every task due now
t0 = System.monotonic_time(:millisecond)  # only the runner reads a clock (org:604-607)

loop(rt, t0):
  wait = Logex.Runtime.next_due_in(rt)    # ms, or :infinity
  sleep(min(wait, pace))                  # pace: how often to run task-less instances,
                                          # or to look at inputs that may change
  t = System.monotonic_time(:millisecond)
  inputs = read_devices()                 # the input points, by name; only what changed is fine
  {rt, outputs, events} = Logex.Runtime.cycle(rt, t - t0, inputs)
  write_devices(outputs)                  # every output point, every cycle
  handle(events)                          # ignore a kind you do not know
  loop(rt, t)
```

What the host can rely on, each pinned by a test (§8):

1. **The first cycle runs at once.** `next_due_in/1` is 0 after `start/1` (and after
   `restart/2`), and every periodic task runs in the first cycle even at `elapsed_ms` 0.
2. **Time is the host's.** `cycle/3` adds `elapsed_ms` to `now`; nothing inside reads a
   clock. A scan's timers count the real time that passed, not a nominal interval
   (org:637-639), so a 30 ms task cycled at 10 ms steps sees 30 ms between its scans.
3. **Late is reported, never replayed.** A cycle that comes a whole interval or more after
   a task fell due runs that task once and reports `{:overlap, task, missed}`; the task
   keeps its phase. A host that sleeps on `next_due_in/1` and is never late sees no
   overlap.
4. **Inputs are a delta.** Only input points, each with a value that fits its type; they
   merge into the image, so a host sends what changed. Every problem with one call comes
   in one raise, a line each, in key order. The image starts at 0, so the first cycle
   after `start/1` carries every input point the host knows, as a runner that reads all
   its devices does; after `restart/2` the image is kept and a delta is enough again.
5. **Outputs are a snapshot.** Every output point, every cycle, whether or not anything
   ran: a runner writes the map as it comes, or diffs it itself.
6. **Events are a log, and an open set.** The overlaps come first, in the order their
   tasks run, then one `{:ran, …}` per scan in the order it ran. A host matches the kinds
   it knows and ignores the rest.
7. **The same calls give the same results.** A cycle is a pure function of `rt`,
   `elapsed_ms` and `inputs`; every order it produces comes from a list in the
   configuration or an explicit sort, never from a map's iteration order (CONTRIBUTING.md,
   "A map of 32 keys or fewer iterates in key order"; §8 pins two orders with more than 32
   keys).
8. **A host mistake raises `ArgumentError`, with a pinned message, and nothing else
   escapes.** Both walks (§8.4) assert it.
9. **A run can be replayed.** Since a cycle is pure, a host that records each cycle's
   `elapsed_ms` and inputs reproduces every output and event from `start/1` exactly: the
   Milestone-2 done sentence's "the same outputs on every run" (`PLAN.md:1369-1373`), and
   a debugging tool a wall-clock PLC does not have.

**What the runner owns, not the core** (org §4.5, org:604-607, decision 14): the clock, the
devices and their `at` routing, the pace of task-less instances, the watchdog, and what a
watchdog fault does to the outputs (decision 14 recommends zeroing them once and requiring
an explicit restart, which is `restart/2`).

## 3. The data

### 3.1 `%Logex.Configuration{}`

```elixir
%Logex.Configuration{
  name: "plant",
  programs: %{"motor" => %Logex.Program{name: "motor"}},
  tasks: [%{name: "fast", interval: 10, priority: 1, line: nil}],
  globals: [%{name: "k1", type: :bool, initial: nil, at: "panel.q.0", line: nil}],
  instances: [%{name: "m1", type: "motor", task: "fast", line: nil}],
  connections: [%{member: "m1.motor", to: "k1", line: nil}]
}
```

- **Lists in declaration order.** The order of `instances` is the order within a task and
  among the task-less; the order of `tasks` is the last tie-break between tasks (org:570-577).
  That is §4.9's "execution order is a list in the configuration" (org:877).
- **Plain maps with every key** of their part, the optional ones nil, and `line`. A map is
  what a host writes; a struct per element would add four public modules for no check a
  map lacks, since `check/1` refuses a missing or extra key by name (Q-15).
- **Programs embedded, by their own names.** `start/1` takes the configuration alone
  (org:675), so the types travel with it, and `Configuration.compile(name, source, %{"motor"
  => program})` (org:470) already holds the same map. From Elixir they are a list, so a key
  can never differ from its program's name.
- **A line on every element**, nil from Elixir, set by M2-2's reader. An element from
  Elixir that brings one is refused, as `Tag.new!/4` refuses a tag with a line
  (`lib/logex/declarations.ex:134-135`): a line is what marks an element read from a file.
- **No `file` and no `warnings` yet.** M2-2 adds `file` with its loader; the first item with
  a configuration warning (M2-4's two-writer warning, or M2-6's timer in an event task)
  adds `warnings: []`. Adding a field to a struct is not rework; a field nothing sets is a
  rule no test can pin.

### 3.2 `%Logex.Runtime{}`, opaque

```elixir
%Logex.Runtime{
  config:    %Logex.Configuration{},
  now:       non_neg_integer,
  globals:   %{global => integer},                       # one value per global; the input
                                                         # points' entries are the input image
  instances: %{instance => %Logex.Instance{}},           # flat, by name (org:875-877)
  tasks:     %{task => %{next_due: integer, overlaps: non_neg_integer}},
  plan:      %{tasks: [...], taskless: [...], wiring: %{...}, inputs: %{...}, outputs: [...]}
}
```

- **One copy of each global** (org:886): `globals` is the only place a global's value lives.
  The input image is not a second map: it is the input points' entries in `globals`, which
  only `cycle/3`'s inputs write, since nothing may drive an input point (CK-2).
- **`plan`** is what `start/1` works out once from the configuration alone and a cycle only
  reads: each task with its instances, the task-less instances, each instance's
  connections, and the input and output points. It is derived data, rebuilt from the
  configuration, so it needs no rule across an edit of its own (§6).
- **Opaque** (`@opaque t`). A host keeps the value and changes it only through the API; one
  built or edited by hand is outside the contract, as a hand-built `%Logex.Program{}` is
  (`lib/logex/runtime.ex:42-43`).
- **One module, two roles** (inventory Q1.26): the struct lives in `Logex.Runtime`, the
  decided name of the value (org:536), beside the functions that run it.

## 4. The rules

Each rule is stated once. A rule marked † was reverted alone in §10 and turned at least one
test red.

### 4.1 The scheduler (`spike runtime.ex`, `start/1`, `cycle/3`, `next_due_in/1`, `restart/2`)

- **SC-1 †** Due tasks run by priority, 0 first (decision 11; org:570).
- **SC-2 †** At one priority, the task due earlier runs first: rule 3a's "longest waiting
  time" (org:572-573). The due time is the task's pending `next_due`, before this cycle
  moves it.
- **SC-3 †** Then declaration order (org:570).
- **SC-4 †** A periodic task is due when its `next_due` is at or before `now`.
- **SC-5 †** A due task adds `missed = div(now - next_due, interval)` to its overlap count
  (org:596).
- **SC-6 †** and gives `{:overlap, task, missed}` when `missed` is more than 0 (org:597).
- **SC-7 †** Its `next_due` moves to `next_due + (missed + 1) * interval`, past `now` by
  whole intervals, so its phase never drifts (org:557-558, 598).
- **SC-8 †** `missed` counts every period since the due time, not at most one; the task
  still runs once, coalesced, never caught up (org:600-602), which no code does otherwise,
  so there is no catch-up branch to revert.
- **SC-9 †** Task-less instances run last, once each, in every cycle, at `elapsed_ms` 0
  too (org:577, 661).
- **SC-10 †** Each scan copies in from the globals as they stand, so an instance sees what
  an earlier one wrote in the same cycle, and never what a later one writes (org:589-590).
- **SC-11 †** Each scan copies each connected var_output out to every global it drives.
- **SC-12 †** A constant connection copies its constant in (org:416).
- **SC-13 †** The inputs merge into a persistent image: a point left out keeps its value
  (org:550).
- **SC-14 †** The outputs are every output point, every cycle, and nothing else.
- **SC-15 †** The events are the overlaps, in their tasks' run order, then one `:ran` per
  scan in run order.
- **SC-16 †** `next_due_in/1` is `:infinity` with no periodic task (org:677).
- **SC-17 †** and otherwise the time to the soonest `next_due`; task-less instances are not
  counted (Q-4).
- **SC-18 †** `start/1` sets `now` to 0 and every `next_due` to 0: every periodic task is
  due in the first cycle (org:556-557).
- **SC-19 †** `start/1` builds each instance with `Runtime.instance/1` (fix F14, org:882-884).
- **SC-20 †** `start/1` runs `Configuration.check/1` again and refuses what `new!/1` would.
- **SC-21 †** `restart/2` sets every overlap count to 0,
- **SC-22 †** every `next_due` to `now`, so every task is due at the next cycle,
- **SC-23 †** keeps the input image,
- **SC-24 †** restarts each instance through `restart/3`,
- **SC-25 †** and puts every other global back at its initial value. In one sentence:
  after `restart/2` the resource is as `start/1` left it, but for the clock and the input
  image (Q-3).
- **SC-26** Each scan is `call/4` with `%Scan{now: rt.now, first: state.first}` and the
  copy-in map, so a resource and `scan/2` cannot drift (D1.13 in the inventory;
  `lib/logex/runtime.ex:7-8`). Not reverted alone: every test that cycles depends on it.

### 4.2 The host contract (`spike runtime.ex`)

- **HM-1 †** `get/2` refuses an internal member (`m1.t1.last`): it reads only what a program
  may name (`FbType.public/1`).
- **HM-2 †** `get/2` refuses a whole function block instance (`m1.t1`) and a whole instance
  (`m1`): it returns an integer, never a map.
- **HM-3 †** `cycle/3` refuses an unlocated global as an input: the host write path is
  deferred (org:1251).
- **HM-4 †** and an output point.
- **HM-5 †** It lists every input problem in key order, more than 32 keys included.
- **HM-6 †** It checks each input's value against its point's type, as `call/4` does.
- **HM-7 †** Every function but `start/1` checks its first argument is a runtime, first;
  `cycle/3` then checks `elapsed_ms`, then the inputs (as `call/4` checks program, state,
  scan, inputs, `lib/logex/runtime.ex:69-74`).
- **HM-8** (not reverted alone; `scheduler_test.exs`'s `get/2` test reads each kind) `get/2` reads a global by name, any tag of an instance by `instance.tag`,
  whatever its section, and a public member at any depth by `instance.tag.member…` (Q-7).

### 4.3 The constructor's checks (`spike configuration.ex`, `check/1`)

- **CK-1 †** A global has at most one driver (org:430-431).
- **CK-2 †** Nothing drives an input point (org:428-429).
- **CK-3 †** Every var_input of every instance is connected (decision 7, org:1471-1472).
- **CK-4 †** The two ends of a connection have one type (org:437-438).
- **CK-5 †** Only a var_input or a var_output connects (org:439).
- **CK-6 †** A var_output takes no constant (org:417).
- **CK-7 †** A var_input's constant fits its type.
- **CK-8 †** A var_input has one source.
- **CK-9 †** A task's interval is 1 to 2147483647 ms (org:442-444; Q-11).
- **CK-10 †** A task's priority is 0 to 2147483647 (org:411; Ed 3 makes it unsigned,
  research IEC-5; Q-11).
- **CK-11 †** An input point takes no initial value (org:428).
- **CK-12 †** No two globals share a location (Q-9).
- **CK-13 †** Globals, instances and tasks share one namespace (Q-6).
- **CK-14 †** in which no two names differ only in case, as no two tags may
  (`lib/logex/declarations.ex:451-456`).
- **CK-15 †** A configuration runs at least one instance (IEC, research IEC-5; Q-12).
- **CK-16 †** A location's address field has no leading zero, so a point has one spelling.
- **CK-17 †** A location's device is one name.
- **CK-18 †** An instance's program is one of the configuration's (org:440-441).
- **CK-19 †** An instance's task is one of the configuration's (org:440-441).
- **CK-20 †** No negative number, which no line can say until a negative literal lexes
  (PLAN §5; the rule `Tag.new!/4` applies, `lib/logex/declarations.ex:411-417`).
- **CK-21 †** An element from Elixir brings no line.
- **CK-22 †** A part that is not a list is reported once: an element that names into it is
  not reported again.
- **CK-23 †** A global is a bool or a dint.
- **CK-24 †** An element has only its part's keys.
- **CK-25 †** The configuration's name is shaped like a name.
- **CK-26 †** A var_input a connection names counts as connected, whatever is wrong with the
  other end; the wrong end is reported, not also "not connected".
- **CK-27 †** Every name is one name (`Declarations.name?/1`, the rule for a tag and a
  program name); the table reverts it for a task's name, and `configuration_test.exs`
  pins its message for each kind.
- **CK-28 †** The problems are listed by part, then each part in its order (§5.1).

### 4.4 Growth

- **GR-1 †** A task's instances are found once, at `start/1`, never by a walk per cycle.
- **GR-2 †** Each instance's connections are found once, at `start/1`, never per scan.
- **GR-3 †** The events are built in reverse and reversed once, never appended one scan at
  a time: `++` is charged few reductions, so the instances test compares 16x, not 4x (§10).

## 5. Every message, exact

### 5.1 `Logex.Configuration.new!/1` and `check/1`

`new!/1` raises one `ArgumentError` whose message is every problem, one per line, in this
order: the name; the programs; then each task, global, instance (shape first, then values);
the shared locations; "at least one instance"; the namespace; each connection; and last the
var_inputs left unconnected, each instance in declaration order and its var_inputs in its
program's. `check/1` returns the same as `{line, message}`; a problem with a line is
formatted `line <n>: <message>` (none from Elixir has one). M2-2's reader sorts by line.

The keyword list itself, checked before anything else (one message, raised at once):
```
Logex.Configuration.new!/1 takes a keyword list of name:, programs:, tasks:, globals:, instances: and connections:, got: <inspect>
Logex.Configuration.new!/1 takes a keyword list of name:, programs:, tasks:, globals:, instances: and connections:: `<key>:` is not one of them
Logex.Configuration.new!/1 takes a keyword list of name:, programs:, tasks:, globals:, instances: and connections:: `<key>:` is given twice
```
The name:
```
a configuration needs a name, as in name: "plant"
<inspect> cannot name a configuration: a name is a letter or `_`, then letters, digits or `_`
```
The programs:
```
programs: must be a list of programs from Logex.compile/2, got: <inspect>
programs: <inspect> is not a %Logex.Program{} from Logex.compile/2
a program in a configuration needs a name: compile it with Logex.compile/2
two programs are named `<name>`: a configuration names each program type once
```
A part and its elements (`<part>` is `tasks`, `globals`, `instances` or `connections`;
`<kind>` its element; `<keys>` its keys as `name:, interval: and priority:`):
```
<part>: must be a list, as in [<example>], got: <inspect>
<part>: <inspect> is not a <kind>: a <kind> is a map, as in <example>
a <kind> from Elixir has no line, got: <inspect>
```

## 6. Each new piece of state, across a cycle, a restart and an online edit

CLAUDE.md's "New state in an instance" asks a field of `%Logex.Instance{}` for a check, a

edit's column is what OE-2 inherits; OE-2 is not built here.

| State | `start/1` | `cycle/3` | `restart/2` | OE-2: an edit that adds it / keeps it / removes it |
|---|---|---|---|---|
| `now` | 0 | `+ elapsed_ms` | kept | kept by every switch; never moves backwards |
| a global, not an input point | its initial value, 0 if none | written by each scan's copy-out | its initial value | added: its initial value (the one rule, as `initial_env/1` is for a tag); kept: its value, and a changed initial value reported as decision 29 reports a tag's; removed: pruned at assemble; its `at` changed: refused (org:860-863) |

## 7. How the later items, and OE-2, extend this without rework

### 7.1 M2-2 · the configuration file

- The reader parses each `.lcf` line, with the lexer and parser as they are (readiness §6),
  into the same element maps, `line` set, and the configuration gains `file`. It calls
  `check/1` and turns each `{line, message}` into a located `%Logex.Diagnostic{stage:
  :configure}` (Q-14), sorted by line. The messages are already written in the text's
  terms where they name a value; the examples in §5.1 that show Elixir maps
  (`as in %{name: …}`) are the Elixir path's only, since a text line cannot be a non-map.
- The words of each line are reserved in `.lcf` by M2-2 and M2-3 (org §4.8). The data path
  refuses a global named like a reserved word from the commit that reserves it (Q-13).
- Fix F15 (`:edit` diagnostics carry no file) is M2-2's: the loader knows each program's
  file. M2-1 does not close it.

### 7.2 M2-3 · periodic tasks in text

Nothing in the scheduler changes: the task maps already carry `interval` and `priority`,
and the instance maps `task`. M2-3's Done-when (the §4.4 plant, 100 and 20 runs in one
simulated second) is the same counting as this Done-when's first part, and should say the
same about the clock: cycles at 0, 10, …, 990 (Q-20).

### 7.3 M2-4 · `var_external`

- The scan step gains globals in and out: a private sibling of `call/4`, used only by
  `cycle/3`, that runs the rungs over the instance's env with the instance's
  `var_external`s read from and written to `rt.globals`, so there is still one copy of each
  global (org:886). `call/4`'s contract for a lone program is unchanged; a program with a
  `var_external` running outside a configuration is M2-4's question (inventory Q4.2).
- `check/1` gains: each `var_external` names a global of its type; a program that writes
  one bound to an input point is refused (it needs the program's write set, inventory
  Q4.6); the two-writer warning goes in the `warnings:` field M2-4 adds (inventory C5).
- `get(rt, "m1.estop")` reads the global, since the instance holds no copy.

### 7.4 M2-5 · function blocks

`get/2`'s member walk (`spike runtime.ex`, `member_value/4`) already follows `FbType`
members to any depth and refuses a non-public one, so `get(rt, "m1.s2.run")` works the day
`Logex.FbType` nests a user type. A function block instance is declared `var`, so CK-5
already refuses connecting one.

### 7.5 M2-6 · event tasks

- A task map gains `single:` (a bool global's name) and its `interval` becomes optional;
  `check/1` gains "a task needs `interval` or `single`" (org:442) and "a `single` source is
  a bool global" (org:445-447).
- A task's runtime state gains `last_single`, 0 at `start/1` (so a trigger already 1 fires
  in cycle 1, MatIEC's reading, decision 11) and 0 again at `restart/2` (IEC's R_TRIG note
  on a cold restart, org:563-566).
- `next_due_in/1` does not count an event task: an edge cannot be predicted, and the
  runner cycles when an input changes (inventory Q6.7).
- The order of an event task among tasks of its priority needs a due time: the cycle's
  `now` is the natural one (inventory Q6.4). M2-6's question; the sort key is a tuple, so
  it is one more term.

### 7.6 OE-2

Every item of org §4.9's "What Milestone 2 must keep" (org:873-887), against this design:

| Constraint | Here |
|---|---|
| plain data only: no funs, pids or refs | `%Logex.Runtime{}` holds maps, lists, integers and the configuration; `plan` is data |
| state keyed by name; instances flat by name, never under a task; execution order a list in the configuration | `instances`, `tasks` and `globals` are maps by name; a task's instances are a list derived from `config.instances` |
| each item's rule for a new piece of state, shared by `start/1` and an edit | §6's table |
| one checked constructor, which the `.lcf` parser feeds | `check/1`, returning `{line, message}` |
| `start/1` builds each instance through `Runtime.instance/1` | SC-19, pinned |
| `%Logex.Runtime{}` opaque, its configuration changed only through the API | `@opaque`; `start/1` re-checks |
| one copy of each global | `globals`, the input image included |
| events an open set | documented in `cycle/3`'s doc and the moduledoc |

OE-2 also needs to compare two configurations by name: an instance's task (a move is
refused), a global's `at` (a change is refused), a task's interval and priority (allowed).
Each is a field of a map keyed by name here. The generation counter OE-2 needs to detect a
stale edit (org:981) is a field it adds to the opaque struct; M2-1 does not reserve it,
since a field nothing reads is a rule no test can pin.

## 11. Open questions for the maintainer

Each gives the options, what each costs, and a recommendation. "Before" says which commit
needs the answer.

**Q-1 · Which §4.4 checks land with M2-1.** *Before commit 2.*
- (a) Every check M2-1's data can express (one driver, input points, every var_input
  connected, types at both ends, only var_input/var_output, unknown names): this design.
- (b) Only the checks the scheduler needs to run safely (names resolve, types agree), the
  rest with M2-2 as org §6.2 lists them (org:1377).
- *Consequence of (b):* between M2-1 and M2-2 the data API accepts a configuration the text
  will refuse, against "the data API refuses what the text cannot say" (org:779-780), and
  M2-2 then tightens it, which breaks Elixir-built configurations ("tightening it later
  breaks plants", decision 7's own reason).
- *Recommend (a).* It is a departure in timing from org §6.2 (DEP-1), not in substance.

**Q-2 · How a host reads the overlap counts.** *Before commit 3.*
- (a) `overlaps/1 :: %{task => count}`, a new public function (this design).
- (b) Stored, readable only through the events (sum them).
- (c) Not stored (another track's choice): the events carry each increment.
- (d) Through `get/2`, as `"fast.overlaps"`: a task attribute as an access path, which IEC's
  access paths do not have, and a new member word that owes a naming stanza.
- *Consequence:* org:596 says the task "adds `missed` … to its overlap count", so (c)
  departs from it; (b) keeps state no test can pin by value; (a) adds one function to
  org §4.6's list.
- *Recommend (a)*, small and pinned: the walk checks it against the oracle's sum.

**Q-3 · Restarting a configuration.** *Before commit 4.*
- (a) `restart(rt, :cold | :warm)` in M2-1: the resource as `start/1` left it, but for the
  clock and the input image (this design).
- (b) No configuration restart; a host calls `start/1` again, which loses the input image
  (the host must resend every input) and sets `now` to 0.
- (c) Defer to the runner.
- *Consequence:* decision 14's watchdog requires "an explicit restart" (org:1493-1495), and
  CLAUDE.md asks a rule for a restart of every new piece of state. (b) makes the input
  image the host's duty to rebuild, and a fresh `now` of 0 is harmless only because every
  instance starts fresh too.
- *Recommend (a)*; its one-sentence rule is what §6's restart column states.

**Q-4 · `next_due_in/1` with task-less instances** (inventory C13). *Before commit 3.*
- (a) Not counted: the time to the soonest periodic task, `:infinity` with none; the runner
  paces task-less instances (this design).
- (b) Counted: 0 whenever a task-less instance exists, so a runner that sleeps on it
  busy-loops, IEC rule 4 taken literally.
- *Consequence:* (b) burns a core and makes `next_due_in/1` useless in the common case of a
  continuous program; (a) leaves the pace to the runner, which org:661 already says ("The
  runner paces cycles").
- *Recommend (a).*

**Q-5 · The first cycle's overlap** (inventory C14). *Before commit 3.*
- (a) Keep the decided rule: anchored at start, every task due at 0, so a first cycle a
  whole interval later reports the period it missed (this design).
- (b) Anchor each task at the first cycle, so a first cycle never overlaps.
- (c) Require the first cycle at `elapsed_ms` 0.
- *Consequence:* under (a) the report is true: the task fell due at 0 and ran at 10, with
  the run due at 10 coalesced into it. A runner that sleeps on `next_due_in/1` (0 after
  `start/1`) never sees it. (b) makes `start/1` and the first cycle two anchors, and
  `restart/2` a third case; (c) adds a host mistake for no gain.
- *Recommend (a)*, and say it in the Done-when and the moduledoc (done in the spike).

**Q-6 · One namespace** (inventory Q1.5, Q2.11). *Before commit 2.*
- (a) Globals, instances and tasks share one namespace, case-only twins refused; program
  types their own (this design: `program motor motor` is fine).
- (b) A namespace per kind.
- *Consequence:* under (b) `get(rt, "m1")` and a connection's other end must say which kind
  they mean; M2-6's `single <g>` and M2-4's `var_external` read a name in a position where
  only a global makes sense, so (b) costs nothing there, but a diagnostic naming `fast`
  could mean a task or a global. (a) can relax to (b) later without breaking anything.
- *Recommend (a).*

**Q-7 · `get/2`'s reach** (inventory Q1.19). *Before commit 4.*
- (a) A global; any tag of an instance, `var`s included; public members at any depth;
  never an internal member or a whole instance; an unknown path raises (this design).
- (b) Only var_inputs, var_outputs and public members.
- (c) Return `{:ok, value} | :error` instead of raising.
- *Consequence:* org's own receipt reads `m1.fault`, a `var` (org:699-704), and the README
  reads `state.env["fault"]` today; (b) loses that for monitoring. (c) breaks the house
  rule that a host mistake raises.
- *Recommend (a).* VAR_ACCESS stays deferred (org:1251); this is a read.

**Q-8 · Inputs to an unlocated global.** Decided against (org:1251, "if wanted"); HM-3 pins
the refusal. No question unless the maintainer wants the write path now.

**Q-9 · The location grammar in M2-1's data** (inventory Q2.9). *Before commit 2.*
- (a) `<device>.<i|q>.<field>[.<field>…]`: the device one name, `i` or `q` lowercase, one
  or more whole-number fields without a leading zero; no two globals at one location
  (this design).
- (b) A dotted device (`rack1.slot2.i.0`).
- (c) Exactly one field.
- *Consequence:* (a) is IEC's hierarchical address with a symbolic root (org:496-503), one
  spelling per point; it lexes as one name today (readiness §6). Widening later breaks
  nothing.
- *Recommend (a).*

**Q-10 · An initial value on an output point.** *Before commit 2.*
- (a) Allowed (this design): a safe value until something drives it, such as a setpoint.
- (b) Refused, as on an input point.
- *Consequence:* org §4.4's line table shows no initial with `at` (org:414), and its check
  names only input points (org:428). Under (a) M2-2 must choose where the value goes on the
  line (inventory Q2.10).
- *Recommend (a)*, M2-2 to place it.

**Q-11 · Ranges for interval and priority.** *Before commit 2.*
- (a) Interval 1 to 2147483647 ms, priority 0 to 2147483647: every configuration integer a
  dint (this design).
- (b) No upper bound.
- (c) A priority range like CODESYS's 0..31 (research CDS-1).
- *Recommend (a)*; widening later breaks nothing.

**Q-12 · A configuration with no instance.** *Before commit 2.* IEC requires a program
(research IEC-5). *Recommend refusing it* (CK-15); relaxing later breaks nothing.

**Q-13 · Reserved words in the data path.** *Before commit 2.*
- (a) None in M2-1: each item that reserves a `.lcf` word refuses it as a name in the data
  path in the same commit, naming what it breaks (this design).
- (b) Every word org §4.8 lists, now.
- *Consequence:* (b) reserves words whose `docs/naming.md` stanzas do not exist yet and may
  change a spelling (org:11-13); (a) can break an Elixir-built configuration that names a
  global `task` between M2-1 and M2-3.
- *Recommend (a).*

**Q-14 · The diagnostic stage for a configuration problem** (inventory Q0.1). *Before
M2-2.* `:configure`, a new value of `Logex.Diagnostic`'s `stage` (recommended), or
`:validate`. M2-1 produces no diagnostic, so it needs no answer to land.

**Q-15 · Elements as maps.** *Before commit 2.* Plain maps (this design), structs per kind
(four public modules), or line-shaped tuples. *Recommend maps*: `check/1` names a missing

**Q-16 · `new!/1`'s error mode** (inventory Q1.6). *Before commit 2.* Every problem in one

**Q-17 · `start/1` re-checks.** *Before commit 3.* Yes (this design), so that a configuration

**Q-21 · A task's phase when OE-2 changes its interval.** *Before OE-2; stated now because

## 12. Departures from decided rules

- **DEP-1 · The §4.4 checks land with M2-1, not M2-2.** Decided: org §6.2 lists "The §4.4
  checks" under M2-2 (org:1377), and org §4.1 stages globals and connections at M2-2
  (org:203-204). Argued in Q-1: M2-1's copy-in needs globals and connections as data, and
  a data API that accepts what M2-2's text refuses breaks the rule that it refuses what the
  text cannot say (org:779-780).
- **DEP-2 · Two functions beyond org §4.6's API list** (org:667-680): `overlaps/1` (Q-2) and
  `restart/2` (Q-3). An extension, not a contradiction; the list does not say it is closed.
- **DEP-3 · `new!/1` raises every problem, not the first.** Decided: org:474-475, "A
  constructor built from Elixir data runs the same checks, as `Tag.new!/4` does for M1-3",
  and `Tag.new!/4` raises the first (`lib/logex/declarations.ex:140-141`). Argued in Q-16.
  The checks are the same; the error mode differs.
- **DEP-4 · CLAUDE.md's "New state in an instance" extended.** It speaks of a field of
  `%Logex.Instance{}` and a rule for a scan, `restart/3` and a switch. M2-1's state is in
  `%Logex.Runtime{}`, so §6 gives each piece a rule for `start/1`, `cycle/3`, `restart/2`
  and OE-2's switch, and commit 7 says so in CLAUDE.md.

Not departures, though they settle tensions the inventory found: the first cycle's overlap
(C14, Q-5) keeps the decided anchoring; `next_due_in/1` ignoring task-less instances (C13,
Q-4) follows org:661.

## 13. Risks

- **A shared misreading of the run order.** The oracle restates priority, due time and
  declaration; a design misreading would land in both. Each key has a worked test in
  `scheduler_test.exs`, and the Done-when's chain of three instances shows the order by its
  effect, not by the events alone.
- **Growth tests are nearly blind to a cheap append.** GR-3 (§10): an events list built with
  `++` per scan grew 4.39x for 4x the instances, inside the bound; only a 16x step sees it.
  A new list built by appending inside a cycle needs the same 16x step, or it passes.
- **`call/4` re-checks on every scan.** Readiness §1.6 measured 34 reductions of 277 for the
  program and state checks and about 19 per input. A configuration checked once at `start/1`
  pays this every scan, about 12% plus the copy-in. Kept: an unchecked second entry would
  be a second evaluator path, against B5. Unverified as a wall-time cost.
- **The opaque struct is inspectable.** `inspect(rt)` prints every field; a host that
  pattern-matches it is outside the contract, and nothing stops it.
- **`restart/2` beside `restart/3`.** One name, two arities, two meanings (a resource, an
  instance). A host that passes a program as the first argument of `restart/2` gets
  "expected a %Logex.Runtime{} from Logex.Runtime.start/1", which names the right thing.
- **Fix F15 stays open** through M2-1: no program carries its file. M2-2 must close it.
- **Map order.** Every order the API produces comes from a list or a sort; two tests use
  more than 32 keys. A new order added later without a sort would pass every small test.
- **The suite's time.** The two walks and the 16x growth test take the suite from 6.2 s to
  8.4 s on this machine (async), measured once; unverified elsewhere.
