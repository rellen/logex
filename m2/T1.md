## 0. Summary

- **The text.** A configuration file is read by its own hand-written recursive descent over
  `Logex.Lexer`'s tokens (`Logex.Configuration.Text`, spike). The lexer is reused whole;
  `Logex.Parser` is not used, so the `.ld` grammar, the golden record and
  `printer_test.exs`'s `@required_shapes` do not change. A line-shape mistake is located at
  its token, with a column. The text reads into plain data: a list of `{kind, line, fields}`
  entries, the shape of the parse AST's leaves (§4.1).
- **One constructor.** Every meaning is checked once, by `check/3`, which both the text
  and Elixir entries reach (§4.2). The spike's `Logex.Configuration` stands in for track S's
  constructor and states the contract T needs from it (§4.3).
- **The spike's done-when passes**: §4.4's `plant.lcf` reads into 40 entries
  (`test/logex/configuration_test.exs`, spike, "reads §4.4's plant into plain data"), loads
  from disk with `motor.ld` and `snapshot.ld` beside it, and a broken source gives exactly
  the receipt's seven diagnostics, one on each of lines 7, 9, 11, 12, 14, 15 and 16 (§7.8).
- **`Logex.compile_file/1` takes only `.ld`** (PLAN M2-2, decided 2026-09-30); its
  `seal.txt` and no-extension assertions flip (`test/logex_test.exs:270-279`).
- **`var_external` in `.ld`** is a row of `@sections` with three rules: no initial value
  (Ed 2 p.43), no instance, and no name a configuration file reserves (org §4.8).
- **Nine stanzas** are appended to `docs/naming.md` in the spike (`program var_global at
  task interval priority with single var_external`), and `naming_test.exs` gains a third
  test that reads the configuration file's keyword table.
- **Recommendations that need the maintainer** (§16): the extension `.lxcf` (T1-Q1); the
  token reader (T1-Q2); a `:configure` stage (T1-Q3); lines in any order (T1-Q4); one
  namespace for tasks, globals and instances (T1-Q5); a type's `var_external` mistakes
  cited once, at its first instance's `program` line (T1-Q6); how a scan reaches a global
  (T1-Q10, recommend leaving `call/4` as it is); and the two-writer warning on the
  configuration's own `warnings` (T1-Q12, a reading of org §4.4 that may be a departure).

## 2. The extension (org §7 decision 3: "choose it before M2-2")

`.lcf` is taken: CodeWarrior's linker requires it (*"Linker command files must end in
.lcf"*, NXP CWPABTR p.44), and CudaText, Loon and Archicad use it too; GitHub holds 5,264
`.lcf` files (res EXT-1..6). logex's own `.ld` is already GNU's linker-script extension
(res EXT-7). Five candidates were free on every registry checked (res EXT-8).

| Option | Reads as | Consequence |
|---|---|---|
| **`.lxcf`** (recommended) | "logex configuration file" | No reading but logex's. Zero GitHub hits, absent from fileinfo, filext, file-extension.info and Linguist (res EXT-8). Avoids the linker association that disqualified `.lcf`. |
| `.ldcfg` | "ld configuration" | Pairs visibly with `.ld`. But "ld" is the GNU linker's name and `.ld` already reads as a linker script, so `plant.ldcfg` reads as "linker configuration" to the embedded audience: the clash that ruled out `.lcf`, by construction. Near `ldconfig`. |
| `.ldcf` | the same, four letters | As `.ldcfg`. |
| `.lcf` (keep) | — | Four other tools' file; a rename later is a migration (decision 3). |

The spike uses `.lxcf`, held once in `Logex.Configuration`'s `@extension` (spike,
`lib/logex/configuration.ex`), with `extension/0` public so `Logex.compile_file/1` can point
a configuration's file to the loader. Changing the choice before M2-2 lands is one line
and the test strings that name it.

## 3. The API

### 3.1 `Logex.Configuration.Text` (new; T's)

```elixir
Logex.Configuration.Text.keywords() :: [String.t()]          # the ten words, lowercase
Logex.Configuration.Text.keyword?(word) :: boolean           # in any case
Logex.Configuration.Text.read(source) ::
  {:ok, [entry]} | {:error, [%Logex.Diagnostic{}], [entry | declared]}
Logex.Configuration.Text.print([entry]) :: String.t()        # canonical text, one line an entry
```

- `read/1` gives one diagnostic for each line that cannot be read, at its token, with a
  column (`stage: :configure`), in line order; a lex error stops it and is the only one
  (`stage: :lex`). With an error it also gives the entries it could read and, for a broken
  line whose name it could read, `{:declared, line, %{kind:, name:}}`, or for a broken
  connection `{:declared, line, %{kind: :connection, instance:, member:}}`, so the checks
  never report that name again (one mistake, one message).
- `print/1` writes lowercase keywords, one space between words, no indentation and no
  comments; `read/1` reads it back as the same entries, each at the line it was printed on.

### 3.2 `Logex.Configuration` (S's; the spike's stand-in)

```elixir
Logex.Configuration.compile(name, source, programs) :: {:ok, %Logex.Configuration{}} | {:error, [diagnostic]}
Logex.Configuration.check(name, entries, programs)  :: {:ok, %Logex.Configuration{}} | {:error, [diagnostic]}
Logex.Configuration.compile_file(path)              :: {:ok, %Logex.Configuration{}} | {:error, [diagnostic]}
Logex.Configuration.extension() :: ".lxcf"
```

- `compile/3` is org §4.4's pure seam, in its decided argument order (T1-Q19): `name` a
  string shaped like a program's name; `source` a binary; `programs` a map from each type
  name to the `%Logex.Program{}` whose `name` is that key. It does no file I/O.
- `check/3` is the one checked constructor's core: the entries `read/1` gives, or the same
  entries built in Elixir with `line: nil`. An entry no line could say raises
  `ArgumentError` (§7.1). A problem the text could also have is a diagnostic; one about an
  entry with no line has `line: nil` and sorts after those with one. The Elixir face that
  raises every problem in one `ArgumentError`, as `Tag.new!/4` raises its first and
  `Runtime.merge!` raises all, is S's to add on top (§4.3, C4).
- `compile_file/1` is the loader: the path must end in `.lxcf`; the configuration is named
  for the basename less `.lxcf`; each type a `program` line names is compiled once, with
  `Logex.compile_file/1`, from `<type>.ld` in the same directory, in the order of the line
  that first names it. Every diagnostic and warning carries its file. The configuration's
  own diagnostics come first, in line order; then each type file's, in that order.
- `%Logex.Configuration{name, tasks, globals, instances, connections, programs, warnings}`
  in the spike: each list in declaration order, each element a map with its `:line`;
  `connections` resolved to `%{instance, member, direction: :input | :output, to, line}`;
  `programs` the map given; `warnings` `%Logex.Diagnostic{severity: :warning}`, in line
  order. S owns the final fields; §4.3 lists what T needs of them.

### 3.3 Changes to existing modules

- `Logex.compile_file/1`: a path whose extension is not exactly `.ld` is a `:file`
  diagnostic with `file: path` and `line: nil`, and the file is not read (spike,
  `lib/logex.ex`; messages F6–F8, §7.2).
- `Logex.Declarations`: `"var_external" => :var_external` in `@sections`; `check/1` gains
  `shared/1` (a var_external's name may not be a configuration keyword), an `initial/1`
  clause (no initial value), and `:var_external` in `instance/1`'s guard (spike,
  `lib/logex/declarations.ex`).
- `Logex.Tag`: `section` gains `:var_external` (typespec).
- `Logex.Diagnostic`: `stage` gains `:configure`; `line` may be nil for a `:configure`
  problem of an entry from Elixir or of the whole configuration (moduledoc and `@type`).
- `Logex.Runtime`: unchanged. A `var_external` in a lone instance is a tag that starts at
  0 by `Program.initial_env/1`, and `call/4` refuses it as an input with its existing
  message (T1-Q10, option G2).

The public surface test (`test/logex/runtime_test.exs:688-735`) pins both new modules in
the spike: `Logex.Configuration` `[__struct__/0,1, check/3, compile/3, compile_file/1,
extension/0]` and `Logex.Configuration.Text` `[keyword?/1, keywords/0, print/1, read/1]`.

## 4. The data shapes, and the contract with S

### 4.1 Entries: what the text reads into

```elixir
{:task,       line, %{name: name, single: nil | global, interval: nil | ms, priority: nil | p}}
{:global,     line, %{name: name, type: :bool | :dint, initial: nil | n, at: nil | location}}
{:program,    line, %{name: name, type: type, task: nil | task}}
{:connection, line, %{instance: name, member: member, to: {:global, name} | {:constant, n}}}
```

- `line` is a positive integer from text and `nil` from Elixir; every other field is
  plain data. A `location` is the string as written, `"panel.q.0"`, and is parsed by the
  checks, so the text and Elixir meet one rule for it.
- `member` is the text after the first `.`: `m1.t1.pre` is `instance: "m1", member:
  "t1.pre"`, refused by the checks as too deep.
- A missing `priority`, or a task with neither `interval` nor `single`, reads as `nil`: the
  grammar allows it, and the checks refuse it with one message from both paths.
- The plant of org §4.4 reads into 3 tasks, 16 globals, 3 programs and 18 connections in
  line order (the done-when test asserts the whole list).

### 4.2 The checked configuration

As §3.2. Execution order is the list `instances` (D1.19). Everything is keyed by name and
plain data (D7.1, D7.2). The spike adds nothing to `%Logex.Instance{}` or `%Logex.Scan{}`.

### 4.3 What T needs from S's one checked constructor (contract)

- **C1. Entries in, by kind and line.** The constructor takes the four entry kinds above,
  or S's own structs built one to one from them, each with an optional line, and the
  compiled programs by type name. The text path passes `read/1`'s entries unchanged.
- **C2. Every check of §6 R10–R46 runs there, once, with §7.4's messages**, so text and
  Elixir data get the same rules (org §4.4 "Loading"; D7.4). Reading (§6 R1–R9) stays in
  `Text`.
- **C3. Problems come back as `{line | nil, message}`** (the spike: diagnostics with
  `stage: :configure`), so the text path makes located diagnostics and the Elixir path a
  raise. Diagnostics with a line come in line order; those without, after, in the order the
  checks find them.
- **C4. The Elixir face raises one `ArgumentError` with every problem**, a line each, in
  that order, as `Runtime.merge!` does for inputs (`lib/logex/runtime.ex:270-289`);
  entries no text could say raise at once, with §7.1's messages.
- **C5. A placeholder for a broken line.** The constructor accepts, from the text path
  only, `{:declared, line, …}` stand-ins (§3.1): their names enter the namespace unchecked,
  nothing that names them is checked further, and a declared connection counts its
  var_input as connected. The Elixir face refuses them (§7.1).
- **C6. A type known to have failed.** The loader passes the set of types whose files did
  not compile; an instance of one is declared, and nothing about it is checked, so a type's
  own mistakes are not echoed as "unknown program type".
- **C7. Fields T reads back:** a global's `location` (device, `:i` or `:q`, address),
  `initial` and `line`; an instance's `type`, `task` and `line`; a connection's direction
  and source or sink; the configuration's `warnings` (§6 W1–W6).
- **C8. One copy of each global** in `%Logex.Runtime{}`, and no `var_external` held in an
  instance's env between scans (§10.3).

## 5. The grammar of a configuration file

```
file        -> line*                      the lexer drops blank lines and comments
line        -> task | global | program | connection
task        -> 'task' NAME ['single' NAME] ['interval' INT] 'priority' INT
global      -> 'var_global' NAME TYPE [INT] ['at' NAME]
program     -> 'program' NAME NAME ['with' NAME]
connection  -> PATH (NAME | INT)          PATH: a name with `.` parts, as `m1.start`
TYPE        -> 'bool' | 'dint'
```

- **Tokens.** `Logex.Lexer.tokenize/1` unchanged (`lib/logex/lexer.ex`): `{:name, {l, c},
  word}`, `{:int_lit, {l, c}, n}`, and `rnd` between lines; a run of newlines and blank
  lines is one `rnd` (`lexer.ex:92-96`); `//` comments and whitespace are never emitted, so
  indentation is cosmetic (org §4.4). The `.` rule makes `panel.q.0` and `m1.start` one
  name (`lexer.ex:121-138`). `%` is an illegal character, so `at %ix0.0` is a lex error at
  its column (decision 6's fallback is not taken).
- **Lines.** The reader cuts the token list at each `rnd`; a line is never empty. A line
  holding `(`, `|` or `)` is refused at that token.
- **Recursive descent.** `line/1` reads `line` by its first token; `task/3`, `inputs/3` and
  `value/5` read `task`; `global/3`, `typed/4`, `initial/3`, `located/4` read `global`;
  `program/3`, `typed_program/4`, `scheduled/4` read `program`; `connection/4` reads
  `connection` (spike, `lib/logex/configuration/text.ex`). Each decision is made on the
  next token alone, as `Logex.Parser`'s.
- **Keywords** are matched in any case; names keep their case. A task's inputs come in
  IEC's order, `single`, `interval`, `priority` (Ed 2 Annex B.1.7 `task_initialization`),
  each once.
- **What the reader decides and what it does not.** The reader checks token kinds and
  positions only. A keyword in a name's place reads as a name (`task with interval 10
  priority 1` is a task named `with`) and the checks refuse it, except where the keyword
  is the next part of the same line, which reads as a missing name (`task interval 10
  priority 1`: "`task` needs a name before `interval`").
- **Line order is free.** Names resolve over the whole file (T1-Q4), as §4.4's own plant
  requires: `task trip single estop priority 0` (line 4) names `estop` before its
  `var_global` (line 6).
- **Why not `Logex.Parser`.** It reads a configuration line too (inv §12 probe 1), but it
  keeps no column, a line of `( )` keeps no line at all (`parser.ex:269-282`), and it
  accepts groups the configuration must then refuse element by element. The token reader is
  about 500 lines with its messages and changes nothing in the `.ld` front end (T1-Q2).

## 6. The rules, numbered

Each rule names its source (decided where, or IEC's, or this design's), the test that pins
it in the spike (`configuration_test.exs` unless named), and its mutant in §15.

### File kinds and the loader

- **R1** `Logex.compile_file/1` compiles only a path ending exactly in `.ld`; anything else
  is a `:file` diagnostic and is not read. *(PLAN M2-2, decided 2026-09-30.)* Test:
  `logex_test.exs` "only a .ld file is a program's…". M1, M44.
- **R2** The loader takes only a path ending in `.lxcf`; a `.ld` path is pointed to
  `Logex.compile_file/1`. *(This design.)* Test: "takes only a configuration's file…". M32.
- **R3** The loader resolves type `t` to `t.ld` in the configuration's directory and
  compiles each type once, in the order of its first `program` line. *(org §4.4 Loading.)*
  Test: "loads the plant from disk…".
- **R4** A type with no readable file is a `:file` diagnostic at the `program` line that
  first names it, in the configuration file. *(This design.)* Test: "a type with no file…".
  M39.
- **R5** A type file's own diagnostics come after the configuration's, each with its file;
  that type's instances are not checked further (C6). Test: "a type's own mistakes…".
- **R6** A configuration's name is its basename less `.lxcf`, shaped like a program's
  name; a bad one is a `:file` diagnostic, and the source is still checked. Test: "a file
  that cannot be read, or whose name…".

### Reading (`Text`, line and column)

- **R7** A line starts with `task`, `var_global` or `program`, or is a connection (a first
  word with a `.`); anything else is "unknown configuration line", with a did-you-mean among

- **R8** A keyword that belongs on a line cannot start one, and the message names the line
  it belongs on. Test: "a keyword that belongs on a line…".
- **R9** `(`, `|` and `)` are refused at their token. Test: "a branch delimiter…". M5.
- **R10** Keywords in any case, names case-sensitive. Test: "keywords are matched in any
  case…". M31.
- **R11** A task's inputs come in IEC's order, each once; a value of the wrong kind is
  located at that value, a missing one at the word that wants it. *(IEC Annex B.1.7 order;
  "once" and the location rule this design's.)* Test: "a task line…". M6, M7, M41.
- **R12** The shapes of a global, a program and a connection line (§5), one mistake a line,
  the rest of the line skipped. Tests: "a global line…", "a program line…", "a connection

- **R13** A broken line still declares its name, and a broken connection still connects
  its var_input (C5). Tests: "a broken line's name is declared…", "a broken connection

## 10. Run-time semantics these items owe the scheduler

T's half of the contract with S. Not spiked: there is no runtime in this track.

### 10.1 Points and the images (M2-2)

- **Input image.** Keyed by input-point name (the global's name), persistent, merged each
  cycle (D1.7 step 2), every point 0 at `start/1`. A key that is not an input point raises
  (§7.7). At step 2 each input point's global takes the image's value.
- **Output image.** Every output point, every cycle, by name, after every due scan (D1.7
  step 5), on a cycle with no due task too: the whole image, as OpenPLC's
  `updateBuffersOut` writes it (res OPL-1). Unlocated globals are not in it (C26; read them
  with `get/2`).
- **Copy-in and copy-out.** Before each scan, each var_input from its global or constant;
  after it, each var_output to every sink (org §4.6 step 4). With `call/4` that is the
  inputs map; `call/4`'s checks pass it, since the constructor checked every connection.

### 10.2 Periodic tasks (M2-3)

As org §4.6, decided. Two points from this design: a task with no instance (W3) keeps its
schedule and emits nothing; and C14's spurious overlap on a first cycle whose elapsed time
spans an interval is S's to settle (inv Q1.16).

### 10.3 One copy of each global, and how a scan reaches it (M2-4)

Recommended (T1-Q10, G2): `call/4` stays as M1-5 left it. In a runtime, before each scan of
an instance whose type declares `var_external`s, the scheduler (private, in
`Logex.Runtime`) merges each one's global into the instance's env, calls `call/4`, reads
each back from the returned env into the global, and drops them from the env. So between
scans no instance holds a copy (D4.8), visibility follows execution order (D1.8), and
`call/4` is still the scheduler's step (D1.13). `start/1` builds each instance with
`instance/1` (F14) and then drops its `var_external`s. A lone instance keeps a
`var_external` as its own tag at 0, which the host cannot set (R46); to drive it, a host
builds a one-instance configuration.

### 10.4 Event tasks (M2-6)

- **Sampling.** Each `single` is sampled once per cycle, after the input image is merged
  and before due tasks are worked out (step 3). Due on an edge: last sample 0, this sample
  1. The last sample starts at 0, so a trigger already 1 in cycle 1 fires (decision 11).
- **Ordering.** An event task's due time is the cycle's `now`, for the earlier-due-time
  tie-break among equal priorities (D1.7 rule 3a).
- **Overlap.** A task with `single` alone never overlaps.
- **`single` with `interval`** (IEC rule 2; no free-software precedent, res MAT-2),
  recommended (T1-Q14): one run per cycle at most; due on an edge, or when this sample is 0
  and its periodic `next_due` has come; the phase stays anchored at start; while the sample
  is 1, a periodic due time that comes is skipped, `next_due` moves past `now` and no
  overlap is counted; when the sample falls to 0 the task is next due at its next phase
  point; an edge run does not move the phase.
- **`next_due_in/1`.** Event tasks are not predictable; it answers for periodic tasks, and
  a runner that reads inputs cycles on any input change (S's).

## 12. How the later items and OE-2 extend it

- **M2-5 (track F).** A function block file is a `.ld` whose first line is `function_block
  <name>`. The loader does not resolve block types itself: it compiles each program type
  with `Logex.compile_file/1`, which resolves `seal` to `seal.ld` beside the program (F's

- **`var_config`** (target, org §5): a fifth line kind, `var_config m2.speed_sp 900`, and an
  eleventh keyword; refused on a var_input (org §4.4).
- **The `%` fallback** (decision 6): a `%` lexeme valid after `at` only; it changes the
  lexer and the golden record, which the `panel.q.0` form does not.
- **Forcing** (target): a force map applied between step 2 and step 5 of `cycle/3`

## 16. Open questions for the maintainer

Each departs from nothing decided unless it says so (§17 lists those).

**T1-Q1 · The extension** (M2-2; decision 3). Options: `.lxcf` — no other reading, zero hits;
`.ldcfg` or `.ldcf` — pairs with `.ld`, but "ld" reads as the linker, the clash that ruled
out `.lcf`; keep `.lcf` — four other tools' file. *Recommend `.lxcf`.* Decide before M2-2's
first code commit.

**T1-Q2 · How a configuration file is read** (M2-2). Options: a recursive descent over
`Logex.Lexer`'s tokens (spiked) — columns on line-shape mistakes, `( )` refused at its token,
no golden or `@required_shapes` change, about 500 lines; or `Logex.Parser`'s rung tree read
like declaration lines (inv Q2.7) — less code, no column, a `( )` line has no line to cite,
groups refused element by element. *Recommend the token reader*: the brief asks for a
hand-written descent, and a configuration has no rungs. Decide before commit 3.

**T1-Q3 · The stage of a configuration diagnostic** (M2-2; inv Q0.1). Options: a new
`:configure` (spiked); or `:validate` with the file telling them apart. *Recommend
`:configure`*: a stage says which stage found it (`diagnostic.ex:9-17`), and `:validate` is
`instructionize/2`'s. A type file's diagnostics keep their own stages. Decide before commit 4.

**T1-Q4 · Line order** (M2-2, M2-3, M2-6; inv Q3.5, Q2.13). Options: names resolve over the
whole file (spiked); or declare before use, as the receipt's "declare it first". *Recommend
any order*: org §4.4's own plant names `estop` on a task line two lines before its
`var_global`, and IEC's grammar puts globals before tasks, so declare-before-use breaks the
decided example. Decide before commit 4.

**T1-Q5 · One namespace** (M2-1, M2-2; inv Q1.5, Q2.11, Q3.4). Options: tasks, globals and
instances in one namespace, a case-only twin refused (spiked); or one per kind. *Recommend
one*: `get(rt, "m1")` and `single m1` cannot be ambiguous, and the messages can say what a
misused name is (C25). It refuses a task and a global of one name, which no example has.
Program types are outside it (`program motor motor` is allowed, as a tag may share its
program's name). Decide with S before M2-1's constructor.

**T1-Q6 · Where a program type's mistake in a configuration is cited** (M2-4; inv Q4.5,
Q0.2). Options: once a type, at its first instance's `program` line in the configuration
file, naming the `.ld` line in the message (spiked) — every configuration diagnostic is in
the configuration file, and it needs no `file` on `%Logex.Program{}`; at the `.ld`
declaration in the program's file — needs F15's field, and the message must name the
configuration; at every instance — one fix, many messages. *Recommend the first.* F15 is
still owed for `Logex.Edit` (org §7 F15); this does not close it. Decide before commit 14.

**T1-Q7 · An output point's initial value** (M2-2; inv Q2.10). Options: none (spiked; the
§4.4 line table gives none with `at`); allowed, written before `at`. *Recommend none*:
allowing one later breaks nothing. Decide before commit 4.

**T1-Q8 · The location grammar** (M2-2; inv Q2.9). Options: a device of one name part, `i`
or `q` in lowercase, one integer field or more, one global a location (spiked); a dotted
device; `I`/`Q` in any case; a single field. *Recommend the spiked form*: org §4.5 says
"integer fields", and each relaxation later breaks nothing. Decide before commit 4.

**T1-Q9 · A task line's order and ranges** (M2-3; inv Q3.1–Q3.3). Options: IEC's order,
each input once, priority and interval 0..2147483647 and 1..2147483647 (spiked); any order;
priority 0..31 (CODESYS's). *Recommend the spiked form*: IEC fixes the order; no IEC range is
quoted (inv U24), and a dint's range is logex's for every other integer. Decide before
commit 10.

**T1-Q10 · How a scan reaches a global** (M2-4; inv Q4.1, Q4.2). Options: **G1** a private
scheduler entry, and a program with a `var_external` refused by `instance/1` — IEC-faithful,
but bars `Logex.Edit` and `scan/2` on such a program; **G2** `call/4` unchanged, the
scheduler merges each global in before the scan and splits it off after, a lone instance
keeping the tag at 0 (spiked, §10.3) — no public change, one copy, D1.13 kept, but a lone
program's `var_external` cannot be driven by its host; **G3** `call/4` takes a
`var_external` as an input and returns it with the outputs — testable alone, but changes
M1-5's pinned host contract (`runtime.ex:303-308`) and `scan/2`'s outputs. *Recommend G2.*
Decide before commit 13.

**T1-Q11 · A global both driven by a connection and written through `var_external`** (M2-4;
inv Q4.7). Options: a warning (spiked, W5); an error. *Recommend a warning*: org §4.4 makes
a write through `var_external` a warning because it is only visible in the IR, and that
reason holds whatever the other writer is. Decide before commit 14.

**T1-Q12 · Where the two-writer warning lives** (M2-4; inv C5). Options: the configuration's
own `warnings` (spiked); "M1-5's `warnings:` channel", read literally as
`%Logex.Program{}.warnings`, which sees one program and cannot see two instances. *Recommend
the configuration's*, reading "channel" as "warnings carried on the compiled value as
`%Diagnostic{severity: :warning}`". If the literal reading was meant, this is a departure
(§17 D1). Decide before commit 14.

**T1-Q13 · "Records which tags it writes"** (M2-4; inv Q4.6, C23). Options: a function over
the IR from B5's one walk (rdy item 3); a `writes` field on `%Logex.Program{}`. *Recommend
the function*: a field on a public struct can be built wrong by hand and must then be
checked. Decide before commit 12.

**T1-Q14 · `single` with `interval`** (M2-6; inv Q6.3). Options: §10.4's rules (phase
anchored at start, periods under a high trigger skipped and not counted, one run a cycle);
re-anchor the phase when the trigger falls; count suspended periods as overlaps. *Recommend
§10.4*: it adds no state and no overlap that is not a miss. There is no precedent to copy
(res MAT-2). Decide before commit 16.

**T1-Q15 · A trigger across a restart and an edit** (M2-6, OE-2; inv Q6.6). Options: restart
resets the last sample to 0, an edit keeps it, and a change of a task's `single` or of its
having an `interval` is refused (recommended, §11); or allow those changes. *Recommend
refusing*: decision 19 allows only interval and priority. Decide before commit 17.

**T1-Q16 · `next_due` when OE-2 changes an interval** (M2-3, OE-2; inv Q3.8). Options:
`min(next_due, now + new)` (recommended); keep `next_due`; re-anchor at the switch (an
early run). *Recommend `min`*: a shorter interval takes effect within one new period, a
longer one runs once more on the old phase, and neither adds a run. Decide before OE-2, but
M2-3's documents state it.

**T1-Q17 · Configuration warnings** (M2-2; inv Q2.17, Q3.6, Q0.3). Options: W1–W6 (spiked);
none; fewer. *Recommend W1–W6*: each marks a likely wiring mistake that is not an error,
as `Logex.Warnings` does for a program. Decide before commit 4.

**T1-Q18 · Unconnected var_inputs** (M2-2; inv Q2.14). Options: one diagnostic an instance,
listing them in declaration order, at its `program` line (spiked); one a var_input. *Recommend
one an instance*: one forgotten block of wiring, one message. Decide before commit 4.

**T1-Q19 · `compile/3`'s argument order** (M2-2; inv C15). Options: org §4.4's
`compile(name, source, programs)` (spiked); `compile(source, programs, name: name)`, like
`Logex.compile/2`. *Recommend keeping §4.4's*: it is decided, and a change is cosmetic.
Decide before commit 4.

**T1-Q20 · A printer for the configuration** (M2-2; inv Q0.5, rdy Q12). Options: `print/1`
with a round-trip property (spiked); none until OE-2. *Recommend the printer now*: it is what
holds "the data API refuses what the text cannot say" to a test (R49). Decide before commit 6.

**T1-Q21 · `.ld`'s case** (M2-2; inv Q2.2). Options: exactly `.ld` (spiked; `seal.LD` is
refused); any case. *Recommend exact*: Elixir and mix match `.ex` exactly, and accepting
`.LD` later breaks nothing. Decide before commit 2.

## 19. Risks

- **The lexer's `.` rule carries every location.** PLAN §5 warns `.` is safe only while
  there are no float literals; a float lexeme would split `panel.q.0`. Mitigation: a
  location lexeme valid after `at`, as the `%` fallback would need anyway.
- **Two messages for one mistake by path.** The text resolves type words (T22) and Elixir
  gives atoms (H9), as tags do today (`declarations.ex:293-294` against `:346-347`).
- **Did-you-mean on error paths** is a Jaro pass over a kind's names for each unknown
  reference: O(errors × names), as the `.ld` compiler's (`compiler.ex:801`). R50's growth
  test covers accepted configurations only.
- **"on its line 8"** names a `.ld` line without its file. Clear while a type is named by its
  file (R3); a library of types elsewhere (M2-5) would want F15's `file`.
- **One namespace** refuses a task named like a global; no example does that, but a
  converted plant might.
- **W6 covers only a task with `single` and no `interval`.** A combined task whose trigger
  stays 1 for long times across its events too.
- **Types resolve beside the configuration only.** No search path; a shared block library is
  M2-5's question.
- **The stand-in is not S's code.** C1–C8 are what must survive a merge; the checks'
  structure and messages are T's, their home S's.
- **Case-insensitive filesystems**: `Motor.ld` resolves for `program m1 motor` on macOS, not
  on Linux; the type's name is still `motor`, from the line.
