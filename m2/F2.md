## 0. The answer in one page

- **A block compiles to its type.** `function_block seal` as the first rung (blank lines
  and comments before it are dropped by the lexer). `Logex.compile(source, name: "seal")`
  returns `{:ok, %Logex.FbType{name: "seal", members: […], body: %Logex.Program{}}}`.
  - Its members are its declarations, in line order. A `var_input` becomes `:input`, a
    `var_output` becomes `:output`, and a `var` becomes `:local`, a role that is new. Every
    member has `write: false`.
  - `FbType.of/1` builds the type from its body, and that is the definition of a user type:
    `FbType.user?/1` holds exactly when a type is what `of/1` gives for its body.
- **The library.** It reaches the compiler in two ways:
  - `Logex.compile(source, name:, types: [seal])`, the pure seam;
  - `Logex.compile_file/1`, which finds `seal.ld` beside the file that names `seal`,
    compiles it first, once, and detects a cycle of files.

  Within one compile, a name means one version of a block.
- **`cal s1 a b q`.** Its signature comes from the block (`FbType.signature/1`): the
  instance, then the var_inputs as values, then the var_outputs as written tags.
  - Rung power is EN, and ENO is the power out.
  - Energised: the operands are copied in, the body runs over `env["s1"]`, and the outputs
    are copied out.
  - De-energised: nothing happens at all (decision 12).
  - One `cal` runs an instance. `cal t1` on a timer is refused, and so is `cal x` on a bool.
- **The evaluator re-enters a body privately** (B5).
  - The scan gains `tags`, filled by the runtime, so `cal` finds its instance's type.
  - `ons_blocked` becomes a tree. `cal` hands its body the scan narrowed to its instance:
    the body's tag table and the instance's own subtree of blocked bits.
  - `now` and `first` are the program's.
  - This departs from CLAUDE.md:134's "the same for every instruction of one call" (F2-Q1).
- **State is nested by name**, at any depth: `env["o"]["inner"]["run"]`. A block's own
  `var`s are hidden from outside, so from a program no path goes deeper than `s1.run`.
  Nothing outside a user block writes its members.
- **Online edit.** This is where the design goes furthest.
  - A user block's type, for the edit, is its name and the kinds of its members, at any
    depth. Its body is not part of it, nor are member order and roles, nor members added or
    dropped. So an edit may change a block's body and its members.
  - The switch moves each instance's members by path, by OE-1's own rules: start what is
    missing, the first test's starts and fit, `:initial_changed`, the timer rules, and
    prune at assemble. This is the nested migration that org:866 left to M2-5.
  - A member whose kind changes is refused by its path:
    ``line 4: `p.edge` is a bool in the running program and a dint in the candidate: a
    member's type changes only with a restart``.
  - An `ons` inside an instance is a one-shot of the program. Its bit is named by its path,
    `p.edge`, and its "rung" is the chain of stripped rungs from the program's `cal` down to
    the body's rung. Decision 21 then blocks it where any rung on that chain changes.
  - A nested timer meets the timer rules by path. The Resume rule resumes a timer only
    where the stopped program does not run it. That resolves inventory C9: a timer frozen
    by a false `cal` still catches up (decision 8), and one whose `cal` an edit restores
    resumes (decision 23).
- **Growth is linear.** Over 30 runs at 50 and 800 levels of nesting (16x), a scan grows
  15.3x to 15.5x, a compile 12.0x to 12.4x, and accept, test, untest, test and assemble
  16.5x to 16.8x. The scan after a switch grows 16.1x to 16.2x for 16x the nested blocked
  bits. One quadratic step got into the spike, and the growth test found it: the plan built
  every nested block's initial state at every level, which grew about 160x for 16x the
  depth.
- **The gate passes.** Format 0, compile 0, test compile 0, `mix test` 0, with 476 tests (6
  doctests), up from 430. Of those, 45 tests are in the new `test/logex/function_block_test.exs`,
  and one more is in `naming_test.exs`. I reverted 29 rules one at a time, and every revert
  turned the suite red (exit 2, §8).
- **The cost to a program with no blocks.** The README motor's `call/4` goes from 278 to 281
  reductions, and its `compile/2` from 7,111 to 7,301 (min of 200, three runs each,
  identical). A seal through `cal` costs 265 reductions against 151 for the same logic
  inline.

## 1. The API: every signature and return shape

```elixir
# lib/logex.ex
Logex.compile(source, name: name)                        # unchanged
Logex.compile(source, name: name, types: [%Logex.FbType{}])
Logex.compile(source, types: types, name: name)          # either order
  :: {:ok, %Logex.Program{}}          # a program's source
   | {:ok, %Logex.FbType{}}           # a source whose first rung is `function_block <name>`
   | {:error, [%Logex.Diagnostic{}]}  # every mistake, in line order
Logex.compile_file(path)
  :: the same three shapes; a block's type word is looked for as `<word>.ld` beside the file
     that names it, compiled first, once (§3, F2-R44 to F2-R47)

# lib/logex/compiler.ex
Logex.Compiler.instructionize(routine, declared \\ [], types \\ [])
  :: {:ok, %Logex.Program{}} | {:ok, %Logex.FbType{}} | {:error, [%Logex.Diagnostic{}]}
Logex.Compiler.instructions()        # gains "cal" => {:cal, :block}

# lib/logex/fb_type.ex
%Logex.FbType{name:, members:, body: nil | %Logex.Program{}}       # body is new
%Logex.FbType.Member{role: :input | :output | :local | :internal}  # :local is new
Logex.FbType.of(%Logex.Program{}) :: %Logex.FbType{}                # new
Logex.FbType.signature(%Logex.FbType{}) ::
  [{{:instance, name}, nil} | [{{:value | :write, :bool | :dint | FbType.t()}, %Member{}}]]  # new
Logex.FbType.user?(term) :: boolean                                 # new, total
Logex.FbType.public/1, member/2, writable/1, initial/1,2            # unchanged

# lib/logex/scan.ex
%Logex.Scan{now:, first:, ons_blocked: [], tags: nil}               # tags is new, the runtime's

# lib/logex/declarations.ex (not in the pinned surface)
Logex.Declarations.kinds() :: ["function_block"]                    # new, for naming_test
Logex.Declarations.split(rungs, declared \\ [], types \\ %{})       # types is new
```

`Logex.Runtime` and `Logex.Edit` gain no function. `call/4`, `scan/2,3`, `put_inputs/3`,
`restart/3`, `instance/1` and every step of `Logex.Edit` take a program that holds blocks,
with the rules of §3. The pinned surface test (`test/logex/runtime_test.exs:688-735`)
changes in three places:
- `Compiler` gains `instructionize: 3`;
- `FbType` gains `of: 1`, `signature: 1` and `user?: 1`;
- `Scan`'s keys gain `:tags`.

## 2. The data shapes

```elixir
# seal.ld compiled (spike FbType.of/1)
%Logex.FbType{
  name: "seal",
  members: [
    %Member{name: "start", type: :bool, role: :input,  write: false, initial: 0},
    %Member{name: "stop",  type: :bool, role: :input,  write: false, initial: 0},
    %Member{name: "run",   type: :bool, role: :output, write: false, initial: 0}
  ],
  body: %Logex.Program{name: "seal", source: "function_block seal\n…", rungs: […],
                       tags: %{…}, warnings: […]}
}

# a member holding an instance: its initial is the overrides map FbType.initial/2 reads
%Member{name: "t1",    type: Logex.FbType.ton(), role: :local, initial: %{"pre" => 250}}
%Member{name: "inner", type: seal,               role: :local, initial: %{}}

# the IR of `xic en cal s1 a stop k1`: the instance, then one lowered operand per formal
{:rung, [{:xic, 9, [{:name, 9, "en"}]},
         {:cal, 9, [{:name, 9, "s1"}, {:name, 9, "a"}, {:name, 9, "stop"}, {:name, 9, "k1"}]}]}

# an instance's state: one map per instance, at any depth (Program.initial_env/1, unchanged)
env["s1"]                  == %{"start" => 0, "stop" => 0, "run" => 1}
env["o"]["inner"]["run"]   == 1
env["p"]["t1"]             == %{"pre" => 100, "acc" => 30, "dn" => 0, "tt" => 1, "en" => 1, "last" => 30}

# the instance's block list: a bit by its path (still a list of names, F8's check unchanged)
%Logex.Instance{ons_blocked: ["edge", "p1.edge", "o.inner.edge"]}

# what call/4 hands the evaluator, built once a scan; never the host
%Logex.Scan{now: 60, first: false, tags: program.tags,
            ons_blocked: %{"edge" => true, "p1" => %{"edge" => true},
                           "o" => %{"inner" => %{"edge" => true}}}}
# and what `cal p1 …` hands p1's body
%Logex.Scan{now: 60, first: false, tags: pulse.body.tags, ons_blocked: %{"edge" => true}}
```

Inside `Logex.Edit` (private, plain data, built at accept from the two programs alone,
fix F5), each direction's plan gains `nested`, one entry per user-block instance of the
program it starts:

```elixir
{"p", %{names: %{"go" => true, …},          # the members its version of the type declares
        members: [{:leaf, "count", :dint, 7, nil, false},          # name, type, initial, old initial, kept?
                  {:timer, "t1", keys, start, from_preset, to_preset, kept?},
                  {:block, "inner", {type, overrides}, kept?, inner_plan}]}}
```

A plan is built once per type name, for each pair of facts: whether each program runs the
instance. So it is linear in the types and their members, not in the instances. Each fact
of a program gains:
- `blocks`: instance name to `{type, run?}`;
- `bodies`: each block type's stripped `ons` and `cal` rungs, its writes, and the instances
  it runs;
- nested entries in `ons`, keyed by `{instance_path, [stripped rung, …]}`;
- `writes` for the bits under those entries.

## 3. The rules

Each rule names where it is decided, or the question that leaves it open, the test that
pins it, and the revert that proves the test (§8). Tests are in
`test/logex/function_block_test.exs` unless named otherwise.

### A block's file

- **F2-R1 A block's file is the one whose first rung is `function_block <name>`**, any
  case (decision 4). The line is taken off before the declarations, as they are taken off
  before the rungs (spike `Compiler.file_kind/1`). *Test:* "compiles to its type…".
- **F2-R2 It compiles to its type** (`FbType.of/1`):
  - members in declaration order, roles as §0;
  - `write: false` on every member;
  - the body a `%Logex.Program{}` named after the block, with its source and warnings.

  *Open:* F2-Q11. *Test:* "compiles to its type…". *Revert:* M16.
- **F2-R3 Its name must be the name it is compiled under**, and so its file's. This is a
  `:validate` diagnostic at the header line (PLAN:1340-1341, "matching the file name").
  *Test:* "its first line names it…", loader test. *Revert:* M22.
- **F2-R4 Its name is a name, and no reserved word.** `var s1 move` would read a mnemonic
  where a type goes. A program's name stays shape-only (PLAN:951-954), because a program's
  name is never spelled in a body (inventory C18). *Test:* "its first line names it…".
- **F2-R5 `function_block` is reserved in a block's file only** (org:744). A tag of that
  name, in any case, is refused there and allowed in a program. In mnemonic position, in
  any file, it gets a message of its own. *Test:* "function_block is reserved…".
  *Revert:* M26.
- **F2-R6 A block is not a program.** `Runtime.instance/1` and the other entry points
  refuse a `%FbType{}` with their own `expected a %Logex.Program{}` message, unchanged
  (`lib/logex/runtime.ex:163-170`). *Test:* "a block is not a program…".

### The library

- **F2-R7 `types:` is a list of user types, each `FbType.user?/1`, no two of one name.**
  Anything else is a host mistake (§4.1). *Test:* "each must be one Logex.compile/2
  gave…".
- **F2-R8 One version of each name per compile.** This covers every type given, every type
  they hold at any depth, and every type a tag declared from Elixir holds. The edit's plans
  and the runtime look types up by name, so two versions of `seal` in one program would be
  ambiguous. *Test:* "a type holds one version…". *Revert:* M17.
- **F2-R9 A type word names a block only where the compile is given it, by its exact
  name.** The name is not reserved (PLAN:732-734). Without a library the unknown-type
  message is unchanged. With one, it lists the blocks given. *Test:* Done-when
  "…located diagnostic".
- **F2-R10 From Elixir,** `Tag.new!("s1", seal)` declares an instance of a valid user
  type. An initial value on it is refused with the message a declaration line gets, and a
  type `user?/1` refuses gets the unknown-function-block message. The data API refuses what
  the text cannot say (decision 28). *Test:* "from Elixir, an instance…".

### Recursion

- **F2-R11 A block never holds an instance of itself.** In its own file, its own name as a
  type word is refused at the `var` line (Ed 2 §2.5; org:342-344). *Test:* Done-when
  "…located diagnostic". *Revert:* M5.
- **F2-R12 At any depth.** A type given that holds a type of the block's own name, for
  instance one compiled against an older version of it, is refused at the `var` line,
  naming the chain. The chain search visits each type once. *Test:* "a type given that
  holds the block's own name…". *Revert:* M6.
- **F2-R13 Across files,** the loader refuses a cycle, at the line in the file that closes
  it, with that file (F2-R46).

### `cal`, at compile time

- **F2-R14 `cal` is a mnemonic**, reserved in every `.ld` (org:743), with
  `{:cal, :block}` in `@instructions` in place of a signature (F2-Q17). *Test:* "is
  reserved, a mnemonic…".
- **F2-R15 Its first operand is an instance of a user block, named whole.** A ton gets
  "which `ton t1` and its preset run". A bool or dint is "a `cal` of a non-instance". A
  member, a literal, a reserved word or nothing gets a message of its own, and the would-be
  operands after it are passed over: one mistake, one message. *Test:* "runs only an
  instance of a user block…". *Revert:* M24.
- **F2-R16 Its operands are the block's var_inputs, then var_outputs, in declaration
  order** (org:319-329). An arity error names every formal. *Test:* "an arity error…".
- **F2-R17 Each operand is checked against the formal it fills, which the message names.**
  The template is ``operand 2 of `cal s1` is `stop` (var_input bool)`` (org:325-326):
  - a type mismatch;
  - a literal that does not fit an input;
  - a literal where the block writes;
  - a var_input where it writes;
  - a member logic may not write where it writes;
  - an instance named whole.

  Two swapped bools compile (org:327). *Test:* "a type error names the formal…".
- **F2-R18 One `cal` runs an instance,** as one `ton` runs a timer. A second `cal` is an
  error at its line, citing the first (F2-Q9). *Test:* "runs only an instance…".
  *Revert:* M4.
- **F2-R19 Anything may follow a `cal` on its path:** ENO is the power out (org:296-297).
  Only a `ton` ends a path. *Test:* "ENO is the power out…".
- **F2-R20 `ton s1 5000` on a user instance** is the existing `{:instance, "ton"}` refusal,
  and gives the instance no preset (spike `Compiler.run_by/4` matches only a built-in).

### Members from outside

- **F2-R21 A user block's inputs and outputs are read anywhere** an operand of their type
  may go (decision 9; org:328). *Open:* F2-Q5. *Test:* "a block's inputs and outputs are
  read anywhere…".
- **F2-R22 A block's own `var`s are hidden.** From a program, `s1.edge` is "not a member".
  So no path from outside is deeper than one member, and `s1.t1.acc` cannot be named
  (`FbType.public/1`, unchanged code, now `:local` too). *Open:* F2-Q7. *Test:* "a var is
  local…". *Revert:* M15.
- **F2-R23 No member of a user block is written by logic outside it**
  (`FbType.writable/1` is empty). *Open:* F2-Q6. *Test:* "…written by no logic outside
  it". *Revert:* M16.
- **F2-R24 The host sets no member** (unchanged): `put_inputs(p, s, %{"p1.go" => 1})` gets
  ``input `p1.go` names a member of `p1`, a pulse: only a var_input is set from outside``,
  and `p1.edge` "reaches into" (probe `F2-probe/misc.exs`).

### Warnings

- **F2-R25 An instance no `cal` runs is warned about, saying `cal`** (PLAN:1350-1351).
  *Test:* "an instance no cal runs, saying cal". *Revert:* M14.
- **F2-R26 A `cal`'s operands are uses with its block's signature.** A var_output only a
  `cal` drives is driven, and a `cal` output on an `ons` storage bit is warned about as any
  writer is (inventory C10). *Test:* "a cal's outputs are written…". *Revert:* M13.
- **F2-R27 A block's body is warned about as a program is,** in `type.body.warnings`.
  *Test:* "a block's body is warned about…".

### Running a block (`Logex.Runtime`, private)

- **F2-R28 Energised: copy in, run the body over the instance's own map, copy out**
  (org:293-307). *Test:* the Done-when's three seal-ins. *Revert:* M3.
- **F2-R29 De-energised: nothing** (decision 12). No input is copied, the body does not
  run, and no output is written. The instance and its output tags keep their values.
  *Test:* "a false EN freezes only its own instance…". *Revert:* M1.
- **F2-R30 ENO is EN.** The power out is the power in, since a body has no way to clear
  ENO. *Test:* "ENO is the power out…".
- **F2-R31 Blocks nest**, an instance a map inside a map. *Test:* "blocks nest…".
- **F2-R32 A timer inside a frozen block keeps `.en` and `last`, and catches up** when the
  block next runs (decision 8; PLAN:1349-1350). *Test:* "a timer inside a frozen block…".
- **F2-R33 `first` and `now` are the program instance's,** inside a body too. So an `ons`
  in a block frozen on the first scan fires when the block first runs (PLAN:1351-1352;
  research CNV-14 for the conventional family's same consequence). *Test:* "first is the
  program instance's…". *Revert:* M23.
- **F2-R34 The body sees its instance's own blocked bits and its type's tag table**, and
  no other routine's. A program bit `edge` and a block's `edge` never collide (inventory
  Q5.15). *Test:* "an ons in a block's rung the edit changes is blocked by its path…".
  *Revert:* M2.
- **F2-R35 `scan.tags` is the runtime's.** A host that fills it in is refused, as one that
  fills `ons_blocked` in is (OE-1). *Test:* "the scan's tag table is the runtime's".
  *Revert:* M19.
- **F2-R36 Total on what a plain swap leaves.** An instance held as anything but a map runs
  from an empty one (`as_map/1`), and a missing member reads 0. Probe `misc.exs`: a swap
  from `var p1 bool` at 1 runs `pulse` from `%{}`.

### The online edit of a program that holds blocks (`Logex.Edit`)

- **F2-R37 A user block's type is its name and its members' kinds, at any depth.** Its
  body, its members' order and roles, and members added or dropped are not part of its
  type. A member whose kind changes is refused by its path at the instance's line, and a
  block renamed is a type change (org:858-867, as M2-5 brings the nested migration).
  *Open:* F2-Q2. *Tests:* "the block's body is not its type…", "a member whose kind
  changes is refused…". *Revert:* M7.
- **F2-R38 Inside an instance both programs declare, each member moves as a tag does, by
  its path** (the nested migration; §4.9's tables):
  - one the state lacks starts at its initial value;
  - at the first test, one the candidate's version adds, or whose value does not fit,
    starts too (decision 26);
  - a kept one keeps its value.

  Each start is reported `{:added, "p.count", 7}`. *Tests:* "a member the block adds…",
  "at the first test a member whose value does not fit…". *Reverts:* M8, M28.
- **F2-R39 A member only the stopped program's version declares is kept, unused, until
  assemble or cancel prunes it,** reported `{:pruned, "p.old", 4}`. *Test:* "a member the
  block adds…". *Revert:* M9.
- **F2-R40 A kept member whose initial value changed keeps its value, and is reported**
  `{:initial_changed, "p.n", {5, 6}}` (decision 29, by path). *Open:* F2-Q16. *Test:* "a
  kept member whose initial value changed…". *Revert:* M20.
- **F2-R41 An `ons` inside an instance a `cal` runs is a one-shot of the program, its bit
  named by its path.** Its rung is the chain of stripped rungs: from the program's rung
  that `cal`s the outermost instance, down to the body's rung that holds it. Decision 21
  and fix F7 then apply unchanged: it is blocked where any rung on the chain is new or
  changed (a `cal`'s operands included), or where the body writes its bit through anything
  else. It is reported `{:ons_blocked, "p1.edge", 0}`. *Open:* F2-Q3. *Tests:* "an ons in a
  block's rung the edit changes…", "an ons in a block run from a rung the edit changes…".
  *Revert:* M10.
- **F2-R42 An instance the edit adds starts whole, and its one-shots are blocked for the
  switch scan,** as an `ons` the edit adds is (decision 21). *Test:* "an instance the edit
  adds starts whole…".
- **F2-R43 A block left pending by an earlier edit survives a second edit before any
  scan,** by path (fix F2). *Test:* "a nested block an earlier edit left pending…".
  *Revert:* M29.
- **F2-R44 A timer inside a block meets the timer rules by its path.** The `.pre` rules
  (decision 23, fixes F1 and F6), `:dn_drops` and `:dn_rises` apply with the presets of
  the `ton`s in each version of the body, where each program runs the block. *Test:* "a
  timer inside a block meets the preset rules…". *Revert:* M27.
- **F2-R45 Resume only where the stopped program does not run the timer** (decision 23 as
  worded: "A timer T runs and F did not", org:1004). Running it means a `cal` chain down to
  the instance and a `ton` in the body. A timer frozen by a false `cal` that both programs
  run is not resumed, and it catches up (decision 8). One whose `cal` the candidate
  restores is resumed. This resolves inventory C9. *Open:* F2-Q4. *Test:* "a timer in a
  frozen block is not resumed…". *Revert:* M11.
- **F2-R46 An output only a `cal` drove is held** where the candidate drives it no more
  (decision 20, through F2-R26's writes). *Test:* "an output only a cal drove is held…".

## 10. Open questions for the maintainer

**F2-Q1 · How `cal` reaches its body, and the scan convention** (inventory C11; readiness
§1.5; F1-Q12).
- *(a) `%Scan{}` gains `tags`, the routine's tag table, filled by the runtime. A `cal`
  hands its body the scan narrowed to its instance:* the body's tags, and the instance's
  subtree of a tree of blocked bits. This is the spike. Cost: CLAUDE.md:134's "the same
  for every instruction of one call" becomes "of one routine run"; one pinned key; one host
  check.
- *(b) Expand every `cal` at compile time into the body with absolute paths,* so the scan
  never changes. Cost: every operand at depth k walks k maps, so a chain of n blocks scans
  in O(n²). The growth test would fail, and the program's IR would grow with instances,
  not types.
- *(c) A private frame struct as the evaluator's third argument.* Cost: CLAUDE.md's
  convention changes for every clause, not one.

*Recommend (a).* It is the smallest departure that stays linear, and F1 reached the same
shape independently. *Decide before:* step 3.

**F2-Q2 · A block type that changes while running** (inventory C12, C20; org:858-871;
F1-Q2, F1-Q3).
- *(a) Refuse any change to a block type,* members or body. This is F1's recommendation.
  Editing a block's logic then needs a restart, as the conventional family edits its
  user-defined instructions offline only (research CNV-17). OE-2 later reopens
  `Logex.Edit`'s per-instance code for the migration.
- *(b) Allow a body-only change.* Cost: the path-keyed one-shot and timer rules of this
  spike, without the member migration.
- *(c) The full nested migration in M2-5,* as org:866 ("until M2-5 brings the nested
  migration") and PLAN:1491-1493 say. This is the spike. Cost: about 400 lines of
  `lib/logex/edit.ex` (+446 −46, its moduledoc included), 12 tests in the edit's describe

  matches Beremiz's hot swap, "leaves that exist in both trees with the same type are paired

*Recommend (c).* The documents already give it to M2-5, the spike shows it linear and

reduce to F1's FB-38 to FB-41, and PLAN M2-5's scope sentence should say who brings the
migration. *Decide before:* step 4.

**F2-Q3 · Which rungs make a nested one-shot "changed"** (decision 21).
- *(a) The chain:* the program's rung that `cal`s the outermost instance, each body rung
  that `cal`s the next, and the body rung that holds the `ons`. This is the spike. A changed
  EN condition or `cal` operand blocks the one-shots under it.
- *(b) The body rung only.* A change to the calling rung, such as its EN or an input
  operand, leaves the bit to compare against a condition it never saw: a false pulse,
  which decision 21 exists to prevent.
- *(c) Block every one-shot inside every instance at any switch that changes the type.*
  That is cruder, and loses real edges in instances whose chains did not change.

*Recommend (a).* At worst it loses one genuine edge, decision 21's accepted cost.
*Decide before:* step 4.

**F2-Q4 · How the Resume rule tells "the stopped program did not run it"** (inventory C9;
org:1004; F1-Q10).
- *(a) From the two programs' text:* resume only where the stopped program has no `cal`
  chain or no `ton` reaching the timer (the spike, F2-R45). At the top level this changes
  nothing within the contract, since a `ton` stamps `last` at every scan; the whole OE-1
  suite passes unchanged. Inside a block it keeps decision 8's catch-up across a false EN
  and decision 23's resume across an edit.
- *(b) Keep the inference "`last` before `now`".* Then a timer frozen by a false `cal` is
  resumed by any switch, and loses the frozen time that decision 8 chose per-timer `last`
  to keep.

*Recommend (a), and reword org:1004's justification sentence, which (a) makes unnecessary.*
This changes how a decided rule is computed, not what it says (§11, item 3). *Decide
before:* step 4.

*Recommend (a).* It is decided, and a positional `cal` passes every input from a tag the

## 11. Every departure from a decided rule

1. **CLAUDE.md:134, the `evaluate/3` convention:** "The scan is read-only and the same for
   every instruction of one call". In the spike it is the same for every instruction of
   one routine run, and narrowed by `cal` for its body (F2-Q1). The spike's CLAUDE.md line
   says so.
2. **PLAN:1343-1347 and org:1407-1410, the M2-5 acceptance text:** "`m1.s2.run` reads one of
   them". The spike tests it as `s2.run` of the instance named `m1`, before M2-1 exists
   (F2-Q12).
3. **Org:1004 and `lib/logex/edit.ex:84-87,692-695`, the Resume rule's mechanism.** The
   decided rule is "A timer T runs and F did not … resumes". Its stated basis is "Every
   `ton` stamps `last` at every scan, so within the contract a `last` before `now` says F
   did not run it". The spike checks "F did not run it" from F's text instead (F2-Q4).
   Behaviour at the top level is unchanged: the OE-1 suite, with its contract walk, passes
   unmodified.
4. **PLAN:1340-1343, M2-5's scope sentence,** does not list the nested migration, though
   org:866 and PLAN:1491-1493 give it to M2-5. The spike builds it (F2-Q2). This is a scope

5. **CLAUDE.md:146-159, "New instructions, step 2":** "add the mnemonic and its operand

6. **PLAN M1-5's `compile(source, name:)`,** pinned with "takes a name and no other
   option". It gains `types:` (F2-Q10).

No other decided rule moves. Decisions 4, 8, 9, 12, 21, 23, 26 and 29, the reserved-word

## 12. Risks

- **The scan convention.** A later evaluate clause that looks anything up in `scan.tags`
  must use the routine's table, not the program's. CLAUDE.md must state it (§9, step 6).
- **`Logex.Edit` roughly doubles in its per-instance code** (+446 −46). The edit walk in
  `api_contract_test.exs` does not yet reach blocks (§7, owed). Until it does, the path
  rules are pinned by example tests and reverts only, not by an independent oracle.
- **Path strings at depth.** A report names a member by its full path, so a chain n deep
  with a reported member at every level builds O(n²) bytes of names. Reductions stay
  linear (§0); memory does not. At the conventional family's 16 levels (research CNV-16)
  this is negligible; at 800 it is measurable (unverified in wall time).
- **Report details.** `{:added, path, map}` for a whole nested instance carries a map, as
  `:added` for a timer already does. A host that assumed integers would break; the report
  kinds are an open set, but their details' shapes are not stated.
- **Fix F15 stays open.** A nested member's refusal cites the instance's line in the
  program, not the member's line in the block's file, and carries no file.
- **`user?/1` trusts a body's rungs as compiled,** as `Logex.Runtime` trusts a program's. A
  hand-built body whose tags agree with its members passes, and is outside the contract,
  as a hand-built `%Program{}` is.
- **A block's warnings live inside its type** (`type.body.warnings`). A host that compiles
  a program never sees its blocks' warnings unless it compiles each block file itself.
- **Per-`cal` cost.** `FbType.signature/1` is rebuilt at every energised `cal`: 265
  reductions for a seal through `cal` against 151 inline. Precomputing it into the type is
  a cheap later change.
- **The loader stops at the first broken dependency** (F2-Q14), so a user fixes one file
  per compile.
